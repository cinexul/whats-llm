AIに文書を渡す前に、三つのことを確認しましょう。データはどこへ行くか、誰が見られるか、その経路は今回の仕事に適しているか。答えはモデル名だけでなく、製品と処理全体で決まります。本書のほかの章で「むやみに貼らない」と書いているときは、この章を指しています。

## 一、ツールも含めてデータの経路をたどる

AIアプリが送るのは、今入力した一文だけとは限りません。会話履歴、添付ファイル、検索した文書、スクリーンショット、ツールの結果もモデルへの入力になり得ます。アプリがその一部だけを選んだり、要約・切り詰めたりすることもあります。

| 経路 | 確認すること |
| --- | --- |
| クラウドモデル | どの提供者が、どのアカウント・規約でその内容を受け取るか |
| ローカルモデル | モデルが本当に端末上で動いているか、アプリがクラウド機能も使っていないか |
| 接続したツール | 検索サービス、コネクター、外部API、リモートMCPサーバーが何を受け取り、返すか |
| モデル周辺の保存先 | 会話履歴、保存されたメモリー、実行ログ、トレース、キャッシュ、共有フォルダー、バックアップ |

ローカルモデルならモデルは手元の端末で動きますが、処理全体がオフラインとは限りません。Web検索は検索語を外へ送り、コネクターは私的な文書を読み、トレースサービスはツールの入出力を記録する場合があります。ローカルのファイルやバックアップにもアクセス制御が必要です。逆に、クラウド製品だから接続先すべてに全情報が渡るわけでもありません。情報源 → アプリ → モデル・ツール → ログ・保存先と一本の線を描くほうが、「ローカル」「企業向け」という名前より実態をつかめます。

## 二、学習利用・保持・アクセス・メモリーを分ける

| 問い | 確認したいこと |
| --- | --- |
| 学習利用 | 内容はモデル改善に使われるか。どの設定で制御し、どんな例外があるか |
| 保持 | 何をどのくらい保存し、削除すると何が消えるか |
| メモリー | 製品が会話から情報を取り出して保存し、後でコンテキストに戻すか。初期設定で有効か。どこで確認・削除できるか |
| アクセスと共有 | 作業領域のメンバー、管理者、提供者、ツールサービスは見られるか |
| 場所と契約 | このサービスとデータ経路は、組織と今回の仕事に承認されているか |

「学習に使わない」は「保存しない」と同じではありません。履歴、運用記録、ツールのトレースを別の規則で保持する製品もあります。履歴を無効にする、新しい会話を開く、会話を削除する、はそれぞれ効果が違い、どれも全ログとバックアップを直ちに消すものではありません。企業アカウントやAPIは個人用と規約が異なる場合がありますが、有料というだけでは判断できず、接続先ツールに独自の方針があることもあります。

メモリーは別に確認しましょう。モデル自体は会話をまたいであなたを覚えていません（第9章）。いわゆる「メモリー」は、製品が保存した情報を後の会話でコンテキストに入れ直す機能です。例えば2026年10月時点で、ClaudeのFree、Pro、Maxプランではメモリーが初期設定で有効で、会話を削除しても、そこから作られたメモリーの項目は消えません。実用的な対策は次のとおりです。

- 機微な内容を扱うときは、一時チャット（製品によってはシークレットチャット）を使うか、先にメモリーをオフにする。
- ときどきメモリーの設定を開き、残すべきでない項目を削除する。
- パスワードや身分証番号の保管場所としてメモリーを使わない。

## 三、データ四段階：実用上の初期判断であり、法的な分類ではない

組織によって名前や規則が異なり、もっと厳しい場合もあります。次の表は日常判断の出発点です。

| 段階 | 例 | 基本の対応 |
| --- | --- | --- |
| 1. 公開 | 公開記事、公開された製品説明 | 通常は利用できる。利用権を尊重し、私的な情報が混ざっていないか確認する |
| 2. 内部 | 日常業務の下書き、非公開の会議議題 | 承認済みツールを使い、必要な部分だけ渡す |
| 3. 機微 | 顧客記録、私的な契約、個人情報 | アクセス・保持・取扱いを適切に定めた承認済み手順を使い、不要な詳細を除く |
| 4. 厳重な制限が必要 | 本番の認証情報、身分証、医療記録、重要な営業秘密 | 認証情報はプロンプトに一切入れない。他の制限対象データは、特に承認された保護の整った環境でのみ扱う |

**データ最小化**とは、仕事に必要な情報だけを渡すことです。顧客メールの文章を整えるなら、名前を「顧客A」に置き換え、口座番号を省けます。特定の顧客を識別する必要があるサポート業務なら、適切な権限を備えた承認済みシステムで扱います。

名前を消しただけで匿名になったり、分類が下がったりはしません。住所、珍しい役職、注文履歴、いくつかの詳細の組み合わせから個人を識別できる場合があります。画像や添付ファイルもデータです。機微な個人情報を任意のチャットへ気軽に貼るべきではありませんが、正式に許可された医療・顧客対応・社内業務でAIを使えないという意味ではありません。情報、目的、サービス、保護策を対応させることが大切です。

## 四、本物の認証情報は安全な設定欄に

パスワード、APIキー、セッションCookie、アクセストークンは、操作する力そのものです。使える人やプログラムは、データを読み、システムを変え、費用を発生させられるかもしれません。

例では`YOUR_API_KEY`のような仮の値を使います。本物は製品の指定する秘密情報の設定欄、シークレット管理サービス、承認済みの認証手順で扱い、会話、ソースコード、画像、診断ログには貼り付けません。安全に保管した場合も、誰が使えるか、何ができるかを絞ります。

自分でコードを書いたり、コーディングエージェントを使ったりするなら、さらに三つ覚えておきましょう。

- キーはGitのリポジトリにコミットしない。ファイルを消しても、古い版に残っていることが多いからです。
- 多くのプロジェクトでは、キーを`.env`というテキストファイルに置きます。`.env`を`.gitignore`（Gitに記録させないファイルの一覧、第26章）に書けば、コミットされません。
- コーディングエージェントは`.env`を読んだり、コマンドの実行中に環境変数を表示したりすることがあります。読み取りを禁止するツールの設定（例えばClaude Codeの設定に`Read(./.env)`という拒否ルールを書く）を使うか、権限を絞ったテスト用のキーだけを渡し、エージェントが読めない場所にキーを置くようにします（第35章）。

鍵を入力していなくても、接続したAgentは既に権限を持っている場合があります。ログイン済みのアカウントやコネクターを通じて、あなたの代わりに文書を読んだり、メッセージを送ったりできます。必要なアカウントとツールだけを接続し、情報を外に出す前に宛先を確認します。

有効な認証情報を誤って露出させたら、漏えいしたものとして扱います。速やかに無効化・交換し、関連するアクセス記録を確認して、サービスやチームの事故対応手順に従います。会話を削除するだけでは、その認証情報は有効なままで、コピーも残っているかもしれません。

## まとめ

- モデル、接続ツール、ログ、バックアップまで経路を追います。「ローカルモデル」は経路の一部しか表しません。
- 学習利用、保持、メモリー、アクセス、削除は別々の制御です。メモリーは初期設定で有効なこともあるので、機微な内容は一時チャットを使うか先にオフにします。
- 分類と最小化で判断し、許可された機微データの業務にも適切な保護を用意します。
- 本物の認証情報は安全な設定欄に置き、リポジトリに入れず、エージェントになるべく読ませず、コネクターが持つ権限も絞ります。
- 鍵が露出したら無効化・交換と調査を行います。会話の削除は対処になりません。

次章では別のコスト、料金・利用枠・不要な文脈について考えます。
