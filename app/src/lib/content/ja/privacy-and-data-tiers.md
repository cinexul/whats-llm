AIに文書を渡す前に、**データはどこへ行き、誰がアクセスでき、その経路は今回の仕事に適しているか**を確認しましょう。答えはモデル名だけでなく、製品と処理全体によって決まります。

本章では、日常の判断に使える四段階のものさしを紹介します。必要な情報を適切な保護の下で活用し、本物のパスワードや鍵は安全な設定欄に保管するためです。

## 一、ツールも含めてデータの経路をたどる

AIアプリが送るのは、今入力した一文だけとは限りません。選ばれた会話履歴、添付ファイル、検索した文書、スクリーンショット、ツールの結果もモデルへの入力になり得ます。アプリは文脈を選択・要約・切り詰めるため、毎回すべての履歴を送るとは限りません。

| 経路 | 確認すること |
| --- | --- |
| **クラウドモデル** | 選択した文脈をどの提供者が、どのアカウント・規約で受け取るか |
| **ローカルモデル** | モデルが端末上で動くか、アプリがクラウド機能も使うか |
| **接続したツール** | 検索サービス、コネクター、外部API、リモートMCPサーバーが何を受け取り、返すか |
| **モデル周辺の保存先** | 会話履歴、保存されたメモリー、実行ログ、トレース、キャッシュ、共有フォルダー、バックアップ |

ローカルモデルなら、モデルを手元の端末で動かせます。ただし、それだけで**処理全体**がオフラインになるわけではありません。Web検索は検索語を外へ送り、コネクターは私的な文書を取得し、トレースサービスはツールの入出力を記録する場合があります。ローカルのファイルやバックアップにもアクセス制御が必要です。

逆に、クラウド製品だから接続先すべてに全情報が渡るとも限りません。実際の経路と権限を確認しましょう。**情報源 → アプリ → モデル・ツール → ログ・保存先**と簡単に描く方が、「ローカル」「企業向け」という名前だけより実態をつかめます。

## 二、学習利用・保持・アクセス・メモリーを分ける

これらは別の問いです。

| 問い | 確認したいこと |
| --- | --- |
| **学習利用** | 内容はモデル改善に使われるか。どの設定や例外があるか |
| **保持** | 何をどのくらい保存し、削除すると何が消えるか |
| **メモリー** | 製品が会話から情報を取り出して保存し、後でコンテキストに戻すか。初期設定で有効か。どこで確認・削除できるか |
| **アクセスと共有** | 作業領域のメンバー、管理者、提供者、ツールサービスはアクセスできるか |
| **場所と契約** | このサービスとデータ経路は、組織と今回の仕事に承認されているか |

**「学習に使わない」は「保存しない」と同じではありません。** 履歴、運用記録、ツールのトレースを別の規則で保持する製品もあります。履歴を無効にする、新しい会話を開く、会話を削除する、といった操作も効果が異なります。どれか一つで全ログとバックアップが直ちに消えるとは考えないでください。

メモリーは別に確認しましょう。モデル自体は会話をまたいであなたを覚えていません（第9章）。いわゆる「メモリー」は、製品が保存した情報を後の会話でコンテキストに入れ直す機能です。会話から自動的にメモリーを作る製品もあり、初期設定で有効な場合もあります。例えば2026年10月時点で、ClaudeのFree、Pro、Maxプランでは「チャットからのメモリー」が初期設定で有効で、会話を削除しても、そこから作られたメモリーの項目は消えません。実用的な対策は次のとおりです。

- 機微な内容を扱うときは、一時チャット（製品によってはシークレットチャット）を使うか、先にメモリーをオフにする。
- ときどきメモリーの設定を開いて保存内容を確認し、残すべきでない項目を削除する。
- パスワードや身分証番号のような情報の保管場所としてメモリーを使わない。

機能の名前や場所は製品ごとに違うので、使っている製品のヘルプで確認してください。

具体的な製品、プラン、設定、契約を確認しましょう。企業アカウントやAPIは個人用チャットと規約が異なる場合がありますが、有料というだけでは判断できません。接続先ツールに独自の方針がある場合もあります。一律の保持日数を暗記するより、実際の経路に適用される現在の規則を調べましょう。

## 三、データ四段階：実用上の初期判断であり、共通の法律ではない

組織によって名前や規則が異なり、もっと厳しい場合もあります。次の表は日常判断の出発点です。

| 段階 | 例 | 基本の対応 |
| --- | --- | --- |
| **1. 公開** | 公開記事、公開された製品説明 | 通常は利用できる。利用権を尊重し、私的な情報が混ざっていないか確認する |
| **2. 内部** | 日常業務の下書き、非公開の会議議題 | 承認済みツールを使い、必要な部分だけ渡す |
| **3. 機微** | 顧客記録、私的な契約、個人情報 | アクセス・保持・取扱いを適切に定めた承認済み手順を使い、不要な詳細を除く |
| **4. 厳重な制限が必要** | 本番の認証情報、身分証、医療記録、重要な営業秘密 | 認証情報はプロンプトに入れない。他の制限対象データは、特に承認された適切な保護のある環境でのみ扱う |

データ最小化とは、**仕事に必要な情報だけを渡すこと**です。顧客メールの文章を整えるなら、名前を「顧客A」に置き換え、口座番号を省けます。特定の顧客を識別する必要があるサポート業務なら、適切な権限を備えた承認済みシステムでその情報を扱うことができます。

名前を消しただけで匿名になったり、分類が下がったりするわけではありません。住所、珍しい役職、注文履歴、複数の詳細の組み合わせから、個人を識別できる場合があります。画像や添付ファイルもデータです。

> **ポイント：** 機微な個人情報を、任意のチャットへ気軽に貼り付けるのは避けましょう。それは、正式に許可された医療・顧客対応・社内業務での利用まで一律に禁止するという意味ではありません。情報、目的、サービス、保護策を対応させます。

## 四、本物の認証情報は安全な設定欄に

パスワード、APIキー、セッションCookie、アクセストークンは、操作する力そのものです。利用できる人やプログラムは、データを読み、システムを変更し、費用を発生させられるかもしれません。

例では`YOUR_API_KEY`のような仮の値を使います。本物は製品の指定する秘密情報の設定欄、シークレット管理サービス、承認済みの認証手順で扱ってください。会話、ソースコード、画像、診断ログに貼り付けないでください。安全に保管した場合も、利用者と権限範囲を制限する必要があります。

自分でコードを書いたり、コーディングエージェントを使ったりするなら、さらに三つ覚えておきましょう。

- キーは決してGitのリポジトリにコミットしない。ファイルを消しても、古い版に残っていることが多いからです。
- 多くのプロジェクトでは、キーを`.env`というテキストファイルに置きます。`.env`を`.gitignore`（Gitに記録させないファイルの一覧、第26章）に書けば、コミットされません。
- コーディングエージェントは`.env`を読んだり、コマンドの実行中に環境変数を表示したりすることがあります。読み取りを禁止するツールの設定を使うか、権限を絞ったテスト用のキーだけを渡すなど、エージェントが読めない場所にキーを置くようにします（具体的な方法は第35章）。

**鍵を入力していなくても、接続したAgentは既に権限を持っている場合があります。** ログイン済みのアカウントやコネクターを通じて、委任された権限で文書を読んだり、メッセージを送ったりできます。必要なアカウントとツールだけを接続し、情報を外に出す前に宛先を確認します。

有効な認証情報を誤って露出させたら、漏えいした可能性があるものとして、速やかに無効化・交換し、関連するアクセス記録を確認して、サービスやチームの事故対応手順に従います。会話を削除するだけでは、その認証情報は無効にならず、すべてのコピーを消すこともできません。

## まとめ

- モデル、接続ツール、ログ、バックアップまで経路を追います。「ローカルモデル」はその一部だけを表します。
- 学習利用、保持、メモリー、アクセス、削除は別々の制御です。メモリーは初期設定で有効なこともあるので、機微な内容は一時チャットを使うか先にオフにします。
- 分類と最小化を使い、許可された機微データの業務にも適切な保護を用意します。
- 本物の認証情報は安全な設定欄に置き、リポジトリにコミットせず、エージェントに読ませないようにし、接続済みの権限も制限します。
- 鍵が露出したら交換と調査を行い、会話の削除だけに頼らないでください。

   - C. 有料プランなら、ほかの条件もすべて安全
   - D. モデル名だけ。新しいほど配慮されている
   > **答えB。** 学習しないという約束は、保存ゼロや、あらゆる機微情報を扱ってよいという約束ではありません。メモリー機能も別に確認します。有料かどうか（C）やモデル名（D）では、保持、アクセス、削除の問題に答えられません。
