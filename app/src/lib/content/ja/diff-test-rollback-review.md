第4部のうち一章だけしか学ぶ余裕がないなら、この章を選んでください。

第23章で見たとおり、AIは手を動かし、しかも間違えます。やり終えたことは、やり遂げたこととは限りません。では、コードを書けない人は、AIが書いたコードが正しいかどうかをどう確かめればよいのでしょうか。

検収は、コードを一行残らず読み解くことではありません。やることは素朴なものばかりです。どこを変えたかを見る（diff）。具体的なチェックで、本当にできていて、ほかを壊していないかを確かめる。壊れたときにどう戻すかを知っておく。最後に三つの問いで締めくくる。本章で一つずつ扱い、第五節で「コードを読めなければならないのか」についての本書の立場をはっきりさせます。

## 一、diffを読む：一種の「間違い探し」ゲーム

AIが変更を終えたら、最初にすることは「できた？」と聞くことではなく、変更をdiffの形で見せてもらうことです。diff（差分）とは、変更前と変更後の対比です。ほとんど同じ二枚の絵で間違い探しをするように、diffは違う箇所を直接囲んで見せてくれます。原稿と一行ずつ突き合わせる必要はありません。

だいたいこんな見た目です（色や表示はツールによって少し違います）。

```diff
  function greet(name) {
-   return "こんにちは、" + name;
+   return "こんにちは、" + name + "！お帰りなさい";
  }
```

読み方は三つだけです。

- 先頭に`+`があり、たいてい緑で表示される行：新しく足した行。
- 先頭に`-`があり、たいてい赤で表示される行：削った行。
- 記号のない行：変わっていない行。前後の文脈として表示されています。

上の変更は、「こんにちは、〇〇」だけだったあいさつに「！お帰りなさい」を足したものです。一回の変更が複数のファイルにまたがることもあり、diffはファイルごとに一か所ずつ並べてくれます。一行ずつの文法が分からなくてかまいません。まず、専門知識がなくても答えられる二つの問いに答えます。

1. 変えた場所は合っているか。トップページの見出しの色を変えてと頼んだのに、diffでは「ユーザーのログイン」の部分が変わっている。そのコードが読めなくても、それていることは分かります。
2. 範囲が大きすぎないか。小さな見出しを一つ変えてほしいだけなのに、十数個のファイル、数百行が変わっている。誤解したか、ついでに触ってはいけないところまで触ったかのどちらかです。

料理人でなくても、「サラダを頼んだのに、なぜ角煮が出てきたのか」は分かるのと同じです。

読んでも分からない部分は、AIに説明させます。たとえばこう頼みます。

> 「ファイルごとに、何を変えたか、なぜ変えたかを普通の言葉で説明して。そのうえで、危険のある変更を別に挙げて：データを削除・上書きしないか、権限やログインに関わらないか、ネット経由で何かを送らないか、パスワードや鍵に触れないか、費用が発生しないか。自信のないところも示して。」

説明とdiffを突き合わせます。見出ししか変えていないと言うのに、diffにログイン関係のファイルがあれば、理由を聞きましょう。

## 二、テストと検収チェック：本当にできていて、ほかを壊していないか

何を変えたかが分かったら、次の問いです。本当にできているか。Aを直したついでにBを壊していないか。後者はプログラミングではとてもよくあることで、回帰（regression）と呼ばれます。もともと正常だった機能が、新しい変更で壊れることです。Bの不具合はdiffの中にないこともあり、diffを見ただけでは見つかりません。

テスト（test）とは、あらかじめ書いておいた小さなチェックの集まりで、「これらの機能はまだ正常か」を自動で確かめます。出荷前の品質検査ラインのように、一つでも不合格なら赤ランプがつきます。テストを書けなくても、その結果は使えます。変更後、今回の変更に関係するテストを実行させ、三つのことを聞きます。どのチェックを実行したか。どれが通り、どれが失敗したか。テストされていないのは何か。

結果を読むときの注意は二つです。全部通っても、テストした範囲に問題がないというだけで、すべてのケースが正しいわけではありません。失敗があれば、まず原因を調べます。今回の変更のせいかもしれないし、もともとの問題や環境の問題かもしれません。マージ前に解決するか、原因と影響をはっきり書き残します。

テストのほかに、あなた自身の検収チェックも同じくらい大切です。コードを書かない人にとっては、むしろこちらが主な手段です。手を動かす前に「何ができたら完成か」を、そのとおりに操作できる手順として書いておきます。

> トップページの検索ボックスに「請求書」と入れると、タイトルに「請求書」を含む記事が一覧表示される。何も入れずに検索してもエラーにならない。ウィンドウをスマホの幅まで狭めても、検索ボックスが見出しに重ならない。

変更後、この手順どおりに自分で操作します。プロジェクトにテストがなければ、この手順があなたのテストです。言い回しの修正なら、文章を校正し、リンクを一通りクリックすれば十分です。動きの変更なら、必ず実際に使ってみます。「検証済みです」というAIの言葉ではなく、自分の目で見た結果を信じてください。

## 三、巻き戻し：何を復元できるか知っておく

巻き戻し（ロールバック）とは、選んだ変更を、以前の分かっている状態に戻すことです。ローカルのプロジェクトでは、たいていGitを使います。Gitが保存するのは、あなたがコミット（commit）した版だけで、編集の一つひとつを自動で記録するわけではありません。大きな変更の前には、出発点をコミットするかバックアップしておきます。Gitを使ったことがなければ、インストールと基本のコマンドは第26章の「Gitの最小限の始め方」にあります。

巻き戻しには限界があります。Gitは一度もコミットしていないファイルやローカルのデータベースを守らず、送信済みのメール、公開した内容、支払った料金、リモートのデータベースの変更も取り消せません。クラウドの作業環境のチェックポイントにも、対象範囲と保存期間があります。こうした限界は第26章で詳しく扱います。検収の場面で役に立つルールは一つだけです。どう取り消すか説明できない操作は、まだ承認しないこと。

## 四、最終チェックの三つの問い

diffを見て、チェックを走らせ、戻り道を確かめたら、最後に三つの問いで締めくくります。AIが「できました」と言うたびに一通りさらい、一つでも答えられなければ、まだマージしません。

1. 何を変えたか。ファイルごとに普通の言葉で説明させ、diffと突き合わせて場所と範囲が合っていることを確かめ、「今回の変更は何のためのものか」を一言で言えること。
2. 本当にできていて、ほかを壊していないか。先に書いた検収手順どおりに自分で試し、関連するチェックが通り、失敗は原因が分かっていて、テストされていない部分も把握していること。
3. 問題があったときの代償はどれくらいで、元に戻せるか。お金、個人データ、パスワードや鍵、ファイルの削除、外部への公開に関わる変更なら、二人目のレビューを経たか。戻り道は用意できているか。

一つ目に答えられないときは、AIに戻って聞きます。「この部分は何をしているの？ なぜこう変えたの？」 あなたが言い直せるようになるまで説明させます。説明がはっきりしない、聞けば聞くほど怪しくなるなら、その変更自体に問題がある可能性があります。

## 五、コードを読めなければならないのか：本書の立場

プログラミングができない人も、コードを一行残らず読めなくても、AIの変更に責任を持てます。ただし、次の四つが条件です。

1. AIの「完了しました」を信じるのではなく、具体的な検収チェックで動きを確かめる（第二節）。
2. diffを普通の言葉で説明させ、危険のある箇所を自分から挙げさせる（第一節）。
3. お金、個人データ、パスワードや鍵、ファイルの削除、外部への公開に関わる変更は、二人目のレビューを受ける。新しい会話を開いて、それまでのやり取りを持たないエージェントにそのdiffだけをレビューさせるか、詳しい人に見てもらいます。同じ会話のAIは、さっきまでの考えを引きずっていて、自分の案をかばいがちです。
4. 元に戻せないものは実行しない（第三節、第26章）。

> **ポイント：** 一行一行を読めることは条件ではありません。何を変えたか説明できない、検収手順で試していない、危険の大きい変更を誰もレビューしていない、問題が起きても戻せない。このどれか一つでも当てはまれば、マージしないでください。

この先のプロジェクトの章も、この基準で検収します。たとえば個人サイトを作るとき（第31章）は、ブラウザを再読み込みして見た目を確かめることが検収チェックです。サイトを一般に公開する、訪問者の情報を集め始めるとなったら、二人目のレビューが必要な範囲に入ります。

## 六、これらを一連の動作につなぐ

これらの動作は、第24章の作業ループの「検収」にあたります。

```text
AIが「できました」
     │
     ▼
①diffを見て、普通の言葉で説明させる ──→ 場所は合っている？ 範囲は普通？ 危険は？
     │
     ▼
②検収手順で試す + 関連するチェック ──→ 失敗は原因を調べ、未テストの部分は書き留める
     │
     ▼
③最終チェックの三つの問い ──→ 何を変えたか / できたか・壊していないか / 代償と戻り道
     │
     ├── 全部通る ──→ マージしてコミットし、次の小さな一歩へ
     │
     └── 詰まった ──→ 聞きただす / 直させる / だめなら巻き戻してやり直す
```

直すほど乱れてきたら、ぐちゃぐちゃの中で無理に直すより、関係のない作業は残したまま、今回の変更を一つ前のよい状態に戻し、タスクとさっき起きた問題を伝え直すほうが速いです。必要なら新しい会話を開きます（第13章・第30章）。

## 七、よくある誤解

| 誤解 | 実際 |
| --- | --- |
| diffを見るにはコードを一行ずつ読めないといけない | まずどこを、どれだけ変えたかを見る。分からない部分は普通の言葉で説明させ、diffと突き合わせる |
| AIが「直しました」と言えば、直っている | 先に書いた検収手順で自分で試し、関連するチェックの結果も見る |
| テストが全部通れば、全部正しい | テストした範囲に問題がないだけ。何がテストされていないかも聞く |
| テストを書けないと検収できない | 「何ができたら完成か」を操作手順にして自分で試せば、それがあなたのテスト |
| 同じ会話でもう一度チェックさせれば十分 | 危険の大きい変更は、新しい会話か人にレビューしてもらう。同じ会話は自分をかばいがち |
| 壊れても、巻き戻せば全部元どおり | Gitが戻せるのはコミットした内容だけ。メール、公開、料金、リモートのデータは戻らない（第26章） |

## まとめ

- diffは変更前後の対比です。`+`は追加、`-`は削除。まずどこを、どれだけ変えたかを見て、分からない部分は普通の言葉で説明させ、危険も挙げさせます。
- テストは、それがカバーする範囲の動きを確かめます。先に書いておく検収手順は、コードを書かない人にとって主なチェック手段です。
- 巻き戻しで戻せるのは記録した状態だけです。どう取り消すか説明できない操作は、まだ承認しません（第26章）。
- 最終チェックの三つの問い：何を変えたか。できたか、壊していないか。代償はどれくらいで、戻せるか。
- 本書の立場：一行一行を読めなくてよい。そのかわり、具体的なチェックで動きを確かめ、diffと危険を説明させ、危険の大きい変更には二人目のレビューを受け、戻せないものは実行しない。

第26章では、AIに手を動かさせながら暴走させない方法、つまり権限の設定と巻き戻せる環境を扱います。

## 出典とバージョンについて

Gitで何を戻せて何を戻せないかは、2026-10-29にGitの公式ドキュメントと照合しました：[コミットの取り消し](https://git-scm.com/docs/git-revert)、[無視するファイル](https://git-scm.com/docs/gitignore)。ブランチとワークツリーの説明と出典は第26章にあります。

> 全6問。概念・誤解・場面・操作の4種類をカバーしています。まず自分で考えてから、引用ブロックの答えと解説を見てください。

1. **[基礎・概念問題]** 一つのdiffの中で、「先頭に`+`が付いた緑色の行」は何を表す？ <!-- quiz: q01 revision: 2 -->
   - A. 削られた行。変更前にはあって、変更後にはなくなった
   - B. ツールが目立たせている、重点的に確認すべきエラーの行
   - C. 新しく足された行。変更前にはなく、変更後に加わった
   - D. 変更されていない行。文脈を見せるために置いてあるだけ
   > **答えC。** diffは「変更前後の対比」です。緑＝足した(`+`)、赤＝削った(`-`)、色も記号もない行は変更されておらず、文脈を見せるためのものです（D）。Aは足すと削るを逆に覚えています。初学者が最も混同しやすい点で、「プラス記号は足す」と覚えれば間違えません。Bは色をエラー表示と取り違えています。diffそのものは正誤を判断しません。

2. **[基礎・概念問題]** 「テストを走らせる」のは主に何を確かめるため？ <!-- quiz: q02 revision: 2 -->
   - A. 今回の変更が、元は正常だった機能を壊していないか
   - B. 新しいコードの書き方が規約どおりで、読みやすいか
   - C. AIが、承認した計画のとおりに変更を進めたかどうか
   - D. 変更後に起こりうるすべてのケースが必ず正しいか
   > **答えA。** テストは工場出荷時の品質検査ラインのように、「既存の機能がまだ正常か」を自動で点検する専用のものです。目の前のdiffの中にない「あちらを立てればこちらが立たず」を捕まえられます。書き方が規約どおりか（B）、計画どおりに変更したか（C）は、diffと最終チェックの三つの問いで確かめます。テストに合格しても、対象のケースが通っただけで、すべてのケースが正しいとは限りません（D）。

3. **[基礎・誤解問題]** 「AIが『直した』と言うなら、確かに直ったのだ。そのままマージする」――どこが間違い？ <!-- quiz: q03 revision: 2 -->
   - A. 間違っていない。AIは自分のコードを確認できるので、言うとおりだ
   - B. 抜き取り確認をしていない点。一、二か所を開いて見れば十分だ
   - C. テストを全部走らせていない点。全部通れば全ケースが正しい
   - D. もっともらしく間違えているかもしれず、diffと検証で確かめる
   > **答えD。** AIはあなたをだましているのではなく、もっともらしく間違えている（第9章のハルシネーション）のです。AI自身の判断は検証の代わりになりません（A）。一、二か所の抜き取りでは、ほかの場所の問題を防げません（B）。関連するテストは対象の動作について証拠を示しますが、合格しても全ケースの正しさは証明できません（C）。

4. **[応用・誤解問題]** 「diffを見るには一行一行のコードが読み解ける必要があり、プログラミング未経験の自分にはそもそも無理だ」――この懸念はどこが余計か？ <!-- quiz: q04 revision: 2 -->
   - A. 余計ではない。コードが読めなければ、diffも読み取れない
   - B. diffで見るのは、どこを、どれだけ、正しい場所を変えたかだ
   - C. diffは見なくてよい。テストが通れば、diffの代わりになる
   - D. 変更されたファイルの数を数えれば十分で、中身は見なくてよい
   > **答えB。** 最終チェックは各行の文法を読み解くことと同じではありません。「正しい場所を触ったか、範囲は正常か」は、「頼んだのはサラダなのに牛肉の角煮が出てきた」と見抜くのと同じで、プログラミング未経験でも判断できます。テストは「違う場所を変えた」たぐいの問題を捕まえられないので、diffの代わりにはなりません（C）。ファイル数を数えるだけでは、頼んだ部分を触ったかどうか分かりません（D）。

5. **[基礎・場面]** ローカルのコード変更に失敗したとき復元できるように、何を準備しますか？ <!-- quiz: q05 revision: 2 -->
   - A. Gitのコミットかバックアップで出発点を保存し、範囲を確かめる
   - B. 新しいブランチを作れば十分で、プロジェクトのフォルダごと保存される
   - C. 画面を撮っておき、壊れたらスクリーンショットを見て手で戻す
   - D. 準備は不要で、コードを戻せばデータベースやメールも元に戻る
   > **答えA。** Gitが戻せるのは記録した内容です（基本コマンドは第26章「Gitの最小限の始め方」）。ブランチだけでは全ファイルのバックアップにも別のディレクトリにもなりません（B）。スクリーンショットではすべての変更を記録できません（C）。データベースやメールなど外部への影響には、それぞれの復旧手段が必要です（D）。作業ファイルを分けたいときは別のチェックアウトやワークツリーを使えます。クラウドのチェックポイントにも対象範囲と保持期限があります。

6. **[応用・操作/観察問題]** 出来合いのコード変更を一つ（または本章のdiffの例を）用意し、コードを読み解かなくてよいので、「最終チェックの三つの問い」を一通り練習しましょう：何を変えたか？ 本当にできていて、ほかを壊していないか？ 問題があったときの代償はどれくらいで、元に戻せるか？ 一つ目に答えられないとき、あなたはどうするつもり？ <!-- quiz: q06 revision: 3 -->
   > **観察できるはず：** 一つ目に答えられないときは、AIに戻ってファイルごとに普通の言葉で説明させ、危険のある箇所も挙げさせ、あなたが一言で言い直せるようになるまで続けます。AIの口ぶりが確信に満ちているからといって通してはいけません。二つ目は先に書いた検収手順と関連するチェックで答え、三つ目は変更がお金、個人データ、鍵、削除、公開に触れていないか、戻り道はどこかを見て答えます。三つとも答えられたら、マージします。
