CodexはOpenAIのコーディングエージェントです。プロジェクトを調べ、ファイルを編集し、コマンドを実行し、変更のレビューも手伝います。本章では、第24章の「調査、計画、実行、検収」を、実際にやり終えられる練習に落とし込みます。

インストール方法、プラン、コマンドは2026-10-29に公式資料と照合しました。インストールしたバージョンや組織の設定によって違うことがあるので、まずバージョンを記録し、使えるコマンドを確かめてください。

## 一、作業する場所を選ぶ

| 形態 | 作業の入口 | 最初に確認すること |
| --- | --- | --- |
| CLI | ターミナル。通常はローカルのプロジェクトを操作 | 現在のディレクトリ、Gitの状態、コマンドの権限 |
| IDE拡張機能 | 対応するコードエディター | 開いているプロジェクト、変更予定のファイル |
| デスクトップアプリ | 専用アプリ | タスクが使うプロジェクトと実行環境 |
| Web／クラウドタスク | ブラウザー。設定済みの環境で処理を実行 | リポジトリ、ブランチ、準備手順、ネットワーク、シークレット |

ローカルでCLIを使っても、モデルがあなたのパソコンでオフラインで動くわけではありません。クライアントはタスクのコンテキストをサーバーに送ります。クラウドタスクにも、あなたのパソコンの依存関係、未コミットのファイル、ログイン情報が自動で引き継がれるわけではありません。

最初は既存の小さなGitプロジェクトで試しましょう（Gitのインストールと基本は第26章「Gitの最小限の始め方」）。作業ツリーがクリーンか確かめ、途中の変更は別に保存します。新しいブランチを作るだけでは、未コミットの作業のバックアップにはなりません。

## 二、インストール、ログイン、状態確認

2026年10月時点の公式ドキュメントでは、単体のインストーラーが最初に案内されています。Node.jsが必要なのは、あとで触れるnpmで入れる場合だけです。macOSまたはLinuxでは次のとおりです。

```bash
curl -fsSL https://chatgpt.com/codex/install.sh | sh
```

WindowsのPowerShellでは次のとおりです。

```powershell
powershell -ExecutionPolicy ByPass -c "irm https://chatgpt.com/codex/install.ps1 | iex"
```

どちらもインストールスクリプトを取得して実行するコマンドです。公式のアドレスであることを確かめ、組織の規則に従ってください。Homebrewの`brew install --cask codex`や、Node.jsの入ったパソコンなら`npm install -g @openai/codex`でも入れられます。方法は一つ選べば十分です。入れたら次で確認します。

```bash
codex --version
codex --help
```

既存のプロジェクトに移動します。例のパスは実際のディレクトリに置き換えてください。以下の`git`コマンドにはGitが必要です。まだGitで管理していないプロジェクトなら、先に第26章の手順で出発点を保存してください。

```bash
cd /path/to/your/project
git status
git switch -c practice/codex-first-task
codex
```

初めて`codex`を実行すると、Sign in with ChatGPT（ChatGPTのアカウントでログイン）を選べます。2026年10月時点の公式料金ページでは、ChatGPTのFree、Go、Plus、Pro、Business、Edu、EnterpriseのどのプランにもCodexが含まれますが、利用枠は大きく違います。Freeは手早い小さな作業で試してみる位置づけ、Goは軽い作業向けです。公式READMEはPlus、Pro、Business、Edu、Enterpriseでのログインを勧めています。APIキーは別の認証・課金の経路で、Codexの利用者全員が用意するものではありません。キーを会話に貼り付けないでください。

対話画面に入ったら、`/`と入力すると今のバージョンのコマンドが表示されます。よく使うものは次のとおりです。

| セッション内コマンド | 目的 |
| --- | --- |
| `/status` | セッションの設定とトークン使用量を見る |
| `/permissions` | Codexに許可する操作を選ぶ（第26章） |
| `/plan` | 計画モードに切り替える（第27章） |
| `/diff` | Gitの変更を見る。まだ追跡していない新しいファイルも含む |
| `/review` | 今の変更をレビューし、問題を探す |
| `/init` | プロジェクトの指示`AGENTS.md`を作る |

## 三、一つの小さな作業を完了する

まず範囲を限定して依頼します。

```text
プロジェクトの指示とREADMEを読んでください。文書に記載された
確認方法を特定してください。まだ編集せず、READMEの小さな改善を
一つ提案し、どう確認するかを説明してください。
```

提案を理解できたら、変更を許可します。

```text
提案したREADMEの改善だけを実施してください。無関係な既存の変更は
保持してください。diffと関連するリンクやコマンドを確認し、変更内容、
実際に確認したこと、未確認の点を報告してください。
この練習では公開、push、デプロイはしないでください。
```

二段階にしているのは、操作に慣れるためです。慣れたら、明確な依頼で実装と検証をまとめて許可でき、無害な細かい手順を毎回承認する必要はありません。

完了したら`/diff`で見るか、ターミナルで次を実行します。

```bash
git diff --stat
git diff
git status --short
```

そのあと第25章のとおり検収します。変更を一つずつ普通の言葉で説明させ、diffと突き合わせます。文書の変更なら文章とリンクを確かめ、機能の変更なら関連するテストを実行して自分でも試します。「エージェントが成功と言った」ことは、実際のコマンドの出力や自分の目で見た結果ほどの証拠にはなりません。`/review`は最初のチェックに向いていますが、お金、個人データ、鍵、削除、公開に関わる変更は、新しい会話か人にもう一度見てもらいます。

## 四、プロジェクトの指示を残す

Codexはプロジェクトの指示を`AGENTS.md`に書きます。`/init`で下書きを作れますが、使う前に内容を確認します。たとえば次のように書けます。

```markdown
# このプロジェクトの作業ルール
- 編集前にREADMEを読む。
- 変更は依頼された目的に絞る。
- リポジトリで指定されたパッケージ管理と確認コマンドを使う。
- 例に認証情報や実際の顧客データを含めない。
- 検証結果と実行できなかった確認を報告する。
```

実際のコマンドを確かめたら、一般的な表現を具体的なコマンドに置き換えます。長い参考資料は別ファイルにしてリンクします。指示はコンテキストに読み込まれるもので、モデルを再学習させるわけではなく、すべての規則が守られる保証もありません。スキルは再利用する手順をまとめ、保存されたメモリはノートを残しますが、どちらも明示的なプロジェクトの規則や、実際に効いている権限の制限の代わりにはなりません。

## 五、権限、クラウド、費用を確認する

サンドボックスは実行環境がアクセスできる範囲を制限し、承認ポリシーはどの操作にあなたの承認が要るかを決めます。この二つの組み合わせで、すでに許可されている操作、確認が必要な操作、禁止される操作が分かれます。2026年10月時点で、CodexはGitで管理されたフォルダでは既定でプロジェクトのファイルを直接変え、サンドボックスが許すコマンドを実行し、範囲を越えるときだけ確認します。それ以外のフォルダでは既定で読み取りのみです（権限の四段階は第26章）。ですから、影響のあるコマンドの前に必ず確認画面が出るとは考えないでください。

クラウドのタスクでは、対象のリポジトリとブランチを確認し、環境の準備手順で依存関係を入れ、どのネットワーク接続先とシークレットを使えるかを把握します。マージ前にdiffと検証結果を確認しましょう。ブランチはコードの変更を戻す助けになりますが、送信済みのメールは取り戻せず、外部のデータベースも自動では元に戻りません。

料金はアカウントの経路で区別します。ChatGPTでログインしていれば、Codexはプランに含まれる利用枠を消費します。大きなタスクほど多く使いますが、トークンごとの請求が別に来るとは限りません。APIキーを使えばAPIの価格で別に課金され、ChatGPTの購読料で賄われることはありません。追加購入した利用枠や接続サービスは別料金です。料金ページは、APIの価格から購読でどれだけの作業ができるかを見積もらないよう、わざわざ注意しています。詳しくは第38章を参照してください。

1. **[基礎・概念問題]** Codexの説明として正しいものは？ <!-- quiz: q01 revision: 2 -->
   - A. Webページでしか使えず、手元のPCには入れられない
   - B. OpenAIのコーディングエージェント。入口が複数ある
   - C. CLIを使うと、モデルは自分のPC上でオフラインで動く
   - D. どのプランでも、まずAPIキーを用意する必要がある
   > **答えB。** CLI、エディター拡張、デスクトップアプリ、Web／クラウドの入口があり、実行環境が異なる場合があるので、Aは誤りです。CLIをローカルで動かしてもオフライン推論にはならず、クライアントはタスクのコンテキストをサービスへ送ります（C）。ChatGPTアカウントでログインすれば使え、APIキーは別の経路です（D）。

2. **[基礎・場面問題]** 対象のChatGPTプランを契約しています。Codex用にAPIクレジットを購入する前に何を確認する？ <!-- quiz: q02 revision: 2 -->
   - A. 購読にCodexは含まれないと決めて、APIを買うのが早い
   - B. 購読にAPI呼び出しもすべて含まれると決めて、確認しない
   - C. まずChatGPTでログインし、使える利用枠を確かめる
   - D. ChatGPTログインはnpm版だけなので、先に入れ直す
   > **答えC。** ChatGPTログインとAPI認証は別の経路です。別課金のAPIを選ぶ前に、現在のアカウントと利用枠を確認します。AとBは確認せずに決めつけています。ログイン方法はインストール方法と関係なく、単体インストーラー、Homebrew、npmのどれで入れてもChatGPTでログインできます（D）。

3. **[基礎・概念問題]** `AGENTS.md`が提供するものは？ <!-- quiz: q03 revision: 2 -->
   - A. コンテキストに読み込まれるプロジェクトの指示
   - B. ファイルへのアクセスを制限するセキュリティ設定
   - C. 書いたルールをモデルに学習させるための仕組み
   - D. Codexにすべての規則を必ず守らせる保証
   > **答えA。** プロジェクトの約束事を明文化し、作業時にコンテキストへ読み込まれます。ファイルへのアクセスを実際に制限するのはサンドボックスと権限設定です（B）。モデルの重みは変わりません（C）。コンテキストに入った規則でも、すべてが守られる保証はありません（D）。

4. **[応用・誤解問題]** 「危険なコマンドならCodexは必ず先に聞く」という説明に足りないものは？ <!-- quiz: q04 revision: 2 -->
   - A. 足りないものはない。危険なら必ず確認画面が出る
   - B. Gitの視点。Gitが外部への操作を自動で防いでくれる
   - C. モデルの視点。より強いモデルに替えれば先に聞く
   - D. 動作は、サンドボックス・承認ポリシー・権限で決まる
   > **答えD。** 操作は許可済み、承認待ち、禁止のいずれにもなり得るので、「毎回聞かれる」は当てになりません（A）。Gitが扱うのは記録したファイルで、外部への操作は防げません（B）。モデルを替えても承認の設定は変わりません（C）。実際の設定を確認し、承認をスキップするオプションは使わないでください（第26章）。

5. **[基礎・場面問題]** クラウドタスクが依存関係不足で失敗しました。次の一手は？ <!-- quiz: q05 revision: 2 -->

   - B. 環境の準備手順を確認し、その環境に依存関係を入れる
   - C. ネットワークとファイルの制限を外して、自分で入れさせる
   - D. 足りない依存関係を避けるように、コードを書き換えさせる
