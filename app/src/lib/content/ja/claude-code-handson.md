Claude CodeはAnthropicのコーディングエージェントです。リポジトリの調査、ファイル編集、ツール実行、Git作業などを支援します。ターミナルや対応エディターなどから利用できます。本章ではターミナルを使い、最初の作業を具体的に進めます。

インストール方法、アカウントの条件、コマンド例は**2026-10-27**に確認しました。実際のバージョンを記録してください。古いチュートリアルでは、すでに変わった導入方法や画面を説明している場合があります。

## 一、インストールして小さなプロジェクトを開く

まずアカウントを確認します。2026年10月時点の公式ドキュメントによると、Claude CodeにはPro、Max、Team、Enterpriseのいずれかのプラン、またはConsole（API）アカウントが必要で、無料のclaude.aiプランには含まれていません。Amazon Bedrockなどのサードパーティのクラウド経由でも使えます。

ターミナルに慣れていなければ、公式のデスクトップアプリ（macOS、Windows、Linux）もあり、コマンドラインを使わずにClaude Codeを利用できます。ダウンロード先は公式のセットアップ文書にあります。本章ではターミナルを例にします。

公式が推奨するのはネイティブインストーラーで、入れた後はバックグラウンドで自動更新されます。macOS、Linux（WindowsのWSLも含む）では次のコマンドです。

```bash
curl -fsSL https://claude.ai/install.sh | bash
```

WindowsのPowerShellでは次のとおりです（CMD用のコマンドも公式ドキュメントにあります）。

```powershell
irm https://claude.ai/install.ps1 | iex
```

どちらもインストールスクリプトを取得して実行するコマンドです。公式のアドレスであることを確かめ、組織のインストール規則に従ってください。Windowsでは、公式はGit for Windows（第26章）も入れることを勧めています。Claude CodeがそれでBashのコマンドを実行できるからです。入れなくても使え、その場合はPowerShellを使います。

パッケージ管理ツールでも入れられます。Homebrewなら`brew install --cask claude-code`、WinGetなら`winget install Anthropic.ClaudeCode`です。この二つは既定では自動更新されないので、定期的に`brew upgrade claude-code`または`winget upgrade Anthropic.ClaudeCode`を実行します。方法は一つ選べば十分です。公式GitHubリポジトリのREADMEではnpmによるインストールは非推奨とされており、古い記事の`npm install -g @anthropic-ai/claude-code`は、今では推奨される出発点ではありません。

インストールしたら新しいターミナルを開き、コマンドが使えることを確かめてから練習用プロジェクトに移動します。以下の`git`コマンドにはGitが必要です。まだGitで管理していないプロジェクトなら、先に第26章「Gitの最小限の始め方」で出発点を保存してください。

```bash
claude --version
claude --help
cd /path/to/your/project
git status
git switch -c practice/claude-first-task
claude
```

パスは実際のディレクトリに置き換えます。`git status`で未保存の変更がないことを確かめ（あれば先に別途保存し）、`git switch -c`で練習用のブランチを作ります。初めて`claude`を実行したらブラウザーの案内に従ってログインし、その後`/status`でセッションと有効なアカウントを確認します。プランによる利用とAPIを使う構成は別の経路です。CLIを入れただけでAPIが無料になるわけではありません。

## 二、調査の後に一つだけ変更する

最初の依頼は、たとえば次のようにします。

```text
プロジェクトの指示と README を読み、このプロジェクトの目的、
入口となるファイル、既存のチェックの実行方法を説明してください。
まだ編集せず、小さな文書改善を一つ提案してください。
```

実在するファイルやコマンドが示されているか確認し、改善を許可します。

```text
提案した文書改善を実施してください。変更は目的に必要な範囲に絞り、
diff と関連する項目を確認してください。変更したファイル、実行した
コマンド、未解決の問題を報告してください。push やデプロイはしないでください。
```

自分でも`git diff`を読みます。動作を変えたなら、関連テストを実行し、変更後の動作も試してください。知らないリポジトリについての自信に満ちた推測より、ファイルの場所で裏付けられた簡潔な説明のほうが役立ちます。

## 三、プロジェクトの指示、メモリ、スキルを区別する

`CLAUDE.md`にはプロジェクトの約束事、便利なコマンド、制約などを書きます。`/init`は下書きを支援しますが、生成内容は確認します。小さな例です。

```markdown
# プロジェクトの指示
- 動作を変える前に README と既存の実装を読む。
- 文書で指定されたパッケージ管理とテストコマンドを使う。
- タスクに必要でなければ生成ファイルを手作業で編集しない。
- 例には架空のデータを使う。
- 検証済みのことと不確かなことを区別して説明する。
```

コマンドを実際に確認してから、一般的な表現を具体化してください。マニュアル全文や認証情報は入れません。

| 仕組み | 保存するもの | 扱い方 |
| --- | --- | --- |
| `CLAUDE.md`とプロジェクト規則 | このプロジェクトで守る明示的な指示 | 他のプロジェクト文書と同様に確認・更新する |
| 自動メモリ（有効な場合） | 過去の作業から製品が保持したノート | 確認し、古くなった観察を修正する |
| スキル | 再利用する手順と、必要に応じたスクリプトや資料 | 出所を確認し、該当タスクで使う |
| 現在の会話 | 今回の要件、証拠、進捗 | 新しいセッションへ重要な状態を引き継ぐ |

`/memory`で、そのバージョンのメモリ画面を確認できます。ノートの保存や指示の読み込みは製品の機能であり、モデルの重みがプロジェクトを学習した証拠ではありません。メモリに保存された主張が自動的に正しくなるわけでもありません。

## 四、目的からコマンドを覚える

| セッション内コマンド | 目的 |
| --- | --- |
| `/help` | 利用できるコマンドを調べる |
| `/status` | セッションとアカウントの設定を見る |
| `/plan` | タスクの計画を進める |
| `/permissions` | 自分が管理できる権限規則を確認・変更する |
| `/memory` | プロジェクトの指示やメモリ設定を確認する |
| `/usage` | 提供される使用量や制限の情報を見る |
| `/diff` | 対応する画面で変更を見る |

ターミナル、エディター、クラウドでは使えるコマンドが異なる場合があります。計画は範囲が不明確なときに役立ちますが、実行環境の権限制御には代わりません。明確で限定された変更を許可した後は、通常の実装と確認を一歩ずつ承認し直す必要はありません。

## 五、実行と課金の境界を把握する

承認要求では、**どのコマンドが、どのファイルやサービスに、何をするのか**を確認します。一つの許可が繰り返しの操作を含む場合もあり、その後も毎回確認されるとは限りません。シェルコマンド、フック、スクリプト付きのスキル、外部ツールはいずれも実際の変更を起こせます。Gitブランチでは外部への送信や支払いは取り消せません。

対応していてタスクの範囲内で許可されている場合、サブエージェントに調査や実装を分担させられます。担当範囲と統合する人を決めましょう。会話が別でも作業ディレクトリが別とは限らず、並行編集で上書きする可能性があります。委譲によって元の権限が広がることはありません。

`/status`とアカウントの使用量画面で、次を区別します。

- **購読による利用：** プランの規則に従って利用枠を消費する。
- **APIや別プロバイダーによる利用：** そのアカウントの料金と制限に従う。
- **追加クレジット、有料モード、接続サービス：** 有効にすると追加料金が生じる場合がある。

個人向けプランの利用料にAPI経由の利用料金まで含まれると考えたり、長い会話は必ず別のトークン請求になると考えたりしないでください。使用量が想定外なら、プラン変更の前に有効な認証情報、モデルやモード、タスクの長さ、繰り返されるツール出力、バックグラウンド作業を調べます。

## 小テスト

1. **[基礎・概念問題]** 確認した公式ドキュメントに合うインストール方法は？ <!-- quiz: q01 revision: 1 -->
   - A. npmが公式の第一候補で、先にNode.jsを入れるのが確実だ
   - B. HomebrewやWinGetで入れれば、その後は自動で更新される
   - C. ネイティブ版など公式の方法から一つ選ぶ。npmは非推奨
   - D. 無料のclaude.aiアカウントでも、入れればすぐに使える
   > **答えC。** 公式はネイティブインストーラーを推奨し、HomebrewやWinGetも案内しています。READMEではnpmによる導入は非推奨です（A）。HomebrewとWinGetは既定では自動更新されないので、自分で更新コマンドを実行します（B）。Claude CodeにはPro、Max、Team、EnterpriseまたはConsoleのアカウントが必要で、無料プランには含まれません（D）。

2. **[基礎・概念問題]** `CLAUDE.md`に向いている内容は？ <!-- quiz: q02 revision: 1 -->
   - A. 確認済みのプロジェクト規約、便利なコマンド、制約
   - B. 毎回すぐにサービスを呼び出せるようにするAPIキー
   - C. 思い出しやすいように、これまでの全会話の記録
   - D. 「今後は権限を確認しなくてよい」という包括的な許可
   > **答えA。** プロジェクトの指示は簡潔で正確、役に立つものにします。鍵をプロジェクトのファイルに書いてはいけません（B）。全履歴は長すぎて要点が埋もれます（C）。プロジェクトの指示で権限制御を置き換えたり、無制限の許可を与えたりもできません（D）。

3. **[応用・誤解問題]** 自動メモリに古いテストコマンドが保存されていました。どうする？ <!-- quiz: q03 revision: 1 -->
   - A. メモリを優先する。過去の作業からまとめられたものだから
   - B. モデルの重みが変わった証拠なので、新しい版を待つしかない
   - C. メモリ機能をすべて切り、今後はコマンドを自分で覚える
   - D. 今のコマンドを確認してから、保存されたノートを修正する
   > **答えD。** メモリは製品が保存したコンテキストのノートで、古くなることがあります。今のリポジトリより信頼できる情報源ではなく（A）、モデルの重みの変化でもありません（B）。ノートは確認して修正できるので、一つ古い内容があったからといって機能を全部切る必要はありません（C）。

4. **[基礎・場面問題]** 長い作業の前に、予想外の費用を避けるために何を見る？ <!-- quiz: q04 revision: 1 -->
   - A. インストールに成功し、バージョン番号が表示されること
   - B. 有効なアカウント、プランの利用枠、有効にした有料機能
   - C. 購読していれば、API呼び出しもすべて含まれていること
   - D. 依頼文を短くしておけば、費用は絶対に枠を超えないこと
   > **答えB。** 購読の利用枠、API課金、追加機能は別々に確認します。実際のアカウントと使用量画面が手掛かりです。インストールの成否（A）は費用と関係ありません。購読料でAPIキーの利用まで賄われるわけではありません（C）。依頼文を短くしても使用量は保証できず、長い作業ではツールの出力やバックグラウンド作業も枠を使います（D）。

5. **[応用・場面問題]** 二つのサブエージェントが編集します。有用な準備は？ <!-- quiz: q05 revision: 1 -->
   - A. 会話が別なら自然に隔離されるので、衝突は起きない
   - B. 同じファイル群を同時に直させ、最後に良い方を選ぶ
   - C. 担当ファイルかワークツリーを分け、統合する人を決める
   - D. より広い権限を渡しておけば、共同作業が円滑になる
   > **答えC。** 明示的な隔離がなければ、並行して作業する側はファイルを共有することがあります。会話が別でもディレクトリが別とは限らず（A）、同じファイルを同時に直せば上書きし合います（B）。委譲によって元の作業の権限が広がることもありません（D）。範囲、権限、統合の調整が必要です。

6. **[基礎・操作問題]** 確認済みのコマンド、作業規約、データの扱いに関する制約を区別し、五行のプロジェクト指示を書いてください。保存済みのメモリとも比較します。 <!-- quiz: q06 revision: 1 -->
   > **観察できるはず：** プロジェクト指示は守るべき規則を示し、メモリは役立つ観察を残します。どちらもリポジトリの変化に合わせた見直しが必要です。
