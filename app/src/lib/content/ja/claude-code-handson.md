Claude CodeはAnthropicのコーディングエージェントで、プロジェクトの調査、ファイルの編集、コマンドの実行、Gitの作業を手伝います。ターミナル、エディターの拡張機能、デスクトップアプリ、Webなどの入り口があり、本章ではターミナルを例に、最初の練習を具体的に進めます。

本章のインストール方法、アカウントの条件、コマンドは2026-10-29に確認しました。作業の前に、自分が入れたバージョンを記録しておきましょう。古いチュートリアルの導入方法や画面は、すでに変わっていることがあります。

## 一、インストールして小さなプロジェクトを開く

まずアカウントを確認します。2026年10月時点で、Claude CodeにはPro、Max、Team、Enterpriseのいずれかのプラン、またはConsole（API）アカウントが必要で、無料のclaude.aiプランには含まれていません。Amazon Bedrockなどのサードパーティのクラウド経由でも使えます。ターミナルに慣れていなければ、公式のデスクトップアプリ（macOS、Windows、Linux）を使う手もあります。ダウンロード先はセットアップ文書にあります。

公式が推奨するのはネイティブインストーラーで、入れたあとはバックグラウンドで自動更新されます。macOS、Linux（WindowsのWSLも含む）では次のコマンドです。

```bash
curl -fsSL https://claude.ai/install.sh | bash
```

WindowsのPowerShellでは次のとおりです（CMD用のコマンドもあります）。

```powershell
irm https://claude.ai/install.ps1 | iex
```

どちらもインストールスクリプトを取得して実行するコマンドです。公式のアドレスであることを確かめ、組織の規則に従ってください。Windowsでは、Git for Windows（第26章）も入れておくと、Claude CodeがBashのコマンドを実行できます。入れなくても使え、その場合はPowerShellを使います。

パッケージ管理ツールでも入れられます。Homebrewなら`brew install --cask claude-code`、WinGetなら`winget install Anthropic.ClaudeCode`です。この二つは既定では自動更新されないので、定期的に`brew upgrade claude-code`または`winget upgrade Anthropic.ClaudeCode`を実行します。方法は一つ選べば十分です。古い記事にある`npm install -g @anthropic-ai/claude-code`は、公式READMEで非推奨とされています。

インストールしたら新しいターミナルを開き、コマンドが使えることを確かめてから練習用プロジェクトに移動します。以下の`git`コマンドにはGitが必要です。まだGitで管理していないプロジェクトなら、先に第26章「Gitの最小限の始め方」で出発点を保存してください。

```bash
claude --version
claude --help
cd /path/to/your/project
git status
git switch -c practice/claude-first-task
claude
```

パスは実際のディレクトリに置き換えます。`git status`で未保存の変更がないことを確かめ、`git switch -c`で練習用のブランチを作ります。初めて`claude`を実行したらブラウザーの案内に従ってログインし、その後`/status`でバージョン、モデル、ログイン中のアカウントを確認します。インストールでつまずいたら、`claude doctor`で診断情報を見られます。

## 二、調査の後に一つだけ変更する

最初の依頼は、たとえば次のようにします。

```text
プロジェクトの指示とREADMEを読み、このプロジェクトの目的、
入口となるファイル、既存のチェックの実行方法を説明してください。
まだ編集せず、小さな文書改善を一つ提案してください。
```

実在するファイルやコマンドが示されているか確認し、改善を許可します。

```text
提案した文書改善を実施してください。変更は目的に必要な範囲に絞り、
diffと関連する項目を確認してください。変更したファイル、実行した
コマンド、未解決の問題を報告してください。pushやデプロイはしないでください。
```

そのあと第25章のとおり検収します。`git diff`の変更を一つずつ普通の言葉で説明させ、diffと突き合わせます。機能を変えたなら、関連するテストを実行し、変更後の動きを自分でも試してください。

## 三、プロジェクトの指示、メモリ、スキルを区別する

`CLAUDE.md`にはプロジェクトの約束事、よく使うコマンド、制約などを書きます。セッションの開始時にコンテキストに読み込まれます。`/init`で下書きを作れますが、生成された内容は自分で確認します。小さな例です。

```markdown
# プロジェクトの指示
- 動作を変える前にREADMEと既存の実装を読む。
- 文書で指定されたパッケージ管理とテストコマンドを使う。
- タスクに必要でなければ生成ファイルを手作業で編集しない。
- 例には架空のデータを使う。
- 検証済みのことと不確かなことを区別して説明する。
```

実際のコマンドを確かめてから、一般的な表現を具体的なコマンドに置き換えます。マニュアル全文や鍵は入れません。

| 仕組み | 保存するもの | 扱い方 |
| --- | --- | --- |
| `CLAUDE.md`とプロジェクト規則 | このプロジェクトで守る明示的な指示 | 他のプロジェクト文書と同様に確認・更新する |
| 自動メモリ（有効な場合） | 過去の作業から製品が保存したノート | 確認して直す。古い観察は当てはまらなくなっていることがある |
| スキル | 再利用する手順と、必要に応じたスクリプトや資料 | 出所を確認し、合うタスクで使う |
| 現在の会話 | 今回の要件、証拠、進み具合 | 新しいセッションに重要な状態を引き継ぐ |

`/memory`では`CLAUDE.md`を編集し、自動メモリのオンオフと内容の確認ができます。どれも、製品が保存した文章をコンテキストに入れ直しているもので、モデル自体がプロジェクトを「覚えた」わけではありません。メモリに書かれた主張が、それで事実になるわけでもありません。

## 四、目的からコマンドを覚える

次のセッション内コマンドは2026年10月時点で使えます。`/`と入力すると、自分のバージョンで実際に使えるものが表示されます。

| セッション内コマンド | 目的 |
| --- | --- |
| `/help` | 使えるコマンドを見る |
| `/status` | バージョン、モデル、アカウント、接続状態を見る |
| `/plan` | 計画モードに入る：案だけ出し、ファイルは変えない（第27章） |
| `/permissions` | 許可・確認・拒否の規則を見る、変える |
| `/memory` | `CLAUDE.md`を編集し、自動メモリを管理する |
| `/diff` | 作業中の変更を見る。AIがさっき行った変更も含む |
| `/code-review` | 今のdiffに誤りがないか確認する（別名`/review`） |
| `/rewind` | 会話とAIが変えたファイルを、前のチェックポイントに戻す（入力欄が空のときEscを2回押しても開く） |
| `/usage` | このセッションの使用量とプランの利用枠を見る（別名`/cost`） |

注意が二つあります。`/rewind`が追跡するのは、Claude Codeが自分の編集機能で変えたファイルだけです。ターミナルのコマンドだけで変わったファイルや、あなたが手で変えたファイルは対象外で、外部への操作も戻せません。ドキュメントにも、Gitの代わりにはならないと明記されています。`/code-review`は同じ会話の中で動くので、最初のチェックには向いていますが、お金、個人データ、鍵、削除、公開に関わる変更は、第25章のとおり新しい会話か人にレビューしてもらいます。

## 五、権限、実行、費用の境界を把握する

権限の四段階と対応するモードは第26章にあります。2026年10月時点で、新しいバージョンのClaude Codeはターミナルでは既定でautoモードから始まります。別のモデルがあなたの代わりに操作を審査するので、毎回聞いてくるとは限りません。最初の練習では、Shift+Tabでステータスバーに「manual mode on」と出るManualモードに切り替えると、ファイル変更やコマンド実行のほとんどの前に確認してくれます。もう一度Shift+Tabを押せば、`acceptEdits`や計画モードにも切り替えられます。承認を求められたら、どのコマンドが、どのファイルやサービスに、何をするのかを読みます。一度の許可が以後の繰り返しの操作を含むこともあるので、毎回確認画面が出るとは考えないでください。ターミナルのコマンド、フック（決まったタイミングで自動実行されるスクリプト）、スクリプト付きのスキル、外部ツールは、どれも実際に影響を及ぼせます。Gitのブランチでは、送ったメッセージや支払いは取り消せません。

製品が対応していてタスクでも許可しているなら、サブエージェント（subagent）に調査や実装を分担させられます。担当範囲を分け、誰が統合するかを決めておきます。会話が別でも作業ディレクトリが別とは限らず、並行して編集すると上書きし合うことがあります。仕事を任せても、元のタスクの権限が広がるわけではありません。

費用はアカウントの経路ごとに考えます。サブスクリプションはプランの利用枠を消費し、`/usage`で確認できます。APIやサードパーティのクラウドは、それぞれの請求に従います。追加の利用クレジットを有効にすれば、その分は別に数えられます。サブスクリプションがAPIキーの料金を払ってくれることはありません。目安を一つ挙げると、2026年10月時点でAnthropicは、APIで課金される企業での利用は開発者一人あたり稼働日一日平均約13ドル、9割の利用者は30ドル未満だとしています。使用量が想定外なら、まずログイン中のアカウント、モデル、タスクの長さ、バックグラウンドの作業を確認します（第38章）。

## 出典とバージョンについて

確認日：2026-10-29。[セットアップ文書](https://code.claude.com/docs/en/setup)で、アカウントの条件、デスクトップアプリ、ネイティブインストーラー（WindowsのPowerShellとCMDを含む）、HomebrewとWinGetが既定では自動更新されないことと更新コマンド、`claude doctor`を確認。[Claude Code公式README](https://github.com/anthropics/claude-code/blob/main/README.md)でnpmによる導入が非推奨であること、[コマンドリファレンス](https://code.claude.com/docs/en/commands)で本章のセッション内コマンドと別名、[チェックポイントの文書](https://code.claude.com/docs/en/checkpointing)で`/rewind`の対象範囲と「Gitの代わりにはならない」こと、[費用の文書](https://code.claude.com/docs/en/costs)で`/usage`と平均費用の数字を確認しました。これは文書で見た状態であり、手元のインストール済みの版とは限りません。

1. **[基礎・概念問題]** 確認した公式ドキュメントに合うインストール方法は？ <!-- quiz: q01 revision: 2 -->
   - A. npmが公式の第一候補で、先にNode.jsを入れるのが確実だ
   - B. HomebrewやWinGetで入れれば、その後は自動で更新される
   - C. ネイティブ版など公式の方法から一つ選ぶ。npmは非推奨
   - D. 無料のclaude.aiアカウントでも、入れればすぐに使える
   > **答えC。** 公式はネイティブインストーラーを推奨し、HomebrewやWinGetも案内しています。READMEではnpmによる導入は非推奨です（A）。HomebrewとWinGetは既定では自動更新されないので、自分で更新コマンドを実行します（B）。Claude CodeにはPro、Max、Team、EnterpriseまたはConsoleのアカウントが必要で、無料プランには含まれません（D）。

2. **[基礎・概念問題]** `CLAUDE.md`に向いている内容は？ <!-- quiz: q02 revision: 2 -->
   - A. 確認済みのプロジェクト規約、便利なコマンド、制約
   - B. 毎回すぐにサービスを呼び出せるようにするAPIキー
   - C. 思い出しやすいように、これまでの全会話の記録
   - D. 「今後は権限を確認しなくてよい」という包括的な許可
   > **答えA。** プロジェクトの指示は簡潔で正確、役に立つものにします。鍵をプロジェクトのファイルに書いてはいけません（B）。全履歴は長すぎて要点が埋もれます（C）。プロジェクトの指示で権限制御を置き換えたり、無制限の許可を与えたりもできません（D）。

3. **[応用・誤解問題]** 自動メモリに古いテストコマンドが保存されていました。どうする？ <!-- quiz: q03 revision: 2 -->
   - A. メモリを優先する。過去の作業からまとめられたものだから
   - B. モデルの重みが変わった証拠なので、新しい版を待つしかない
   - C. メモリ機能をすべて切り、今後はコマンドを自分で覚える
   - D. 今のコマンドを確認してから、保存されたノートを修正する
   > **答えD。** メモリは製品が保存したコンテキストのノートで、古くなることがあります。今のリポジトリより信頼できる情報源ではなく（A）、モデルの重みの変化でもありません（B）。ノートは確認して修正できるので、一つ古い内容があったからといって機能を全部切る必要はありません（C）。

4. **[基礎・場面問題]** 長い作業の前に、予想外の費用を避けるために何を見る？ <!-- quiz: q04 revision: 2 -->
   - A. インストールに成功し、バージョン番号が表示されること
   - B. 有効なアカウント、プランの利用枠、有効にした有料機能
   - C. 購読していれば、API呼び出しもすべて含まれていること
   - D. 依頼文を短くしておけば、費用は絶対に枠を超えないこと
   > **答えB。** 購読の利用枠、API課金、追加機能は別々に確認します。実際のアカウントと使用量画面が手掛かりです。インストールの成否（A）は費用と関係ありません。購読料でAPIキーの利用まで賄われるわけではありません（C）。依頼文を短くしても使用量は保証できず、長い作業ではツールの出力やバックグラウンド作業も枠を使います（D）。

5. **[応用・場面問題]** 二つのサブエージェントが編集します。有用な準備は？ <!-- quiz: q05 revision: 2 -->
   - A. 会話が別なら自然に隔離されるので、衝突は起きない
   - B. 同じファイル群を同時に直させ、最後に良い方を選ぶ
   - C. 担当ファイルかワークツリーを分け、統合する人を決める

   > **答えC。** 明示的な隔離がなければ、並行して作業する側はファイルを共有することがあります。会話が別でもディレクトリが別とは限らず（A）、同じファイルを同時に直せば上書きし合います（B）。委譲によって元の作業の権限が広がることもありません（D）。範囲、権限、統合の調整が必要です。
