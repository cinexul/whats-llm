これまでの三つのプロジェクト（第31～33章）では、AIはほぼ「あなたが一言いえば一つやる」形で付き添ってきました。この章ではやり方を変えます。目標と一連の流れを渡し、AIに何ステップも続けて自分で進めさせ、あなたは横で「調査→計画→実行→検収」の進み具合を見守り、要所でだけ手を出します。終わったときには三つのものが手元に残ります。「必停リスト」一枚、AIが書いてあなたが照合した要約ファイル`summary.md`、そしてファイルを書く前にAIが本当に止まって確認してきたことを、自分の目で確かめた経験です。

第19章の「手を動かすAI」が、初めて本当にあなたの手に渡ります。手を動かすからこそ、この章ではまずブレーキを練習します。ブレーキは二層です。一層目はツールの**権限設定**（読み取り専用、変更前に確認する、など）で、これが実際に操作を止めます。二層目はあなたがプロンプトに書くルールで、どこで止まって確認すべきかをエージェントに伝えますが、実際にやってしまうのを止めることはできません。

## 一、準備

- 複数ステップだが、どのステップも危なくない小さな目標を選ぶ。初回はこれにしましょう。フォルダにある三つの文書をそれぞれ一文で要約し、一つの一覧にまとめる。ファイルを並べる、一つずつ読む、一つずつ要約する、まとめる、と何ステップもありますが、何も消さず、何も送らず、お金も使いません。初回から「メールボックスを片づけて」「顧客に自動返信して」と頼むのは、初心者ドライバーをいきなり高速道路に乗せるようなものです。
- どんなステップに分けるかを考えておく。自分でも説明できない流れは、AIに走らせることはできません（第14章）。
- やり直せる環境を用意する。文書のコピーだけを入れた専用の練習用フォルダを作り、Gitで管理します（第26章）。プラットフォーム付属のエージェントを使う場合は、どんな隔離環境が用意されているかを確かめます。
- 「必停リスト」を作る。どのステップはあなたの承認なしにやらせないかを書き出します。作り方はステップ2で説明します。

## 二、一歩ずつやる

### ステップ0：最小限の動かし方――プログラミングエージェントで、まず権限を絞る

別のプラットフォームを用意する必要はありません。プログラミングエージェント自体が複数ステップを続けて走らせられ、あなたが対話する画面が、AIの作業を見守り、いつでも止められる場所になります。初回は次のとおりに進めます。

1. 練習用フォルダを作る。たとえば`agent-practice`に、短い文書三つのコピー（一、二ページずつ。原本は入れない）を置き、第26章に沿ってGitを初期化して一度コミットし、出発点にします。
2. このフォルダでプログラミングエージェントを起動し（第28、29章）、まず「いまどのフォルダにいる？」と聞いて、場所を間違えていないか確かめます。
3. 権限を「変更する前に確認して」に合わせる。2026年10月時点では、Claude Codeはv2.1.283以降、ターミナルとVS Codeで自動モード（auto）で起動します。別のモデルが操作を審査し、ふつうは確認を出さないので、先に切り替えます。`claude --permission-mode manual`で起動するか、起動後に`Shift+Tab`を押してステータスバーに「manual mode on」と出るまで切り替えます。手動モードでは、ファイルを読むのは確認なしですが、ファイルの変更、ほとんどのコマンドの実行、ネットへの接続の前には必ず確認してきます。Codexは、Gitで管理されたフォルダではファイルを直接変更できるAutoが標準なので、`/permissions`でRead Onlyに切り替えます。現在のフォルダのファイルは読めますが、ファイルの変更やネット接続にはあなたの承認が要ります。こうした名前や入口はバージョンによって変わります。
4. 送信や削除のできるツールはつながない。今回はメール、チャット、クラウドストレージ、カレンダーのような外部ツールは使いません。会話の中で`/mcp`と入力し、いま何がつながっているかを見ます（MCPは第22、36章）。メッセージを送ったり、ものを消したり、お金を使ったりできるものは、いったん無効にするか、それらがつながっていない環境に替えます。

こうして走らせれば、何かを変えようとするたびにAIはまずあなたに確認してきます。出てきた確認で「拒否」を選べば済みます。

### ステップ1：普通の言葉で、目標 + 一連の流れを与える

目標だけ渡して放っておかず、「どんな手順で進めるか」もはっきり伝えます。

```text
目標：このフォルダにある三つの文書をそれぞれ一文で要約し、一覧にまとめる。

次の流れで進めて：
① まず調査：フォルダにどんな文書があるか並べて。そこで止まって、私に見せて。
② 私が「続けて」と言ってから、一つずつ読み、一つずつ一文の要約を書いて。
③ まとめた一覧は会話の中に直接書いて。まだファイルには保存しないで。

ルール：
- 既存のファイルを削除したり変更したりしないこと。何も外部に送らないこと。
- 迷うところは私の代わりに推測せず、止まって聞くこと。
```

この文章の半分は「何をしてはいけないか」と「どこで止まるか」です。これがブレーキの二層目です。本当にAIを止められるのは、ステップ0の権限設定です。

### ステップ2：まず「必停リスト」を作る――この章の核心

開始を押す前に、次のような動作を「必ず人が確認する」と決めておきます。判断の基準は一つだけです。このステップは取り消せるか。結果を伴うか。

| AIに任せてよいこと | 必ず止まってあなたの承認を待つこと |
| --- | --- |
| ファイルを読む、整理する、分類する、下書きを作る、一覧を作る | お金を使う：従量課金のサービスを呼ぶ、注文する、クレジットを消費する |
| どうでもよい小さな選択肢から一つ選ぶ | データを消す・上書きする：削除、全消去、元のファイルの書き換え |
| 一ステップ終えたら報告して、次へ進む | 外部に送る：メール送信、提出、公開、外部APIの呼び出し |
| 内容をある形式から別の形式に変える | AIが迷っていて、あなたが決めるべき判断 |

このリストは二層で実行します。一層目はツールに任せます。右側の動作は権限設定で止め、送信、削除、支払いのできるツールは初回はそもそもつなぎません。二層目がプロンプトのルールです。第26章で扱ったとおり、確認が出なかったからといって操作が無害とは限りません。付録Cも、Markdownファイルやプロンプトの一文はシステムレベルの強制的な制限の代わりにならないと注意しています。リストも権限も、AIが動き出す前に決めておきます。事故が起きてから足すのでは遅すぎます。

### ステップ3：走らせる。あなたは「調査→計画→実行→検収」の過程を見張る

開始を押したら、その場を離れないでください。初回は一ステップずつ見届けます。

- 「調査」が正しいか：正しいファイルを見つけたか。目標を正しく理解したか。最初の一歩がずれると、そのあとは間違った前提の上でどんどん整ったものを作っていきます（第14章）。
- 文書を並べたあと、止まってあなたの「続けて」を待ったか。
- 必停点で本当に止められたか：手動モードやRead Onlyでは、ファイルを変えたり、何かを変えるコマンドを実行したりしようとすると、ツールが先に確認を出します。確認なしに何かが変わっていたら、権限が緩すぎたか、つなぐべきでないツールがつながっていたということで、プロンプトの書き方の問題ではありません。すぐに止め、第30章に沿って状況を確かめて元に戻し、権限を絞ってから走らせ直します。
- 道を外れたと思ったら、いつでも割り込んで説明し直してから続けさせるか、きれいな状態に戻してやり直します。

### ステップ4：検収し、書き込みを一回だけ許可する

一通り終わったら、第25章の「最終チェックの三つの問い」で検収します。

1. AIは実際に何をしたか。最終的な一覧だけでなく、途中で何に触れたかも見ます。`git status`（フォルダでどんな変更があったかを表示する、読み取りだけのGitコマンド）を実行させて見せてもらえば、何も変わっていないはずです。
2. 止まるべきところで止まったか。文書を並べたあと「続けて」を待ったか。途中であなたが許可していない書き込み、削除、送信はなかったか。これは結果のできばえより大事です。
3. 結果を信じてよいか。要約を二つ選んで原文と照らし合わせます。AIの自己チェックはうのみにできません（第14章）。

問題がなければ、一覧を保存させます。

> 話し言葉のリクエスト：*「一覧は確認した。このフォルダに新しいファイル`summary.md`として保存して。ほかのファイルは一つも触らないで。」*

このときAIは、このファイルを作ってよいかを先に確認してきます。ファイル名と内容を確かめてから許可しましょう。保存できたら、もう一度`git status`を見ます。追跡されていない（Untracked）`summary.md`が一つ増えているだけで、既存のファイルは何も変わっていないはずです。このステップで、ブレーキがどう働くかを自分の目で確かめられます。AIは止まって何をしたいかを説明し、通すかどうかはあなたが決めます。

### 完了の基準

次がすべてそろえば、このプロジェクトは完了です。

- コピーだけを入れた練習用フォルダで、手動モードかRead Onlyで走らせ、送信や削除のできるツールはつながなかった。
- AIはまず三つの文書を並べ、止まってあなたの「続けて」を待った。
- 少なくとも二つの要約を抜き取りで確認し、原文と合っていた。
- `summary.md`を作る前にAIが確認してきて、あなたが許可したあと、`git status`に増えていたのはこのファイル一つだけだった。
- 最初から最後まで、あなたが許可していない書き込み、削除、送信はなかった。

## 三、よくあるつまずき

| つまずき | 何が起きるか / どう避けるか |
| --- | --- |
| いきなり取り返しのつかない大仕事を任せる | メールを消す、メッセージを送る、お金を動かす。事故が起きれば本物の事故です。送らない、消さない、最後に新しいファイルを一つ書くだけの目標で練習しましょう |
| プロンプトだけをブレーキにする | プロンプトに「消す前に聞いて」と書いても、消せる・送れる権限とツールを渡していれば、そのままやってしまうことがあります。まず権限を絞り、危ないツールをつながない。プロンプトは二層目です |
| 標準設定なら確認してくれると思い込む | 新しいClaude Codeの標準は自動モードで、CodexもGitで管理されたフォルダではそのままファイルを変更できます。初回の前に、ステータスバーや`/permissions`でモードを確かめましょう |
| 開始を押したら席を外す | 初回は最初から最後まで見張り、とくに必停点で止められたかを見ます（第19章） |
| 「確認しました」という言葉を本当の確認だと思う | AIの自己チェックも「続きを書いている」だけです。大事な情報は自分で確かめます（第14章） |
| 道を外れたのに、乱れた中で無理に直す | きれいな状態に戻して新しい会話を始め、さっきつまずいた点を前提として伝え直します（第13、30章） |
| ステップが多いほど強いと思う | 十数ステップを一気に走らせると、一つずつ見届けられません。歩幅を小さく、確認点を細かくしたほうが安定します |

## 四、もう一歩進める

一歩進むたびに、「ブレーキは足りているか」を改めて問いましょう。

- ツールやデータソースを一つ二つつなぐ（MCP、第22、36章）。新しい能力を一つつなぐたびに、間違いと攻撃の入口が一つ増えます。必要なものだけを、まず読み取りの権限だけでつなぎます。
- よく走らせる流れをスキルにする（Skills、第22、36章）と、次からは一言で呼び出せます。
- 権限は少しずつ、控えめに緩める。あるステップの安全性に完全に確信があり、しかも取り消せるときだけ、確認なしでやらせます。お金を使う、データを消す、外部に送るの三つは、ずっと必停リストに残しておくことを勧めます。
- 「どう仕事をすべきか」の説明を書く。ルール、触ってよいもの・いけないものをプロジェクトの説明ファイルに書きます（第28章）。モデル自体は前の会話を覚えていません。製品が作業を始めるたびにこのファイルを文脈に入れ直すから、AIはこれらのルールを「覚えている」のです。

```text
6. 想像上の将来の要件のために、抽象化の層、引数を渡すだけのラッパー、デザインパターンを足さない。まず今の要件を満たすいちばん簡単な作りにする。
7. 外部からの入力やAPIの応答は、システムの境界で検証する。フロントエンドの検証をバックエンドの検証の代わりにしない。エラーは処理するか報告し、黙って握りつぶさない。
8. まず動いて確かめられる最小の版を作り、それから少しずつ仕上げる。一時的な確認用のコードと正式な実装は分ける。
9. 一区切りできるたびに、上のような問題が入り込んでいないか確かめ、型チェックとテストを実行する。

```

## まとめ

- このプロジェクトで、自分で複数ステップを続けて走るエージェント（第19章）を初めて扱う。練習するのは「勢いよく走らせる」ことではなく「止められる」こと。
- 最小限の動かし方：練習用フォルダにはコピーだけを入れ、Gitで始める。権限は手動モードかRead Only（新しいClaude Codeは標準が自動モードなので、先に切り替える）。送信や削除のできるツールはつながない。
- ブレーキは二層。ツールの権限設定が一層目、プロンプトのルールが二層目。確認なしに何かが変わったら権限が緩すぎるので、絞ってから走らせ直す。
- 走っている間は「調査→計画→実行→検収」を見張る。検収では、何をしたか、止まるべきところで止まったか、結果を信じてよいかを見て、最後に書き込みを一回だけ自分で許可し、`git status`で増えたのが`summary.md`だけだと確かめる。
- お金を使う、データを消す、外部に送るの三つは、ずっと人の確認が必要な設定にしておくことを勧める（第14、19、26章）。

次章では、別の形でAIをつなぎます。出来合いの画面ではなく、あなた自身のプログラムからAPIでモデルを直接呼び出します。

## 出典とバージョンについて

確認日：2026-10-29。

- [Claude Codeの権限モード](https://code.claude.com/docs/en/permission-modes)：v2.1.283以降、ターミナルとVS Codeのセッションはautoモードで始まること。手動モード（設定値は`default`、コマンドラインでは`manual`も可）はファイルの変更、シェルコマンドの実行、ネット接続の前に確認すること。`Shift+Tab`で切り替えられ、起動時に`--permission-mode`で指定できること。
- [Codexの承認とセキュリティ](https://learn.chatgpt.com/docs/agent-approvals-security)：Gitで管理されたフォルダではAuto（作業ディレクトリ内でファイル変更やコマンド実行をそのまま行う）が勧められること、読み取りだけにしたいときは`/permissions`で切り替えること。
- [Codexの権限プリセットのソース](https://github.com/openai/codex/blob/main/codex-rs/utils/approval-presets/src/lib.rs)：Read Onlyは現在のワークスペースのファイルを読め、ファイルの変更やネット接続には承認が要ること。
- [Claude Codeのコマンド](https://code.claude.com/docs/en/commands)：`/mcp`、`/permissions`などセッション内のコマンド。

## 小テスト

> 全6問。概念・誤解・場面・操作の4種類をカバーしています。答えと解説は各問の下の引用ブロックにあります――まず自分で考えてから、照らし合わせてください。

1. **[基礎・概念問題]** エージェントに複数ステップの作業を任せることと、前のいくつかのプロジェクトの「一つ聞けば一つ答える」との、最も根本的な違いは？ <!-- quiz: q01 revision: 3 -->
   - A. 裏側のモデルが強いので、もっと難しい問題を扱える
   - B. 自分で何ステップも続けて走り、人は要所で見張る
   - C. 画面の機能が充実していて、多くの情報を同時に見られる
   - D. 自分で結果を確認するので、ほとんど間違えなくなる
   > **答えB。** Agentの急所は「自分で一区切り先まで進む」ことであって（第19章）、より賢いとか、より間違えないとかではありません。自分で走り、しかも止まってあなたに聞かないこともありうるからこそ、この章は「ブレーキを付ける」ことを最優先にしています。AとCのモデルや画面は違いの本質ではありません。Dは逆で、AIの自己点検は全面的には信用できません（第14章）。

2. **[基礎・概念問題]** この章が繰り返し強調する「ブレーキ」（必停リスト）は、本質的に何か？ <!-- quiz: q02 revision: 3 -->
   - A. プロンプトに「削除禁止、送信禁止」と書けば、そのとおりにする
   - B. Agentの一歩一歩を遅くし、人が反応する時間を増やすこと
   - C. 削除・送信・支払いなどを、前もって人の確認が必要にする
   - D. 問題が起きたときに、Agentを強制終了するための停止ボタン
   > **答えC。** ブレーキはAIを遅くすることではなく、**安全な範囲を囲う**ことです。範囲内は思い切り走らせ、取り返しのつかない、結果を伴う動作に当たったら、必ず止まってあなたの承認を待たせます。実際には、まずツールの権限設定（手動モードや読み取り専用、送信や削除のできるツールをつながない）で確実にし、プロンプトのルールは二層目です。Aは二層目だけに頼っていて、それでもやってしまうことがあります。BとDは「どのステップがあなたを通るべきか」に答えていません。

3. **[基礎・誤解問題]** 「目標をはっきり伝えて開始を押したから、あとは別のことをしていい」――初めてAgentを作るとき、この考えのどこが間違いか？ <!-- quiz: q03 revision: 2 -->
   - A. 初回は最後まで見張り、必停点で止められたかを見る
   - B. 目標が大ざっぱすぎた。細かく書けば安心して離れられる
   - C. 問題ない。プロンプトに「まず私に聞いて」と書いてある
   - D. 最高の権限にしていないので、途中で確認待ちで止まる
   > **答えA。** Agentが自分で走るのはそのとおりですが、必停点に来たときに止められたか、先にあなたに聞いてきたかは、自分の目で確かめてはじめて安心できます。聞かずに取り返しのつかないことをしたなら、権限がゆるすぎたということで、すぐに中断します。BとCは、はっきり伝えればプロンプトに書けば手を離せると考えています。Dはちょうど逆で、初回こそいちばん厳しい権限を使うべきで、確認を求めて止まることはむしろ望ましいことです。

4. **[応用・場面問題]** Agentに顧客資料のフォルダを整理させます。次のどのステップを、**最も**「必ず止まってあなたに聞く」に設定すべきか？ <!-- quiz: q04 revision: 2 -->
   - A. 資料を表から一段落の文章の説明にまとめ直す
   - B. 顧客資料を会社名の順にもう一度並べ替える
   - C. いくつかの表を、同じ一つの形式にそろえる
   - D. 重複だと判断した顧客記録を、そのまま削除する
   > **答えD。** 削除は**取り返しがつかず**、重大な結果を伴う動作で、まさに必停点です。A、B、Cはいずれも、範囲内で任せてよい低リスクの整理です（結果は別に保存し、原本は動かさないことが前提）。見分ける基準はいつも同じで、このステップは元に戻せるか、結果を伴うか、です（第14章に呼応）。

5. **[応用・場面問題]** Agentが途中で明らかにずれてきて、やるほど乱れていく。最善の損切りは？ <!-- quiz: q05 revision: 2 -->
   - A. いまの会話の中で、一言ずつ追いかけて直させる
   - B. まずこの一回を最後までやらせ、あとでまとめて直す
   - C. 中断して元に戻し、新しい会話で前提を伝え直す
   - D. 権限を少し広げ、AI自身に混乱を片づけさせる
   > **答えC。** 汚れた文脈の中で無理に直そうとすると、たいてい直すほどずれていきます（第13・30章）。だからこそ準備の段階で「巻き戻せる環境」を用意しておくのです――まさにこの瞬間に、すっきりやり直すために。Aはまさに無理に直すやり方です。Bは間違った方向にさらに走らせることになります。Dは、すでに間違えているAIが与えうる影響をかえって広げます。

6. **[基礎・操作/観察問題]** この章のステップ0～4で、実際に一回走らせてみましょう：練習用フォルダでプログラミングエージェントを起動し、権限を手動モードかRead Onlyにして、三つの文書をそれぞれ一言で要約してまとめさせ、あなたが照合したあとで`summary.md`への保存を許可します。走らせる前に、作業を「調査→計画→実行→検収」のステップに分け、「必停リスト」を作っておきます。終わったら「完了の基準」と一つずつ照らし合わせます。 <!-- quiz: q06 revision: 3 -->
   > **観察できるはず：** この練習の目標には、必停点が一つしかないと気づくでしょう。最後に`summary.md`を作る書き込みです。手動モードやRead Onlyでは、AIはそこで止まって確認してきて、許可すると`git status`に増えるのはこのファイル一つだけです。送らない、消さない、唯一の書き込みは目に見えて取り消せる。これこそ初回に選ぶべき目標です。目標に「消す、送る、お金を使う」が現れたとたん、対応するステップは「必停リスト」に入れ、しかもプロンプトに書くだけでなく、先に権限設定で押さえなければなりません。**まずブレーキを考え抜き、それから走らせる話をする**――これがAgentを作る正しい順番です（第14・19・26章に呼応）。
