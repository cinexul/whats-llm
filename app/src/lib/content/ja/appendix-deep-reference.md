この付録は Claude Code と Codex の実用リファレンスです。第28・29章では最初の作業を試しました。ここでは次に使う機能を選び、問題を切り分けます。例は **2026-10-22** に確認しています。違いがあれば、インストール済みバージョンのヘルプで照合してください。

## 一、実行ファイルとアカウントを確認する

ターミナルで、インストールしたツールのコマンドを実行します。

```bash
claude --version
claude --help
```

```bash
codex --version
codex --help
```

どちらも対話型のセッション内では `/status` で状態を確認し、`/` でコマンドを探せます。シェルとセッション内のコマンドは別です。Bash に `/status` と入力しても、エージェントの状態は表示されません。

問題を報告するときは、バージョン、OS、実行場所、有効なアカウントを記録します。購読ログイン、API 認証情報、組織設定によって、意図しない請求先が選ばれていないか確認してください。診断メモに実際のキーは入れません。

## 二、問題に合う操作を選ぶ

| 目的 | Claude Code の入口 | Codex の入口 | 確認点 |
| --- | --- | --- | --- |
| セッション確認 | `/status` | `/status` | アカウント、設定、実行コンテキスト |
| コマンド探索 | `/help` または `/` | `/` と `codex --help` | そのバージョンで提供されるもの |
| 権限確認 | `/permissions` | `/permissions` | 許可範囲と制限 |
| プロジェクト指示の下書き | `/init` の後に `CLAUDE.md` を確認 | `/init` の後に `AGENTS.md` を確認 | パス、コマンド、規則の正確さ |
| 変更確認 | `/diff` または `git diff` | `/diff` または `git diff` | 追跡済みの変更と想定外のファイル |
| 保存された知識の確認 | 提供されていれば `/memory` | 提供されるメモリ設定とプロジェクトファイル | 古いノートや矛盾 |
| 長い会話の整理 | 提供される圧縮・新規セッション機能 | `/compact` または新しいセッション | 要件と証拠が要約に残っているか |

これは入口を探すための表で、同じ画面を保証するものではありません。エディターや管理されたクラウド環境では、別の操作になっている場合があります。

## 三、プロジェクト指示、メモリ、スキル、設定

**プロジェクト指示**には安定した作業規約、**メモリ**には保持した観察、**スキル**には再利用する手順を置きます。設定は有効なツール、接続情報、モデル選択、権限など、アプリ自体を制御します。Markdown の文章は OS の制限を強制するものではありません。

良い指示ファイルは、確認できる長さで、実行できる具体性があります。

```markdown
- 最初に README と既存の実装を読む。
- 文書で指定されたロックファイルとパッケージ管理を使う。
- 完了前に、変更した動作に関係する確認を実行する。
- 実行したコマンド、結果、未確認の仮定を報告する。
```

必要なら確認済みのリポジトリ情報で具体化します。個人の好みや秘密情報を共有の規則に混ぜないでください。下位ディレクトリにも指示ファイルがある場合、編集対象にどれが適用されるかを確認します。すべてが全体に適用されるとは限りません。

## 四、計画と推論設定

目標が曖昧、変更が複数システムにまたがる、間違った仮定の影響が大きい、といった場合に計画が役立ちます。関連ファイル、変更案、検証方法を求め、具体的な次の操作につなげます。

推論の強さやモデル選択は、応答時間、使用量、結果に影響します。高い設定は難問で役立つ場合がありますが、足りない証拠を補ったり、誤った要件を直したりはしません。小さな文章修正で長い計画会議をすると、修正自体より手間がかかります。

## 五、サンドボックスと承認を分ける

サンドボックスはファイル、プロセス、ネットワークへのアクセスを制限します。承認規則は、操作を自動許可するか、確認するか、拒否するかを決めます。組織のポリシーがさらに両者を制約する場合もあります。

例外を許可する前に、具体的なコマンド、対象、副作用を確認します。依存関係が足りないなら環境の準備を調べ、すべての制限を無効にするのは避けます。依頼された作業に必要な範囲の権限を選びましょう。「自動」モードが、あらゆる操作の妥当性を保証するわけではありません。

## 六、サブエージェントとオーケストレーション

独立した調査、別コンポーネント、範囲を限定したレビューなど、明確に引き継げる作業を分担します。たとえば次のように依頼できます。

```text
プレビューが失敗する原因を調べてください。アプリのファイルを読み、
既存の確認コマンドを実行できます。編集はしないでください。
失敗したコマンド、証拠、最小限と思われる修正案を返してください。
```

並行編集ではファイル担当を分けるか、worktree を隔離します。会話が別でもファイルシステムは自動では分離されません。調整するエージェントは変更を統合し、全体の結果を検証し、元の範囲を守ります。作業者を増やすと使用量や調整コストも増え得ます。複数のエージェントの一致は、独立した証拠とは限りません。

## 七、フックと無人実行

フックはライフサイクルのイベントに応じて設定済みの処理を実行します。無人実行では、操作ごとに人が回答せずにタスクを進めます。繰り返す確認や自動化に役立つ一方、スクリプト実行、サービス接続、ファイル変更も行えます。

有効にする前に実際のコマンドを読み、作業ディレクトリ、認証情報、タイムアウト、期待する出力を設定します。ログに秘密情報を残さないようにします。失敗時の対応と、再実行で外部操作を重複させない方法も決めます。フックは単なる指示文ではなく、実行される処理です。

## 八、スキル、プラグイン、MCP

内容を確認できるスキルから始めます。`SKILL.md`、明確な説明、短い手順、必要な補助ファイルをそろえ、架空のデータで検証します。保存先や任意のメタデータはクライアントごとに違います。

MCP では提供元、ローカルのコマンドかリモートの URL、アカウント範囲、公開された機能を確認します。書き込みを追加する前に、内容を知っている対象への読み取りを試します。プラグインは複数のスキルやサーバーをまとめる場合があるため、実際に有効な内容を調べます。プラグインや MCP 接続そのものは、送信や公開の許可ではありません。

## 九、コンテキスト、圧縮、引き継ぎ

役立つ引き継ぎには、目標、現状、変更ファイル、コマンドと結果、未解決の問題、証拠の参照先を含めます。会話全体をそのまま複製する必要はありません。

圧縮は重要な状態を保ちながらコンテキストを短くできますが、細部が抜けることがあります。正確な文言が必要なら元ファイルやログを開き直します。新しいセッションは焦点を絞る助けになりますが、資料の再読やキャッシュ再利用の喪失もあり得ます。常に安くなると考えず、タスクを整理するために選びます。

## 十、失敗している層を調べる

| 症状 | 最初に役立つ確認 |
| --- | --- |
| コマンドが見つからない | インストール結果、実行ファイルの位置、シェルの再起動、`PATH` |
| ログイン・アクセス失敗 | 有効なアカウント、認証情報の出所、組織ポリシー、サービス状態 |
| 利用枠・レート制限 | 使用量画面、リセット時刻、モデルやモード、並行リクエスト |
| クラウドで依存関係が不足 | 環境の準備、パッケージ管理、ロックファイル、システム依存関係 |
| 権限エラー | 正確なパスや操作と、有効なサンドボックス・承認規則 |
| MCP ツールがない・失敗する | サーバー接続、認証、提供機能、サーバーログ |
| 想定外の編集 | Git diff、指示の適用範囲、共有ディレクトリ、タスクの範囲 |
| 成功報告なのに動かない | 実際に再現し、コマンドの結果を確認する |

疑わしい原因を一つずつ変え、元のエラーを残します。原因を特定せずに再起動、権限拡大、プラン変更を繰り返すと、診断しにくくなります。

## 十一、レビューと統合

`git status --short` でファイル全体の状態を確認します。未ステージの変更には `git diff --stat` と `git diff`、次のコミット用にステージ済みの変更には `git diff --cached --stat` と `git diff --cached` を使います。未追跡ファイルは別途読みます。これらの diff コマンドはその内容を表示しません。関係する動作を検証し、実行できなかった確認を記録したうえで、依頼の許可範囲とリポジトリの手順に従ってコミット、PR、push、デプロイを行います。

レビューでは具体的な問題、変更後の動作、検証の証拠を説明します。エージェントによるレビューは有用な分析の一つですが、テストや、手順で求められる人の判断の代わりにはなりません。
