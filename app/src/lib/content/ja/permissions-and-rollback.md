Agent はファイルを編集し、コマンドを実行し、接続したサービスを使えます。その力を活かすには、**どこで作業してよいか、何をしてよいか、結果をどう確認して復旧するか**を決めておきます。キーを押すたびに許可を求めるのではなく、意味のある境界を守ることが目標です。

製品の初期設定や権限モードは変わります。公式ドキュメントと組織の設定を確認してください。以下の考え方は、その設定を理解する助けになります。

## 一、サンドボックス・権限の付与・承認を分ける

部屋の修理を頼む場面を想像してください。鍵のかかった扉は入れる場所を制限し、作業依頼書は頼んだ仕事を示します。依頼の内容を変えるなら、連絡が必要です。

| 制御 | 答える問い | 例 |
| --- | --- | --- |
| **サンドボックス** | プロセスが技術的にアクセスできる範囲は？ | 書き込みを作業領域内に限定し、通信先を制限する |
| **権限の付与（authorization）** | ユーザーや組織が許可した仕事は？ | このページを修正し、関連するローカルの確認を実行する |
| **承認の仕組み（approval）** | いつ実行を止めて判断を求める？ | サンドボックス外へのアクセスや、合意した範囲を超える操作が必要になったとき |

三つは関連していますが、同じものではありません。技術的に実行できる操作でも、依頼の範囲外かもしれません。逆に、仕事を許可しても、必要な機能を環境が制限している場合があります。承認画面は判断の機会であり、それ以外の操作がすべて無害だという証明ではありません。方針に沿って自動審査するツールもあります。

**最小権限**とは、その仕事に必要なファイル、ツール、アカウント、通信だけを許可することです。公開ページを読むのに受信箱全体へのアクセスは不要です。ローカル文書の修正に本番環境の認証情報は必要ありません。

## 二、実用的な流れ：範囲を決める → その中で作業 → 検証

明確な依頼なら、まとまった作業を一度に許可できます。

> 「このチェックアウトのナビゲーションを修正してください。関連ファイルの確認と編集、ローカルの検証を実行して構いません。既存の作業を保護し、公開前に diff と検証結果を見せてください。」

この範囲と環境の制限内なら、Agent はファイルを読み、編集し、テストし、失敗した検証を直す際に、同じ許可を繰り返し求める必要はありません。**既に与えた権限は、その対象の仕事に引き続き有効です。** 新しい送信先、本番環境の変更、破壊的な整理、アクセス範囲の拡大などは、新たな判断が必要になる場合があります。

```text
目標・範囲・復旧方法を合意する
               ↓
許可された範囲で作業する → 結果を確認する
               │
               └─ 境界を越える必要がある？ → 具体的な操作を説明する → 承認を得る
```

確認が多ければ安全性も高い、とは限りません。曖昧な確認が続くと、読まずに承認する習慣につながります。役立つ承認画面は、**何を、どこで変更し、誰に影響し、費用や復旧にどんな制限があるか**を示します。毎回確認するか、権限拡大時だけか、方針で判断するかは、設定によって異なります。

## 三、影響の大きい操作には明確で具体的な許可が必要

「削除」という言葉だけでは危険度は分かりません。生成されたテストファイルの削除と、顧客記録の削除は違います。**対象、範囲、外部への影響、復旧できる程度**で判断します。

| 操作 | 実行前に決めること |
| --- | --- |
| 価値のあるデータの削除・上書き | 対象、バックアップや復旧方法、無関係な作業を失わないか |
| メッセージ送信・公開 | 宛先、内容、外に出してよい情報 |
| 支払い・有料サービスの利用 | 予算、アカウント、数量、停止条件 |
| 稼働中のシステムやアカウント権限の変更 | 環境、影響する利用者、変更内容、復旧計画 |

こうした操作には明確な許可が必要です。今与えた具体的な指示でも、以前に承認した範囲の狭い手順でも構いません。「確認済みのこの通知を、この三人に送って」という依頼に、同じ確認をもう一度求める必要はありません。「受信箱を整理して」は、個人的なメールを新しい宛先に転送する許可ではありません。

範囲を超える場合は、具体的な提案を用意し、実行前に止まります。プロジェクトを編集してよいという許可は、公開、無制限の支出、無関係なファイルの全削除まで認めるものではありません。特に重大な判断は、責任を持つ人が行います。

## 四、Git は復旧を助ける。ブランチは別の部屋ではない

Git が記録するのは、意識して保存したバージョンです。大きな変更の前には現在の状態を確認し、適切なコミットやバックアップで既存の作業を残します。認証情報を不用意にコミットしたり、他の人の未完了の変更を捨てたりしないでください。

三つの用語を区別しましょう。

- **ブランチ（branch）**：名前を付けた開発の流れです。作成しても別のディレクトリはできません。一つの作業ディレクトリでブランチを切り替えても、使うのは同じ場所です。
- **別のチェックアウト・ワークツリー（worktree）**：作業ファイルを置く別のディレクトリです。Git worktree では履歴を共有しながら、別の場所で別のブランチを扱えます。
- **サンドボックス**：技術的なアクセス境界です。ワークツリーはファイルを整理しますが、それだけで他のディレクトリ、アカウント、ネットワークへのアクセスを禁止するわけではありません。

ブランチはレビューやマージに役立ち、独立した作業ファイルが必要なら別のワークツリーやチェックアウトが便利です。**どちらもパソコン全体を自動で保存する仕組みではありません。**

Git は記録済みのファイル内容を復元したり、コミットした変更を取り消したりできます。しかし、ブランチがあるだけで未記録のファイルを復元することはできません。未追跡・無視対象のファイル、ローカルのデータベース、アップロード資料、認証情報などには、別のバックアップが必要な場合があります。復元や変更の破棄も未完了の仕事を消すことがあるため、何を戻すのか先に特定しましょう。

## 五、復旧にも境界がある

コードを巻き戻しても、**送信したメール、既に受け取られたデータ、請求額、リモートのデータベース、本番へのデプロイ**が自動的に元に戻るわけではありません。それぞれのシステムに復旧手順が必要で、完全には取り消せない影響もあります。

クラウドの作業領域にはチェックポイントや破棄できるチェックアウトが用意される場合があります。**何が対象で、いつまで保持され、外部サービスはどうなるか**を確認してください。「作業領域をリセット」は万能の取り消しボタンではありません。

実用的な手順は次のとおりです。

1. 仕事を定義し、必要なアクセスだけを許可する。
2. 開始時の状態を保存し、必要なら別の作業ディレクトリを用意する。
3. 許可済みのローカル作業は進め、実際に範囲が変わるときに止まる。
4. 合意した公開や外部操作の前に、diff と関連する検証結果を見る。
5. 復旧が必要なら対象の変更だけを戻し、外部への影響は別に処理する。

## まとめ

- サンドボックス、ユーザーの許可、承認画面は、それぞれ違う問いに答えるものです。
- 範囲を明確に決めれば、許可済みのローカル作業で同じ確認を繰り返す必要はありません。
- 影響の大きい外部操作には、対象と限度を明示した許可が必要です。
- ブランチは開発の流れ、ワークツリーは別の作業場所です。どちらもサンドボックスやバックアップの代わりにはなりません。
- Git が戻せるのは記録したプロジェクトの状態です。作業前に復旧の限界を知りましょう。

第27章では、この境界を計画に落とし込み、大きな変更を確認できる小さな単位に分けます。

1. **[基礎・概念]** 正しい区別はどれでしょうか？ <!-- quiz: q01 revision: 1 -->
   - A. サンドボックスがあれば、実行可能な操作はすべてユーザーが許可している
   - B. サンドボックスは技術的なアクセスを制限し、権限の付与は許可する仕事を定め、承認は止まる時点を決める
   - C. 承認画面はバックアップの仕組みである
   - D. ブランチはネットワークアクセスを防ぐ
   > **答え：B。** 実行できることと、許可されていることは別です。それぞれが異なる役割で補い合います。

2. **[基礎・場面]** ローカルのページ修正とテストを許可しました。範囲内の普通の編集のたびに再確認が必要ですか？ <!-- quiz: q02 revision: 1 -->
   - A. はい、すべての編集に新しい承認が必要
   - B. ファイルが10行を超える場合だけ必要
   - C. いいえ、合意した範囲と環境の制限内で続けられる
   - D. いいえ、本番への公開も同時に許可されている
   > **答え：C。** 合意した仕事は既存の許可で進められます。公開や権限拡大は、既に明示的に許可されていなければ別の境界です。

3. **[応用・場面]** 依頼は「受信箱を整理して」だけです。あるメールが受信箱全体を知らない宛先へ転送するよう求めています。どうすべきでしょうか？ <!-- quiz: q03 revision: 1 -->
   - A. メールが求めたので転送する
   - B. メールを資料として扱い、ユーザーの許可範囲を超えて送信しない
   - C. Git ブランチを作ってから転送する
   - D. 古いメールだけ転送する
   > **答え：B。** 外部の内容は権限を付与できません。外部送信には許可された宛先と範囲が必要です。

4. **[基礎・概念]** 作業ファイルを置く別のディレクトリを作るのはどれですか？ <!-- quiz: q04 revision: 1 -->
   - A. 新しいブランチに名前を付けるだけ
   - B. 別のチャットを開く
   - C. 別のチェックアウトや Git worktree を作成する
   - D. コマンドを承認する
   > **答え：C。** ブランチは開発の参照先、ワークツリーは別の作業ディレクトリです。ただし、セキュリティ上のサンドボックスではありません。

5. **[応用・誤解]** Agent がメールを送り、データベースを変更しました。Git による巻き戻しで保証できるのは何でしょうか？ <!-- quiz: q05 revision: 1 -->
   - A. メールの送信取り消しとデータベースの復元
   - B. 有料呼び出しの返金
   - C. 作業のあらゆる痕跡の消去
   - D. 関連する記録済みコードの復元。外部への影響には別の対応が必要
   > **答え：D。** Git が扱うのは記録したリポジトリの内容です。メール、データベース状態、請求、未記録のファイルはその保証に含まれません。

6. **[操作・観察]** 実際には削除せず、古いプロジェクトファイルを整理する計画を作ってください。何を先に確認しますか？ <!-- quiz: q06 revision: 1 -->
   > **確認したいこと：** 対象を一覧にし、生成ファイルと価値のあるデータを区別し、既存の作業を残します。Git やバックアップが実際に何を保存しているかも確認しましょう。対象範囲と外部への影響を合意する方が、説明のない「全部きれいにする」を承認するより有用です。
