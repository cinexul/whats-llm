Agentはファイルを編集し、コマンドを実行し、接続したサービスを使えます。その力を活かすには、**どこで作業してよいか、何をしてよいか、結果をどう確認して復旧するか**を決めておきます。キーを押すたびに許可を求めるのではなく、意味のある境界を守ることが目標です。

製品の初期設定や権限モードは変わります。公式ドキュメントと組織の設定を確認してください。以下の考え方は、その設定を理解する助けになります。

## 一、サンドボックス・権限の付与・承認を分ける

部屋の修理を頼む場面を想像してください。鍵のかかった扉は入れる場所を制限し、作業依頼書は頼んだ仕事を示します。依頼の内容を変えるなら、連絡が必要です。

| 制御 | 答える問い | 例 |
| --- | --- | --- |
| **サンドボックス** | プロセスが技術的にアクセスできる範囲は？ | 書き込みを作業領域内に限定し、通信先を制限する |
| **権限の付与（authorization）** | ユーザーや組織が許可した仕事は？ | このページを修正し、関連するローカルの確認を実行する |
| **承認の仕組み（approval）** | いつ実行を止めて判断を求める？ | サンドボックス外へのアクセスや、合意した範囲を超える操作が必要になったとき |

三つは関連していますが、同じものではありません。技術的に実行できる操作でも、依頼の範囲外かもしれません。逆に、仕事を許可しても、必要な機能を環境が制限している場合があります。承認画面は判断の機会であり、それ以外の操作がすべて無害だという証明ではありません。方針に沿って自動審査するツールもあります。

**最小権限**とは、その仕事に必要なファイル、ツール、アカウント、通信だけを許可することです。公開ページを読むのに受信箱全体へのアクセスは不要です。ローカル文書の修正に本番環境の認証情報は必要ありません。

## 二、実用的な流れ：範囲を決める → その中で作業 → 検証

明確な依頼なら、まとまった作業を一度に許可できます。

> 「このチェックアウトのナビゲーションを修正してください。関連ファイルの確認と編集、ローカルの検証を実行して構いません。既存の作業を保護し、公開前にdiffと検証結果を見せてください。」

この範囲と環境の制限内なら、Agentはファイルを読み、編集し、テストし、失敗した検証を直す際に、同じ許可を繰り返し求める必要はありません。**既に与えた権限は、その対象の仕事に引き続き有効です。** 新しい送信先、本番環境の変更、破壊的な整理、アクセス範囲の拡大などは、新たな判断が必要になる場合があります。

```text
目標・範囲・復旧方法を合意する
               ↓
許可された範囲で作業する → 結果を確認する
               │
               └─ 境界を越える必要がある？ → 具体的な操作を説明する → 承認を得る
```

確認が多ければ安全性も高い、とは限りません。曖昧な確認が続くと、読まずに承認する習慣につながります。役立つ承認画面は、**何を、どこで変更し、誰に影響し、費用や復旧にどんな制限があるか**を示します。毎回確認するか、権限拡大時だけか、方針で判断するかは、設定によって異なります。

## 三、「承認をスキップする」スイッチは、初心者は入れない

多くのツールには、Agentへの確認を減らしたり、まったく確認しなくしたりするオプションがあります。2026年10月時点で、Claude Codeには`--dangerously-skip-permissions`（bypassPermissionsモードに相当）があり、Codexには`--dangerously-bypass-approvals-and-sandbox`（別名`--yolo`）と、`danger-full-access`というサンドボックス設定があります。どれも名前に「dangerous」（危険）が入っています。承認を止め、ものによってはサンドボックスまで外すからです。そうなると、Agentの判断ミスや、Webページやメールから読み込んだ悪意ある指示が、そのまま実際の操作になりかねません。

初心者はこうしたオプションを使わないでください。確認が煩わしいという理由で有効にするのもやめましょう。どうしても必要な場合、たとえば無人でテストをまとめて回すときでも、隔離したサンドボックスか使い捨ての環境に限ります。個人のファイルや大事なアカウント、認証情報が入っていない仮想マシンやコンテナです。Claude Codeの公式ドキュメントも、このモードはネットにつながらないコンテナや仮想マシンなどの隔離環境でだけ使うよう勧めています。Codexのドキュメントも、この全開放の組み合わせを高リスクで非推奨としています。

もう一つ、「自動モード」の類があります。別のモデルや事前の方針が操作を審査するので、確認画面はかなり減ります。煩わしさは減りますが、公式も安全を保証するものではないと明記しています。自動で通った操作が、どれも適切だとは限りません。削除、公開、支払いのような操作は、次の節のとおり明確に許可しましょう。どんなモードがあり、何と呼ばれているかは、使っているバージョンの公式ドキュメントで確認してください。

## 四、影響の大きい操作には明確で具体的な許可が必要

「削除」という言葉だけでは危険度は分かりません。生成されたテストファイルの削除と、顧客記録の削除は違います。**対象、範囲、外部への影響、復旧できる程度**で判断します。

| 操作 | 実行前に決めること |
| --- | --- |
| 価値のあるデータの削除・上書き | 対象、バックアップや復旧方法、無関係な作業を失わないか |
| メッセージ送信・公開 | 宛先、内容、外に出してよい情報 |
| 支払い・有料サービスの利用 | 予算、アカウント、数量、停止条件 |
| 稼働中のシステムやアカウント権限の変更 | 環境、影響する利用者、変更内容、復旧計画 |

こうした操作には明確な許可が必要です。今与えた具体的な指示でも、以前に承認した範囲の狭い手順でも構いません。「確認済みのこの通知を、この三人に送って」という依頼に、同じ確認をもう一度求める必要はありません。「受信箱を整理して」は、個人的なメールを新しい宛先に転送する許可ではありません。

範囲を超える場合は、具体的な提案を用意し、実行前に止まります。プロジェクトを編集してよいという許可は、公開、無制限の支出、無関係なファイルの全削除まで認めるものではありません。特に重大な判断は、責任を持つ人が行います。

## 五、Gitの最小限の始め方

これまでの章で何度も「開始時の状態を保存する」「問題が起きたら巻き戻す」と書いてきました。ローカルのプロジェクトでは、ふつう**Git**がその役を担います。ファイルのバージョンを記録する道具で、「コミット」（commit）するたびに、その時点のプロジェクトを後から戻れる版として保存します。最低限、次のことを押さえれば十分です。

**1. インストールして確認する。**

- Windows：Gitの公式サイトgit-scm.comから「Git for Windows」をダウンロードし、既定の設定のままインストールします。
- macOS：「ターミナル」で`xcode-select --install`を実行し、Appleのコマンドラインツール（Gitを含む）を入れます。Homebrewを使っているなら`brew install git`でも構いません。
- Linux：ディストリビューションのパッケージ管理ツールで入れます。

入れたら新しいターミナルを開き、`git --version`を実行します。バージョン番号が表示されれば完了です。手順は変わることがあるので、git-scm.comのインストールページで確認してください。

初めて使う前に、Gitに自分の名前を伝えます。パソコンごとに一度でよく、この二つは各コミットの記録に書き込まれます。

```bash
git config --global user.name "あなたの名前"
git config --global user.email "you@example.com"
```

**2. プロジェクトの出発点を保存する。** プロジェクトのフォルダに移動し、まず`git status`を実行します。「not a git repository」と表示されたら、まだGitで管理していないフォルダです。次を順に実行します。

```bash
git init
git add -A
git commit -m "作業前の出発点"
```

`git init`はこのフォルダをGitの管理下に置くもので、一度だけ実行します。`git add -A`はフォルダ内の追加・変更・削除をすべて「保存予定」のリストに入れます。`git commit -m "..."`はそのリストを一つの版として保存し、引用符の中に一言説明を書きます。コミット前に、パスワードや鍵のファイルが混ざっていないか見ておきましょう。記録したくないファイルは、プロジェクト内の`.gitignore`というテキストファイルに名前を書いておくと、Gitが対象外にします。以後は小さな一歩を終えて確認するたびに、`git add -A`と`git commit -m "やったこと"`で新しいセーブポイントを作ります（第27章）。

**3. 何が変わったかを見る。**

- `git status`：前回のコミット以降に変更されたファイルと、Gitがまだ記録していない新しいファイル（Untracked files）を一覧にします。
- `git diff`：まだコミットしていない変更を行単位で表示します。読み方は第25章を参照してください。

**4. 取り消す。**

- まだコミットしていないファイルを壊してしまった：まず`git diff ファイル名`で中身を確認し、`git restore ファイル名`を実行すると、最後のコミット（または`git add`）の時点の内容に戻ります。そのファイルの保存していない変更はそのまま捨てられ、取り戻せません。
- Agentが新しく作り、一度もコミットしていないファイルは、`git restore`の対象外です。`git status`では「Untracked files」に表示されるので、不要と確かめてから手で削除します。
- コミット済みの変更を一つ取り消したい：`git log --oneline`でそのコミットの番号を探し、`git revert 番号`を実行します。Gitはその変更を打ち消す「逆向き」のコミットを新しく作り、元の記録は残すので、比較的安全です。実行前に、手元の未コミットの変更はコミットするか片付けておきます。

ネット上の解説でよく見る`git reset --hard`は、未コミットの変更を一度にすべて捨てます。初心者は使わないでおきましょう。取り消しには何手順もかかることがよくあります。一つずつ進め、そのたびに`git status`で結果を確かめてください。

**5. 取り消しの限界。** Gitが扱うのは、このフォルダの中で記録したファイルだけです。Agentが送ったメール、消したクラウド上のデータ、公開した投稿、支払った料金は、Gitでは戻せません（第七節）。

**Agentに任せることもできます。** 自分でコマンドを打ちたくなければ、コーディングエージェントに「Gitでこのプロジェクトの出発点を保存して。各コマンドを実行する前に何をするか説明し、私が確認してから進めて」と頼みましょう。コマンドの実行を求められたら、上の説明と照らし合わせて理解してから承認します。

## 六、ブランチは別の部屋ではない

大きな変更の前には`git status`で現在の状態を確認し、コミットやバックアップで既存の作業を残します。認証情報を不用意にコミットしたり、他の人の未完了の変更を捨てたりしないでください。

三つの用語を区別しましょう。

- **ブランチ（branch）**：名前を付けた開発の流れです。`git switch -c practice/first-task`で新しいブランチを作って切り替えると、以後のコミットはその流れに記録されます。作成しても別のディレクトリはできません。一つの作業ディレクトリでブランチを切り替えても、使うのは同じ場所です。
- **別のチェックアウト・ワークツリー（worktree）**：作業ファイルを置く別のディレクトリです。Git worktreeでは履歴を共有しながら、別の場所で別のブランチを扱えます。
- **サンドボックス**：技術的なアクセス境界です。ワークツリーはファイルを整理しますが、それだけで他のディレクトリ、アカウント、ネットワークへのアクセスを禁止するわけではありません。

ブランチはレビューやマージに役立ち、独立した作業ファイルが必要なら別のワークツリーやチェックアウトが便利です。**どちらもパソコン全体を自動で保存する仕組みではありません。**

Gitは記録済みのファイル内容を復元したり、コミットした変更を取り消したりできます。しかし、ブランチがあるだけで未記録のファイルを復元することはできません。未追跡・無視対象のファイル、ローカルのデータベース、アップロード資料、認証情報などには、別のバックアップが必要な場合があります。復元や変更の破棄も未完了の仕事を消すことがあるため、何を戻すのか先に特定しましょう。

## 七、復旧にも境界がある

コードを巻き戻しても、**送信したメール、既に受け取られたデータ、請求額、リモートのデータベース、本番へのデプロイ**が自動的に元に戻るわけではありません。それぞれのシステムに復旧手順が必要で、完全には取り消せない影響もあります。

クラウドの作業領域にはチェックポイントや破棄できるチェックアウトが用意される場合があります。**何が対象で、いつまで保持され、外部サービスはどうなるか**を確認してください。「作業領域をリセット」は万能の取り消しボタンではありません。

実用的な手順は次のとおりです。

1. 仕事を定義し、必要なアクセスだけを許可する。
2. 開始時の状態を保存し（第五節）、必要なら別の作業ディレクトリを用意する。
3. 許可済みのローカル作業は進め、実際に範囲が変わるときに止まる。
4. 合意した公開や外部操作の前に、diffと関連する検証結果を見る。
5. 復旧が必要なら対象の変更だけを戻し、外部への影響は別に処理する。

## まとめ

- サンドボックス、ユーザーの許可、承認画面は、それぞれ違う問いに答えるものです。
- 範囲を明確に決めれば、許可済みのローカル作業で同じ確認を繰り返す必要はありません。
- 「承認のスキップ」「フルアクセス」のようなスイッチは、初心者は入れません。使うとしても隔離した使い捨ての環境だけです。自動モードは確認を減らしますが、すべての操作が適切だと保証するものではありません。
- 影響の大きい外部操作には、対象と限度を明示した許可が必要です。
- Gitの最小限の始め方：`git init`、`git add -A`、`git commit`で出発点を保存し、`git status`と`git diff`で変更を見て、`git restore`でファイルの未コミットの変更を捨て、`git revert`でコミットを取り消します。
- ブランチは開発の流れ、ワークツリーは別の作業場所です。どちらもサンドボックスやバックアップの代わりにはなりません。
- Gitが戻せるのは記録したプロジェクトの状態です。作業前に復旧の限界を知りましょう。

第27章では、この境界を計画に落とし込み、大きな変更を確認できる小さな単位に分けます。

   - C. コマンドを承認して、サンドボックスに複製を作って実行させる
   - D. 別のチェックアウトを作るか、Git worktreeを使う
   > **答えD。** ブランチは同じディレクトリの中の開発の流れで、フォルダは増えません（A）。新しい会話でもディレクトリが変わるとは限りません（B）。コマンドを承認しても作業ファイルの複製はできません（C）。ワークツリーは別の作業ディレクトリを用意しますが、セキュリティ上のサンドボックスではありません。

5. **[応用・誤解]** Agentがメールを送り、データベースを変更しました。Gitによる巻き戻しで保証できるのは何でしょうか？ <!-- quiz: q05 revision: 1 -->
   - A. メールの送信を取り消し、データベースを変更前の状態に戻す
   - B. リポジトリの全ファイルを戻す。一度もコミットしていないものも含む
   - C. 記録済みの関連コードを戻す。メールとデータベースは別に対応する
   - D. 起きてから間もなければ、外部への操作もまとめて取り消せる
   > **答えC。** Gitが扱うのはリポジトリに記録した内容です。メール、データベースの状態、請求はGitの外にあり、時間に関係なく取り消せません（A・D）。一度もコミットしていないファイルは、Gitに保存されていません（B）。

6. **[操作・観察]** 実際には削除せず、古いプロジェクトファイルを整理する計画を作ってください。何を先に確認しますか？ <!-- quiz: q06 revision: 1 -->
   > **確認したいこと：** 対象を一覧にし、生成ファイルと価値のあるデータを区別し、既存の作業を残します。Gitやバックアップが実際に何を保存しているかも確認しましょう。対象範囲と外部への影響を合意する方が、説明のない「全部きれいにする」を承認するより有用です。
