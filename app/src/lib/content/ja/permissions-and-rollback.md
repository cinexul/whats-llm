Agentはファイルを編集し、コマンドを実行し、接続したサービスを使えます。その力を活かすには、どこで作業してよいか、何をしてよいか、結果をどう確認して復旧するか、の三つを決めておきます。キーを押すたびに許可を求めるのではなく、意味のある境界を守ることが目標です。

## 一、サンドボックス・権限の付与・承認を分ける

部屋の修理を頼む場面を想像してください。鍵のかかった扉は入れる場所を制限し、作業依頼書は頼んだ仕事を示します。依頼の内容を変えるなら、先に連絡が必要です。

| 制御 | 答える問い | 例 |
| --- | --- | --- |
| サンドボックス | プロセスが技術的にアクセスできる範囲は？ | 書き込みは今のプロジェクトフォルダ内だけ。ネット接続は禁止 |
| 権限の付与 | あなたや組織が許可した仕事は？ | このページを修正し、関連するローカルの確認を実行する |
| 承認 | いつ止まって人の判断を待つか？ | サンドボックスの外に出るコマンドや、合意した範囲を超える操作のとき |

サンドボックス（sandbox）は技術的な囲いで、囲いの外のファイルやネットワークには触れられません。三つは関連していますが、同じものではありません。技術的に実行できるコマンドでも、あなたの依頼の範囲外かもしれません。承認画面は判断の機会であり、画面が出ないからといって、ほかの操作がすべて無害なわけではありません。

最小権限とは、その仕事に必要なファイル、ツール、アカウント、通信だけを許可することです。公開ページを読むのに受信箱全体へのアクセスは要りません。ローカル文書の修正に本番システムの鍵は要りません。

## 二、権限の四段階

ツールごとに権限設定の呼び名は違いますが、おおむね低いほうから四段階に並べられます。

![権限の四段階の図：下から順に、読み取りのみ、変更のたびに確認、プロジェクト内のファイルは自由に編集、何も聞かずに実行。下の二つは初心者向き、三つ目は出発点を保存してから使う、四つ目は初心者は使わない、と示されている](/figures/ja/permission-levels.svg)

1. 読み取りのみ：ファイルを見て質問に答えるだけで、何も変えません。知らないプロジェクトをまず調査させるのに向いています。
2. 変更のたびに確認：ファイルを変える前、コマンドを実行する前に止まって、あなたの同意を待ちます。使い始めのうちに向いています。
3. プロジェクト内のファイルは自由に編集：プロジェクトフォルダ内の変更は毎回確認せず、範囲外（ネット接続、プロジェクト外のファイルの変更など）は確認します。Gitで出発点を保存したあと（第五節）なら、手間が省けて、しかも戻せます。
4. 何も聞かずに実行：承認をオフにし、サンドボックスまで外すこともあります。初心者は使いません。

2026年10月時点の対応は次のとおりです（モード名は今後変わる可能性があります）。Claude CodeのManualモード（設定上の値は`default`）は、ファイルの変更、コマンドの実行、ネット接続のほとんどの前に確認するので、第2段階にあたります。`acceptEdits`モードは作業ディレクトリ内のファイルを直接変えられるので、第3段階です。ただし、新しいバージョンのClaude Codeは、ターミナルとVS Codeでは既定で後で触れるautoモードから始まります。第2段階で使いたいときは、ターミナルでShift+Tabを押し、ステータスバーに「manual mode on」と出るまで切り替えます。Codexは、Gitで管理されたフォルダでは最初から第3段階です（呼び名はAuto。サンドボックスの外に出るときだけ確認します）。それ以外のフォルダでは既定で読み取りのみです。セッション中に`/permissions`と入力すると変更できます。

第4段階はどちらのツールにもあり、名前にはどれも「dangerous」（危険）が入っています。Claude Codeの`--dangerously-skip-permissions`オプション（`bypassPermissions`モードに相当）、Codexの`--dangerously-bypass-approvals-and-sandbox`オプション（別名`--yolo`）と`danger-full-access`というサンドボックス設定です。これを使うと、Agentの判断ミスや、Webページやメールから読み込んだ悪意ある指示が、そのまま実際の操作になりかねません。確認が煩わしいという理由で有効にしないでください。無人でテストをまとめて回すなど、どうしても必要な場合でも、使い捨ての隔離環境に限ります。個人のファイルや大事なアカウント、鍵が入っていない仮想マシンやコンテナです。両社のドキュメントとも、これを高リスクと位置づけています。

ほかに「自動モード」の類もあります（たとえばClaude Codeのautoモード。新しいバージョンではターミナルでの既定です）。別のモデルが操作を審査するので、確認画面はかなり減ります。公式ドキュメントには、確認は減るが安全を保証するものではないと明記されています。削除、公開、支払いのような操作は、引き続き第四節のとおり明確に許可してください。

## 三、実用的な流れ：範囲を決める → その中で作業 → 検証

明確な依頼なら、まとまった作業を一度に許可できます。

> 「このプロジェクトのナビゲーションの不具合を直してください。関連ファイルの確認と編集、ローカルの検証は実行して構いません。私の既存の変更は残し、公開前にdiffと検証結果を見せてください。」

この範囲と環境の制限内なら、Agentはファイルを読み、編集し、テストし、失敗した検証を直すときに、同じことを何度も聞く必要はありません。すでに与えた許可は、その対象の仕事に引き続き有効です。新しい送信先、本番環境の変更、破壊的な整理、アクセス範囲の拡大などで、はじめて新たな判断が必要になります。

```text
目標・範囲・復旧方法を合意する
               ↓
許可された範囲で作業する → 結果を確認する
               │
               └─ 境界を越える必要がある？ → 具体的な操作を説明する → 承認を得る
```

確認画面が多いほど安全、とは限りません。曖昧な確認が続くと、読まずに承認する癖がつきます。役に立つ承認画面は、何を、どこで変え、誰に影響し、いくらかかり、どこまで戻せるかを示します。

## 四、影響の大きい操作には明確で具体的な許可が必要

「削除」という言葉だけでは危険度は分かりません。生成されたテストファイルの削除と、顧客記録の削除は大違いです。対象、範囲、外部への影響、戻せるかどうかで判断します。

| 操作 | 実行前に決めること |
| --- | --- |
| 価値のあるデータの削除・上書き | 対象、バックアップや復旧方法、無関係な作業を失わないか |
| メッセージ送信・公開 | 宛先、内容、外に出してよい情報 |
| 支払い・有料サービスの利用 | 予算、アカウント、数量、停止条件 |
| 稼働中のシステムやアカウント権限の変更 | 環境、影響する人、変更内容、復旧計画 |

許可は、今与える具体的な指示でも、以前に承認した範囲の明確な手順でも構いません。「確認済みのこの通知を、この三人に送って」に、同じ確認をもう一度求める必要はありません。一方、「受信箱を整理して」は、個人的なメールを新しい宛先に転送する許可ではありません。プロジェクトを編集してよいという許可も、公開や支払い、無関係なファイルの一掃まで認めるものではありません。範囲を超えるときは、具体的な案を示し、実行前に止まります。

## 五、Gitの最小限の始め方

これまでの章で何度も「出発点を保存する」「問題が起きたら巻き戻す」と書いてきました。ローカルのプロジェクトでは、ふつうGitがその役を担います。ファイルのバージョンを記録する道具で、コミット（commit）するたびに、その時点のプロジェクトを後から戻れる版として保存します。最低限、次のことを押さえれば十分です。

### 1. インストールして確認する

- Windows：Gitの公式サイトgit-scm.comから「Git for Windows」をダウンロードし、既定の設定のままインストールします。
- macOS：「ターミナル」で`xcode-select --install`を実行し、Appleのコマンドラインツール（Gitを含む）を入れます。Homebrewを使っているなら`brew install git`でも構いません。
- Linux：ディストリビューションのパッケージ管理ツールで入れます。

入れたら新しいターミナルを開き、`git --version`を実行します。バージョン番号が表示されれば完了です。

初めて使う前に、Gitに自分の名前を伝えます。パソコンごとに一度でよく、この二つは各コミットの記録に書き込まれます。

```bash
git config --global user.name "あなたの名前"
git config --global user.email "you@example.com"
```

### 2. プロジェクトの出発点を保存する

プロジェクトのフォルダに移動し、まず`git status`を実行します。「not a git repository」と表示されたら、まだGitで管理していないフォルダです。次を順に実行します。

```bash
git init
git add -A
git commit -m "作業前の出発点"
```

`git init`はこのフォルダをGitの管理下に置くもので、一度だけ実行します。`git add -A`はフォルダ内の追加・変更・削除をすべて「保存予定」のリストに入れます。`git commit -m "..."`はそのリストを一つの版として保存し、引用符の中に一言説明を書きます。コミット前に、パスワードや鍵のファイルが混ざっていないか見ておきましょう。記録したくないファイルは、プロジェクト内の`.gitignore`というテキストファイルに名前を書いておくと、Gitが対象外にします。以後は小さな一歩を終えて検収するたびに、`git add -A`と`git commit -m "やったこと"`で新しいセーブポイントを作ります（第27章）。

### 3. 何が変わったかを見る

- `git status`：前回のコミット以降に変更されたファイルと、Gitがまだ記録していない新しいファイル（Untracked files）を一覧にします。
- `git diff`：まだコミットしていない変更を行単位で表示します。読み方は第25章を参照してください。

### 4. 取り消す

- まだコミットしていないファイルを壊してしまった：まず`git diff ファイル名`で中身を確認し、`git restore ファイル名`を実行すると、最後のコミット（または`git add`）の時点の内容に戻ります。そのファイルの保存していない変更はそのまま捨てられ、取り戻せません。
- Agentが新しく作り、一度もコミットしていないファイルは、`git restore`の対象外です。`git status`では「Untracked files」に表示されるので、不要と確かめてから手で削除します。
- コミット済みの変更を一つ取り消したい：`git log --oneline`でそのコミットの番号を探し、`git revert 番号`を実行します。Gitはその変更を打ち消す「逆向き」のコミットを新しく作り、元の記録は残すので、比較的安全です。実行前に、手元の未コミットの変更はコミットするか片付けておきます。

ネット上の解説でよく見る`git reset --hard`は、未コミットの変更を一度にすべて捨てます。初心者は使わないでおきましょう。取り消しには何手順もかかることがよくあります。一つずつ進め、そのたびに`git status`で結果を確かめてください。

自分でコマンドを打ちたくなければ、コーディングエージェントに「Gitでこのプロジェクトの出発点を保存して。各コマンドを実行する前に何をするか説明し、私が確認してから進めて」と頼むこともできます。コマンドの実行を求められたら、上の説明と照らし合わせて理解してから承認します。

## 六、ブランチは別の部屋ではない

三つの用語を区別しましょう。

- ブランチ（branch）：名前を付けた開発の流れです。`git switch -c practice/first-task`で新しいブランチを作って切り替えると、以後のコミットはその流れに記録されます。作成しても別のディレクトリはできません。同じフォルダの中でブランチを切り替えても、使うのは同じフォルダです。
- ワークツリー（worktree）や別のチェックアウト：作業ファイルを置く別のディレクトリです。`git worktree`を使うと、履歴を共有しながら別の場所で別のブランチを扱えるので、二つの作業が互いに干渉しません。
- サンドボックス：技術的なアクセス境界です。ワークツリーはファイルを整理するだけで、それだけで他のディレクトリ、アカウント、ネットワークへのアクセスを防ぐわけではありません。

ブランチもワークツリーも、パソコン全体のスナップショットを撮る仕組みではありません。Gitが戻せるのは記録した内容だけで、未追跡・無視対象のファイル、ローカルのデータベース、鍵には、それぞれ別のバックアップが必要です。復元や変更の破棄も、保存していない作業を消すことがあるので、何を戻すのか先に特定しましょう。

## 七、復旧にも境界がある

コードを巻き戻しても、送信したメール、すでに相手が受け取ったデータ、支払った料金、リモートのデータベースの変更は戻りません。本番へのデプロイも自動では取り消されません。それぞれのシステムに復旧手順が必要で、完全には取り消せない影響もあります。

クラウドの作業環境や一部のツールにはチェックポイントがあります（たとえばClaude Codeの`/rewind`。第28章）。使う前に、何が対象で、いつまで保存されるかを確かめてください。「作業環境をリセット」は万能の取り消しボタンではありません。復旧が必要なときは今回の作業の変更だけを戻し、外部への影響は別に処理します。だからこそ、公開や送信のような外部への操作の前に、diffと検証結果を確かめておきます（第25章）。

## まとめ

- サンドボックスは技術的に触れられる範囲を、権限の付与はするべき仕事を、承認はいつ止まって人に聞くかを決めます。
- 権限はおおむね四段階：読み取りのみ、変更のたびに確認、プロジェクト内のファイルは自由に編集、何も聞かずに実行。初心者は下の三つを使い（三つ目はGitで出発点を保存してから）、四つ目は使いません。自動モードは確認を減らしますが、すべての操作が適切だとは保証しません。
- 範囲を一度はっきり決めれば、許可済みのローカル作業で同じ確認を繰り返す必要はありません。削除、公開、支払い、本番システムの変更には、対象と限度を明示した許可が必要です。
- Gitの最小限の始め方：`git init`、`git add -A`、`git commit`で出発点を保存し、`git status`と`git diff`で変更を見て、`git restore`でファイルの未コミットの変更を捨て、`git revert`でコミットを取り消します。
- ブランチは開発の流れ、ワークツリーは別の作業場所です。どちらもサンドボックスやバックアップの代わりにはなりません。
- 巻き戻しで戻るのは記録したプロジェクトの状態だけです。外部への影響は別に処理します。

第27章では、この境界を計画に落とし込み、大きな変更を一つずつ検収できる小さな単位に分けます。

## 出典とバージョンについて

権限モード、関連するスイッチ、Gitの始め方は、2026-10-29に公式ドキュメントで確かめ直しました。本章の承認手順は実用上の提案であり、すべての製品の初期設定が同じという意味ではありません。

   - C. コマンドを承認して、サンドボックスに複製を作って実行させる
   - D. 別のチェックアウトを作るか、Git worktreeを使う
   > **答えD。** ブランチは同じディレクトリの中の開発の流れで、フォルダは増えません（A）。新しい会話でもディレクトリが変わるとは限りません（B）。コマンドを承認しても作業ファイルの複製はできません（C）。ワークツリーは別の作業ディレクトリを用意しますが、セキュリティ上のサンドボックスではありません。

5. **[応用・誤解]** Agentがメールを送り、データベースを変更しました。Gitによる巻き戻しで保証できるのは何でしょうか？ <!-- quiz: q05 revision: 2 -->
   - A. メールの送信を取り消し、データベースを変更前の状態に戻す
   - B. リポジトリの全ファイルを戻す。一度もコミットしていないものも含む
   - C. 記録済みの関連コードを戻す。メールとデータベースは別に対応する
   - D. 起きてから間もなければ、外部への操作もまとめて取り消せる
   > **答えC。** Gitが扱うのはリポジトリに記録した内容です。メール、データベースの状態、請求はGitの外にあり、時間に関係なく取り消せません（A・D）。一度もコミットしていないファイルは、Gitに保存されていません（B）。

6. **[操作・観察]** 実際には削除せず、古いプロジェクトファイルを整理する計画を作ってください。何を先に確認しますか？ <!-- quiz: q06 revision: 2 -->
   > **確認したいこと：** 対象を一覧にし、生成ファイルと価値のあるデータを区別し、既存の作業を残します。Gitやバックアップが実際に何を保存しているかも確認しましょう。対象範囲と外部への影響を合意する方が、説明のない「全部きれいにする」を承認するより有用です。
