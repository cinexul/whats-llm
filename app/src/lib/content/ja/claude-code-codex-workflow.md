第23章では、コーディングエージェントが何かを見ました。自分でプロジェクトを読み、ファイルを変え、コマンドを実行するAgentです。本章では、それを連れてどう仕事をするかを扱います。Claude CodeでもCodexでも、うまくいくタスクはほとんど同じループをたどります：調査 → 計画 → 実行 → 検収。この順番を身につければ、いつ任せてよく、いつ立ち止まって確かめるべきかが分かります。

本章もコードが書けることを前提にしません。インストールと具体的なコマンドは第28・29章で扱います。

## 一、おさらい：Webチャットとどこが違うか

| | Web/アプリのチャット | コーディングエージェント |
| --- | --- | --- |
| コードの扱い | 文章をくれる。コピーして使うのは自分 | プロジェクトのファイルを直接変える |
| どれだけ知っているか | 貼り付けた内容だけ | 自分でプロジェクト全体を探って現状をつかむ |
| 進め方 | 一問一答 | 目標に向かって自分で何歩も進む |
| 間違えたときの結果 | 答えが違うだけ。使わなければよい | 本当にファイルが変わる。だから巻き戻せることが必要 |

最後の行が肝心です。本当にあなたのものを変えるので、「やり直しのきく環境で使う」ことは、こだわりではなく前提です。

第23章のたとえがここでいちばん役に立ちます。とても優秀で手が速いけれど、初出勤の新人同僚です。力仕事を任せれば速くたくさんこなしますが、あなたのルールも、触ってはいけない場所も知らず（第28章でルールの書き方を扱います）、自信たっぷりに間違えます（第9章のハルシネーション）。だからあなたは率いる側です。仕事を振ることと検収することはあなたの役目で、最後に名前が載るのもあなたです。

## 二、核心ワークフロー：調査 → 計画 → 実行 → 検収

下の図がこのループです。四つのうち、調査と実行は主にAIがやります。計画と検収は、あなたが守る二つの関門です。計画はあなたが承認してはじめて実行に移り、検収はあなたが通してはじめてマージされます。検収で通らなければ、その場で無理に直すのではなく、調査か計画に戻ります。

なぜこの二つの関門が欠かせないのでしょうか。コーディングエージェントは間違えるうえに、手を動かせるからです。この二つが同時に成り立つ以上、実行前に計画を見ることと、実行後に検収することは省けません。二つの関門を守れば、残りの力仕事は安心して任せられます。

![作業ループの図：調査、計画、実行、検収の四つが輪になって並び、各段階の下に人がそこで何をするかが書かれている。計画と検収は人が守る関門。検収で不合格なら矢印で調査か計画に戻り、合格ならコミットして次の小さな一歩に進む](/figures/ja/work-loop.svg)

### ① 調査：AIがプロジェクトを読み、あなたはざっと確かめる

いきなり変更させてはいけません。まず関係するコードを探させ、今どう実装されているかを説明させて、見当違いの場所を探していないか確かめます。たとえばこう頼みます。

> 「まだ手を動かさないで、調査だけして。ページに検索ボックスを追加するには、どのファイルが関わっていて、今はどう実装されている？」

### ② 計画：AIが案を出し、あなたが承認する

「どう変えるつもりか」を計画として書かせます。どのファイルを触るか、新しく何を足すか、何ステップに分けるか。あなたが読んで承認してから、手を動かし始めさせます。数十秒で済むこのステップで、「30分も見当違いの方向に進んでいた」という手戻りの大半を防げます。2026年10月時点では、Claude CodeもCodexも計画モードを備えていて、`/plan`と入力すれば入れます。そうしたモードがないツールでも、「まだ手を動かさず、計画だけ出して」と言えば同じことができます（第27章で詳しく扱います）。

### ③ 実行：AIがファイルを変え、あなたはいつでも止められる

承認すると変更が始まります。どの操作を毎回確認し、どの操作を許可の範囲内で自動実行するかは、ツールと権限の設定しだいです（第26章）。確認画面が出ないからといって、危険がないわけではありません。削除、公開、外部への送信などは、事前に決めたルールに従わせます。それていると感じたら中断し、はっきり伝え直してから続けさせます。

### ④ 検収：あなたが確かめ、合格したらマージする

これがあなたにとって最も重要なステップで、第25章で詳しく扱います。要は三つの問いです。何を変えたか（diffを見て、普通の言葉で説明させる）。本当にできていて、ほかを壊していないか（先に書いておいた検収手順で試し、関連するテストも走らせる）。問題があったときの代償はどれくらいで、元に戻せるか。コードを一行残らず読める必要はありませんが、この三つに答えられないうちはマージしないでください。

## 三、初めて動かすとき、何を期待するか

1. まず、やり直しのきく環境を用意します。ローカルのプロジェクトで手を動かさせるときは、Gitで管理し、出発点をコミットしてから新しいブランチを切ります（Gitを使ったことがなければ、先に第26章の「Gitの最小限の始め方」を）。ブランチ自体はバックアップではありません。Gitが戻せるのはコミットした版だけで、メール、デプロイ、外部データの変更は取り消せません。Webやクラウドの入り口には、それぞれ別の隔離と復元の仕組みがあるので、別途確かめてください（第26章）。
2. 最初はしばらく「読む」時間がかかります。プロジェクトを見て回っているので、固まったと思わないでください。
3. 確認画面が何を聞いているか読みます。確認を求める操作もあれば、許可済みの範囲で自動実行される操作もあります。
4. 間違えるし、それることもあります。それが普通です。そのときは、ぐちゃぐちゃの中で無理に直そうとしないこと。いちばん手っ取り早いのは、きれいな状態に巻き戻し、新しい会話を開いて、さっきぶつかった問題を前提として伝え直すことです（第13章・第30章）。
5. とても新しい技術が関わるときは、バージョンをはっきり伝えるか、最新の資料を貼り付けます（第9章の知識カットオフ）。
6. 鍵、パスワード、本物の個人情報を、会話に貼ったりコードに書いたりしないでください（第37章）。費用については、サブスクリプションの利用枠とAPIの従量課金は別物です。第38章で詳しく扱います。

初心者がいちばんよくやる失敗は、大きな機能を一気に全部作らせることです。変更が大きいと検収が大変になり、問題が起きても巻き戻しにくくなります。小さく分けるほうが速いのです。小さく作り、小さく検収し、一度コミットして、次へ進みます（第27章）。

## 四、Claude CodeとCodex：どこが同じで、どこが違うか

| | 同じところ（安定） | 違うところ（変わる。第28・29章） |
| --- | --- | --- |
| 位置づけ | どちらもプロジェクトで手を動かすコーディングエージェント | 提供元、中身のモデル、用意されている入り口 |
| ワークフロー | どちらも「調査 → 計画 → 実行 → 検収」が当てはまる | 具体的なコマンド、ショートカット、画面 |
| 安全 | どちらも権限設定と巻き戻せる環境が必要 | 既定の権限と設定の仕方 |
| 始め方 | どちらもGitのブランチで小さく試す | インストールとログインの方法 |

このワークフローはどのツールに替えても使えます。ある製品のボタンではなく、「間違えるうえに手を動かせる助手をどう率いるか」から来ているからです。

## 五、よくある誤解

| 誤解 | 実際 |
| --- | --- |
| AIなのだから書いたコードは正しいはず。そのままマージ | 自信たっぷりに間違える。第25章のとおり検収し、三つの問いに答えられなければマージしない |
| 大きな機能を一度に全部作らせるのが一番楽 | 大きな変更は検収しにくく巻き戻しにくい。小さく分けて小さく検収するほうが速い |
| プロジェクト全体と昨日の会話を覚えている | モデル自体に会話をまたぐ記憶はない。CLAUDE.mdのような「プロジェクト記憶」は、製品が保存した文章を毎回コンテキストに入れ直しているもの（第9章・第28章） |
| プログラミングができないと使えない | 一行一行を書ける必要はない。仕事を振り、具体的なチェックで検収できればよい |
| それたら、追いかけてずっと直し続ける | 巻き戻して新しい会話でやり直す。乱れたコンテキストの中で無理に直すと、たいてい悪化する |

## まとめ

- Claude CodeとCodexは、プロジェクトの中で手を動かすコーディングエージェントです。ターミナル、エディタ、デスクトップアプリ、Webのどこで使うかは製品によります。
- Webチャットとの根本的な違いは、ファイルを直接変え、自分でプロジェクトを探り、何歩も進むこと。だから巻き戻せる環境で使います。
- 核心のワークフローは調査 → 計画 → 実行 → 検収。あなたは二つの関門を守ります。計画の承認と、変更の検収です。検収で通らなければ調査か計画に戻ります。
- 初めて使うときは、出発点をコミットしてGitのブランチを切り、タスクを小さく分け、それたら巻き戻してやり直し、鍵は絶対に貼らないこと。
- このワークフローは特定のツールに依存しません。一度学べば、ツールを替えても使えます。

次章（第25章）では、ワークフローの中でいちばん練習しておきたい一歩、diffの読み方、テスト、巻き戻し、検収を詳しく扱います。

## 小テスト

> 全6問。概念・誤解・場面・操作の4種類をカバーしています。まず自分で考えてから、引用ブロックの答えと解説を見てください。

1. **[基礎・概念問題]** プログラミングエージェント（Claude Code / Codexなど）と、WebチャットAIの最も根本的な違いは？ <!-- quiz: q01 revision: 2 -->
   - A. より強いモデルを使っているので、答えが正確で間違いも少ない
   - B. プロジェクト全体を覚えていて、会話を変えても忘れない
   - C. プログラミングの質問だけに答え、ほかの分野は扱わない
   - D. プロジェクトのファイルを直接変更し、コマンドも実行できる
   > **答えD。** チャットAIは「あなたが行き来してコピペする」もの。プログラミングエージェントは「あなたのプロジェクトの中で直接手を動かす」もの。これこそが、効率的でありながら「許可の仕組み」で見張る必要がある理由です。AとCは違いをモデルの強さや話題の範囲と捉えています。Bはモデルと製品を混同しています。モデル本体に会話をまたぐ記憶はなく、「プロジェクト記憶」は製品が毎回ファイルをコンテキストに入れ直しているものです。

2. **[基礎・概念問題]** 「調査 → 計画 → 実行 → 検収」のループのうち、人にとって最も肝心な仕事はどのステップ？ <!-- quiz: q02 revision: 2 -->
   - A. 調査：関連ファイルを自分で探し出してから、Agentに渡す
   - B. 実行：Agentの変更を一つ残らず見張り、一件ずつ承認する
   - C. 計画の承認と、実行後にdiffを見てテストを走らせる検収
   - D. 目標をはっきり書けば十分で、残りはすべてAgentに任せる
   > **答えC。** AIに仕事をさせるとき、人は二つの関門を守ります：**手を動かす前に計画を承認し、手を動かしたあとに変更を検収する**。調査や実行のような力仕事はAIに任せ（A・B）、あなたはざっと目を通し、いつでも止められるようにしておけば十分です。Dは二つの関門をどちらも手放しています。

3. **[基礎・誤解問題]** 「AIなのだから書いたコードは正しいはず。そのままマージすればよい」――どこが間違い？ <!-- quiz: q03 revision: 3 -->
   - A. 自信たっぷりに間違えるので、検収していない変更はマージしない
   - B. 間違っていない。コードが動きさえすれば、それは正しいということだ
   - C. Agent自身に「本当に問題ない」と確認させていない点が間違いだ
   - D. 全部書き直していない点が間違い。Agentのコードは人が直すべきものだ
   > **答えA。** ハルシネーション（第9章）はコードを書くときも同じように起きます。存在しない関数をでっち上げたり、バージョン違いの書き方を使ったりします。動くことは正しいことと同じではありません（B）。Agentに太鼓判を押させても検証にはなりません（C）。全部書き直すのは逆の極端です（D）。diffは見る、チェックは走らせる、はっきりしないところはまず説明させましょう。

4. **[応用・誤解問題]** 「大きな機能を一度に全部作らせるのが一番楽」――なぜしばしば、かえって手間が増えるのか？ <!-- quiz: q04 revision: 2 -->
   - A. 実は増えない。大きな仕事を一度に伝えれば、やり取りが減る
   - B. Agentは一度に一つのファイルしか変更できず、何度にも分けるから
   - C. 変更が大きいほど一行ずつ検収できず、誤りの特定も巻き戻しも難しい
   - D. 問題は大きなタスクが利用枠を多く使うことだけで、ほかは同じだ
   > **答えC。** 大きな変更は大きな死角です。diffを見終えられず、誤りは大量の変更に紛れ、きれいに巻き戻せません。タスクを小さく分け、先に計画を見て、小さく検収するほうが、かえって最も速いのです（第27章）。Bは誤りで、一度に多くのファイルを変更できることこそが問題です。Dは利用枠だけを見て、検収と巻き戻しの難しさを見落としています。

5. **[基礎・場面問題]** コードを直させたら、Agentが本筋からそれて、直すほど乱れてきた。最善の損切りの動作は？ <!-- quiz: q05 revision: 3 -->
   - A. 同じ会話の中で、正しくなるまで一言ずつ何度も直し続ける
   - B. きれいな状態に巻き戻し、新しい会話でぶつかった問題を伝える
   - C. 今の変更の上にもう一度直させて、誤りを上書きする
   - D. プロジェクトを丸ごと消し、最初から生成し直させる
   > **答えB。** 乱れたコンテキストの中で無理に直すと（A・C）、たいてい直すほど歪んでいきます。**巻き戻し + 教訓を携えたきれいな会話でやり直す** ことが、ほぼいつも速いのです（第13章・第30章）。事前にコミットやバックアップをしておけば、戻る地点を確保できます（Gitの基本は第26章）。巻き戻すのはこのタスクの変更だけにしましょう。プロジェクトを消すと（D）、うまくいっていた部分まで失います。Gitで外部への操作は取り消せません。

6. **[応用・操作/観察問題]** ツールを実際にインストールする必要はありません。コードの変更（または第25章のdiffの例）を一つ見つけ、第25章の「最終チェックの三つの問い」を当てはめてみましょう：何を変えたか？ 本当にできていて、ほかを壊していないか？ 問題があったときの代償はどれくらいで、元に戻せるか？ 一つ目に答えられなければ、戻って普通の言葉で説明させるべきです。 <!-- quiz: q06 revision: 3 -->
   > **観察できるはず：** 検収は神秘的なものではなく、この三つの問いだけです。しかもコードを一行残らず読める必要はありません。一つ目はAIの普通の言葉での説明とdiffの突き合わせ、二つ目は先に書いた検収手順とテスト、三つ目は危険と戻り道で答えます。「三つの問いに答えられなければマージしない」という習慣は、どんなコマンドを覚えるよりも大切です。インストールと具体的なコマンドは第28・29章と付録Cを参照してください。
