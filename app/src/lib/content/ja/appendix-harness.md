付録Cはツールにどんなコマンドや設定があるかの一覧です。この付録では、それらを自分のルールや確認とつなげて、コーディングエージェントの仕事を信頼できるものにする方法を扱います。業界では、この仕組み一式をharness（ハーネス）と呼んでいます。

## 一、Harnessとは何か

harnessはもともと馬に付ける引き具のことです。馬の力は変わりませんが、引き具があってはじめて、馬は荷車をあなたの望む方向へ引けます。AIの分野では、2026年時点で「エージェント = モデル + harness」という言い方がよく使われます。harnessはエージェントのうちモデル以外のすべてを指し、モデルへの指示、使えるツール、作業が終わるまでモデルを繰り返し呼び出すループ、各ステップでモデルに何を見せるかを決めるコンテキスト管理、権限と確認が含まれます。例えばAnthropicはClaude Agent SDKを汎用のエージェントharnessと呼び、Claude Codeを動かしているのと同じツール、エージェントループ、コンテキスト管理を提供すると説明しています。

使う側から見ると、harnessには二つの層があります。内側の層はツールに組み込まれたものです。Claude CodeやCodexのようなコーディングエージェントには、ループ、ファイルの読み書きやコマンド実行のツール、コンテキストの圧縮、許可の仕組みがすでに入っていて、ふつうは変えられません。外側の層は自分で組むものです。プロジェクトのルールファイル、手を動かす前の計画確認、自動テストや確認、人による受け入れ確認です。ThoughtworksのBirgitta Böckelerは、外側の層を二種類に分けています。手を動かす前にやり方を伝える事前のガイド（ルールファイルなど）と、手を動かした後に問題を見つけて自分で直させる事後のチェック（テストやコードチェックなど）です。

以下は、この外側の層を組むために本書がまとめた作業チェックリストです。上の資料と本書第24〜27章のやり方をまとめたもので、どこかのメーカーの公式な方法ではありません。Claude CodeでもCodexでも考え方は同じです。

## 二、自分で組める外側の層：四つの部品

| 部品 | 種類 | 役割 | 例 |
| --- | --- | --- | --- |
| プロジェクトのルールファイル | 事前のガイド | 毎回の作業開始時にコンテキストへ入り、このプロジェクトのやり方を伝える | `CLAUDE.md`、`AGENTS.md`（第28章、付録C） |
| 計画の関門 | 事前のガイド | 手を動かす前に、どのファイルを変え何を再利用するかを確認する | 計画モード（第27章） |
| 自動の確認 | 事後のチェック | 変更のたびに実行し、失敗したら自分で直させる | テスト、コードチェック、ビルド |
| 人の受け入れ確認 | 事後のチェック | 動作が要件どおりか確かめ、リスクの高い変更にはもう一段の確認を加える | この付録第六節のチェックリスト（第25章） |

一つ区別しておきたいのは、ルールファイルはコンテキストに入る文章にすぎないということです。モデルはたいてい従いますが、保証はありません。`.env`の読み取りやディレクトリの削除のように、本当に止めたいことは、ツールの権限ルールやサンドボックスで強制します（第26章）。

## 三、五ステップのワークフロー

外側の層を具体的な会話に落とすと、次の五ステップになります。各ステップの「AIに言う言葉」の例は平易な言葉のプロンプトで、製品のコマンドではありません。

| ステップ | このステップで何をさせるか | プロンプト例 |
| --- | --- | --- |
| ① 調査 | まず現状を把握し、手は動かさない | 「手を動かす前に、このプロジェクトを調査して：全体の構造、今回の要件に近い既存のやり方、再利用できる共通モジュール（ネットワークリクエスト、エラー処理、ログ、フォームなど）、命名とコードのスタイル。ファイルパスを付けて一覧にして、まだコードは書かないで。」 |
| ② ルールを書く | 調査結果をルールとして固める | 「上の調査結果を、AI向けのプロジェクトルールに整理して：どの仕組みを必ず再利用すべきか、何が禁止か。」 |
| ③ 計画の関門 | 案を出し、あなたの承認を待つ | 「タスクは〈……〉。手を動かす前に計画を出して：どのファイルを変更・追加するか、どの既存の仕組みを再利用するか、新しい依存が必要か（必要なら理由も）。私が承認するまでコードを書かないで。」 |
| ④ 実行 | 既存のものに沿って | 「承認。既存のディレクトリ構造、命名、スタイルに厳密に従い、さっき見つけた共通モジュールを再利用して実装して。自分で新しい抽象を持ち込まないで。」 |
| ⑤ 検収 | 自己点検のあと、あなたが確認 | 「さっき参考にした既存の書き方と照らし合わせて自己点検して：車輪の再発明をしていないか、全体の設計を壊していないか、共通モジュールを迂回していないか。そのうえで、何を変えたか、どこにリスクがあるかを平易な言葉で説明して。」その後、第六節のチェックリストで受け入れ確認をします。 |

流れ全体で手戻りをいちばん減らすのは第③ステップ、つまり手を動かす前に何をしようとしているかを見ることです。多くのツールには、このステップを守る計画モードがあります（第27章、付録C）。

## 四、プロジェクトのルールファイル：コピーできる雛形

第②ステップのルールは、プロジェクト内のファイルにしておき、ツールが作業開始のたびに自動で読むようにするのが一番です。Claude Codeは`CLAUDE.md`を使い（ない場合は`AGENTS.md`も読みます）、Codexは`AGENTS.md`を使います（付録C）。「プロジェクトの決まりを覚えた」ように見えるのは、製品が作業のたびにファイルをコンテキストに入れ直しているからで、モデル自体が覚えているわけではありません（第13章）。ファイルに書いたことだけを「覚えている」ので、ルールは具体的なほど安定します。

次の雛形の`<...>`を、自分のプロジェクトの実情に置き換えてください。

```markdown
# プロジェクトのルール / AIとの協働ルール

## 最も大事な原則
- 既存の実装方法と設計に沿う。自分の流儀を持ち込まない。
- 新しい仕組み（ライブラリ、抽象、層）を入れる前に、同じ種類の既存のやり方がないか調べる。あれば再利用し、なければ理由と代案を先に説明して承認を待つ。
- 全体のアーキテクチャ（層の構造、依存の向き、命名規則）を壊す変更はしない。

## 作業の流れ
1. まず関連する既存の実装と共通モジュールを調べ、参考にした場所（パス）を挙げる。
2. 実装計画（変更・追加するファイル、再利用するもの、新しい依存の要否と理由）を出し、承認されてからコードを書く。
3. 変更後は既存の確認、フォーマット、テストを実行し（<例：npm run lint && npm test>）、結果を報告する。

## 技術スタックとバージョン
- <例：TypeScript 5 / React 18 / Vite>

## ディレクトリ構造と役割
- <例：components/画面　hooks/ロジック　services/通信　utils/共通関数>
- 依存の向き：<例：画面 → hooks → servicesの一方向。逆向きや層の飛び越しは禁止>

## 必ず再利用する共通の仕組み
- ネットワークリクエスト：<例：services/apiClient>（あちこちで直接fetchを書かない）
- エラー処理：<例：AppError / errorHandler>
- ログ：<例：logger>（直接console.logを使わない）

## 禁止事項
- 勝手に第三者の依存を追加する
- .envなどの鍵のファイルを読む・表示する
- 層を飛び越えた依存（画面層から直接データベースに触れるなど）
```

## 五、うまく働かせるためのコツ

| コツ | やり方 |
| --- | --- |
| ルールは具体的に | 「きれいに書いて」では効きません。再利用するモジュール名、ファイルパス、禁止事項を書き込みます |
| 調査・計画・実行を分ける | 一言で全部済ませようとせず、調査と計画の承認をそれぞれ別の往復にします |
| 小さく進める | 一度に大きく変えさせると脱線しやすいので、小さく分け、一歩ごとに確認します |
| ルールを足し続ける | 脱線に気づいたら、対応するルールをファイルに足し、チームで共有します |
| 確認を自動で走らせる | テストやコードチェックのコマンドをルールファイルに書き、変更のたびに実行して結果を報告させます |
| 抽象化しすぎない | 「再利用」が行きすぎると不要なラッパーが増えます。既存コードの粒度に合わせます |

## 六、本番前のチェックリスト

この二つのチェックリストを手元に置きましょう。AIに渡す前に一つ目を、その成果物を採用する前に二つ目を確認します。

### AIに渡す前に

- 渡す内容に、機密のコード、本番データ、個人情報は入っていないか。あれば先にマスキングするか、渡さない（第37章）。
- APIキー、パスワード、接続文字列が紛れ込んでいないか。これらは一切渡さない（第37章）。
- 使うサービスとプランは、会社やこの場面で認められたものか。
- 前提（言語、フレームワーク、バージョン）をはっきり伝えたか。
- 関連するコード、ログ、期待する動作など、十分な文脈を渡したか。

### 成果物を採用する前に

コードを書けない人がすべての変更を一行ずつ理解する必要はありません。ただし、次のことは必ず行います。

- 具体的な受け入れ確認で動作を確かめる。どのページを開き、どこを押し、何が見えるべきか。関連するテストが通るか、もとの機能が壊れていないか（第25章）。
- エージェントに今回のdiffを平易な言葉で説明させる。どのファイルをなぜ変えたかを聞き、リスクのある部分を指摘させます。変更の範囲が依頼と合わなければ、まだ採用しません。
- お金、個人データ、鍵、ファイルの削除、外部への公開にかかわる変更は、もう一人に確認してもらう。詳しい同僚か、少なくとも別に立てた独立のレビューです。
- 元に戻せない操作は実行しない。変更がGitにコミットされ、データのバックアップがあることを先に確かめます（第26章）。送ったメールや書き換えた本番データは、Gitでは戻せません。
- 新しく加えた依存ライブラリの出どころは信頼できるか、ライセンスはその使い方を認めているか（第39章）。
- 出てきた関数名、API、設定項目は本当に存在するか。公式ドキュメントや実際の実行結果で確かめる（第9章）。
- 重要な事実、数字、引用を自分で確かめたか（第39章）。

## 七、チームでルールを決めるとき

一人で使うなら習慣で回りますが、チームで使うなら書かれたルールが必要です。データ、許可、認証情報、復旧の四つの書き方は第40章にあります。コーディングのチームはそれに加えて、次の二つを決めましょう。

1. 承認の流れ：AIが生成したコードを、レビュー、マージ、デプロイまで誰がどんな基準で承認するか。
2. 共有の資産：プロジェクトのルールファイルやよく使うプロンプトテンプレート（付録B）をまとめてチームで使い、定期的に見直す。ツールもモデルも変わり続けるからです。

## まとめ

- harnessはエージェントのうちモデル以外のすべて、つまり指示、ツール、ループ、コンテキスト管理、権限、確認を指します。コーディングツールには内側の層が組み込まれていて、あなたが組むのは外側の層です。
- 外側の層は、事前のガイド（ルールファイル、計画の関門）と事後のチェック（自動の確認、人の受け入れ確認）でできています。本当に止めたいことは、ルールに書くだけでなく権限やサンドボックスで強制します。
- 五ステップの中では、手を動かす前に計画を見ることが手戻りをいちばん減らします。
- 採用前にコードを一行ずつ読む必要はありませんが、具体的な確認で動作を確かめ、diffとリスクを説明させ、リスクの高い変更はもう一人に確認してもらい、元に戻せない操作は実行しません。
