前面几章讲了怎么带编程智能体顺利做事：通用工作流（第24章），以及Claude Code和Codex的实际操作（第28、29章）。可是不管你多熟练，总会出岔子：它会犯错、会跑偏、会自信地胡来。这一章不教你“永远不出错”，而是教两件更实在的事：认得出八种最常见的失误，晓得病根和对策；真卡住了、改乱了，有一套急救清单把你捞回干净的状态。这些做法不分工具。

## 一、八种常见失误：症状 → 原因 → 对策

下面每一条都是新手反复碰到的问题，你可以对号入座。

### 1. 任务太模糊，它丢三落四

你说“帮我优化一下这个页面”，它改出来的东西完全不是你想要的，或者只做了一半。指令太笼统，它只能猜，而它常常猜错（第11章）。把目标说具体：要达成什么、动哪一块、什么算“做完”。动手前先让它复述一遍它的理解。

### 2. 一次改太大，根本没法验收

你让它“把整个功能全做完”，它改了十几个文件，满屏的diff你看不过来，出了问题也不知从哪查。改动越大，盲区越大。把任务拆小：做一小块、验收一小块、提交一次，再做下一块（第27章）。

### 3. 不看diff，连点“同意”

它每次请求许可，你都看也不看就点同意，回头发现它动了不该动的文件，甚至删了重要的东西。把确认当成例行公事，等于拆了刹车（第26章）。同意之前先看它要做什么、改了什么；看不明白就问“这一步是做什么的”，问清楚再放行（第25章）。

### 4. 一个对话从头聊到尾，不切换

同一个对话聊了几十轮，它越来越“不听话”：无视你的新要求、翻出早被否决的方案、前后矛盾。这是第3、13章讲的上下文问题：对话越长，噪音越多，重点被淹没。一个话题一个对话；它开始“不听话”了，就开新对话，把还需要的信息重新交代清楚。

### 5. 轻信幻觉，不复核

它信誓旦旦地用了一个根本不存在的写法，或者引了一个查无此事的依据，你照单全收。它追求的是“像真的”，不是“是真的”（第9章），说得越流畅，不代表越可靠。越要紧的事越要验证：让它给出处、跑测试，关键事实自己再查一遍。

### 6. 方向错了还硬纠，越改越歪

一个方向明显走不通，你还揪着它在原方案上一句句改，结果越改越乱。错误的尝试已经塞满了上下文，它被自己之前的错误带着走（第13章）。承认此路不通：回滚到上一个干净的状态，开新对话，把刚才碰到的问题当作前提重新交代。

### 7. 没验收就合并

它说做完了，你直接合并、上线，过两天才发现原来好好的功能被弄坏了。这是把“它说做完了”当成了“它做对了”。按第25章验收：让它解释改了什么，照事先写好的步骤亲手试，跑相关测试；验收三问答不上来，就别合并。

### 8. 贴了密钥或敏感信息

图省事把API密钥、密码、真实的个人信息贴进了对话，或者写进代码推到了公开仓库。贴进去的东西就等于交了出去（第37章）；密钥落到别人手里，别人就能花你的钱（第35章）。万一贴出去了，立刻到对应平台作废旧密钥、换新的，别心存侥幸。

> **要点：** 八条其实只违反了三条原则：没把话说清（1、2），没守住动手前后的两道闸门（3、5、7），上下文和数据没管好（4、6、8）。记住这三条，比死记八条更管用。

## 二、卡住了怎么办：五步急救清单

上面讲的是防，这一节讲救。它已经跑偏、你一头雾水、改得一团乱时，别在乱局里缠斗，按下面五步走：

```text
卡住/改乱了，按顺序来：
① 先中断 ──→ ② 说清现状 ──→ ③ 回滚到上个好状态 ──→ ④ 开新对话重来 ──→ ⑤ 诊断
（立刻喊停）  （先盘点再动）    （回到干净的地方）       （换张干净桌子）    （想清为什么会偏）
```

1. 先中断。觉得不对劲，第一反应是打断它，而不是看着它继续往错的方向跑。截至2026年10月，Claude Code和Codex都可以按Esc打断正在进行的操作。越早停，损失越小；停下来以后，也别在慌乱中继续点同意。

2. 说清现状。先盘点：它现在改了哪些东西？哪些是你想要的，哪些是跑偏弄的？上一个干净、能用的状态在哪里？`git status`和`git diff`能列出改过的文件（第26章）。不盘清就回滚，容易退过头或退不到位。

3. 回滚到上个好状态。这是急救的核心。如果你一开始就用Git存了起点、切了新分支，现在就能把这次任务的改动退回那个干净的状态，具体命令见第26章“Git最小起步”；Claude Code的`/rewind`也能退回它自己改过的文件（第28章）。前面几章反复说“先存起点再动手”，就是为了这一刻。回滚撤不回已经发出的邮件、删掉的云端数据这类外部影响。

4. 开新对话重来。回到干净状态后，别在那个乱掉的对话里继续。开一个新对话，把“刚才那条路走不通、碰到了什么问题”当作前提告诉它，让它带着教训重新规划。旧对话里堆满了错误的尝试，在那上面继续，它还会被带偏。

5. 诊断。最后花一分钟复盘：这次跑偏，病根在哪？任务说得太模糊（第1条）？一次让它改太多（第2条）？还是该回滚的时候硬纠了（第6条）？找到病根，下次从源头堵住，比如先让它出计划（第27章），或者把任务拆得更小。

新手最常见的错误，不是出岔子本身，而是出了岔子不肯回滚：总觉得“再调一下就好了”，半小时后比一开始还糟。熟练的人恰恰相反，一感觉方向不对，宁可回滚重来，也不在一团乱上缝缝补补。

## 三、常见误解

| 误解 | 实际 |
| --- | --- |
| 我够熟练就不会出岔子 | 它会犯错又能动手，出岔子是常态；要紧的是会救 |
| 跑偏了就追着它一直纠 | 回滚、开新对话重来；在乱掉的上下文里硬纠往往越改越糟（第6条） |
| 许可确认很烦，一路点同意就好 | 那等于拆了刹车；同意前先看它要做什么（第3条、第26章） |
| 它说做完了就是做对了 | 没验收就别合并（第7条、第25章） |
| 回滚就是失败、认输 | 回滚是最大的安全网，往往是回到正轨最快的路 |
| 贴一次密钥应该没事 | 贴进去就等于交出去；立刻作废、换新（第8条、第37章） |

## 小结

- 编程智能体一定会出岔子，因为它会犯错又能动手；目标不是永远不出错，而是认得出、救得回。
- 八种常见失误：任务模糊、一次改太大、不看diff连点同意、会话不切换、轻信幻觉、方向错了硬纠、没验收就合并、贴了密钥。它们只违反三条：没说清、没守两道闸门、上下文和数据没管好。
- 五步急救：先中断、说清现状、回滚到上个好状态、开新对话重来、诊断。核心是回滚，这正是“先存起点、切分支再动手”的价值。
- 最大的误区是出了岔子不肯回滚。具体的回滚命令见第26章。

到这里，第四部分就告一段落：你有了通用工作流、两个工具的上手方法，以及出岔子时的急救办法。下一部分开始真正做项目。

## 小测验

> 共6题，涵盖概念、误区、情景、操作四类。先自己想，再看引用块里的答案解析。

1. **[基础·概念题]** 本章对“出岔子”的基本态度是？ <!-- quiz: q01 revision: 3 -->
   - A. 出岔子多半是提示词没写好，写好就能避免
   - B. 出岔子是常态，目标是认得出、救得回来
   - C. 出岔子说明这个工具不行，应该换一个用
   - D. 只要用得足够熟练，就基本不会再出岔子
   > **答案B。** 出岔子源于编程智能体“会犯错 + 会动手”的本性（第23、24章）。写好提示词能减少一部分（A），换工具（C）或更熟练（D）也一样，都做不到不出岔子。成熟的用法是**会救**：认得出八种常见失误、用得了五步急救。

2. **[基础·概念题]** 五步急救清单的正确顺序是？ <!-- quiz: q02 revision: 2 -->
   - A. 回滚 → 中断 → 开新对话 → 说清现状 → 诊断
   - B. 中断 → 开新对话 → 回滚 → 诊断 → 说清现状
   - C. 中断 → 说清现状 → 回滚 → 开新对话 → 诊断
   - D. 说清现状 → 诊断 → 中断 → 回滚 → 开新对话
   > **答案C。** 顺序很重要：**先停损（中断）、再盘点（说清现状）、回到干净处（回滚）、换张干净桌子（开新对话）、最后想清为什么（诊断）。** 不先中断（A、D），它会在你盘点时继续改；跳过盘点直接回滚（B），容易退错位置。

3. **[进阶·误区题]** “它跑偏了，我揪着在原方案上一句句纠正就好”——为什么往往越纠越糟？ <!-- quiz: q03 revision: 3 -->
   - A. 纠正多了它就会变谨慎，多纠正几次总能改对
   - B. 问题在于纠正太慢，换个更强的模型就好
   - C. 只要每次说得更详细，就能把它拉回正轨
   - D. 错误尝试塞满了上下文，它被旧错误带着走
   > **答案D。** 这是第6条“方向错了还硬纠”，病根在第13章那张被塞满的“桌面”。说得更详细（C）或换模型（B），旧的错误仍堆在上下文里。**回到干净状态、开个带着教训的新对话**，几乎总比在乱局里硬纠快，这也是急救清单③④步。

4. **[进阶·误区题]** “回滚就等于失败、等于认输”——这个想法错在哪？ <!-- quiz: q04 revision: 3 -->
   - A. 没错，回滚说明之前做的全都白费了
   - B. 回滚是安全网，往往是回到正轨最快的路
   - C. 回滚会删掉整个项目，只能最后才用
   - D. 回滚只适合新手，熟练了以后就该原地修好
   > **答案B。** “先存起点、切Git分支再动手”（第26章）铺垫的就是这一刻。回滚只退这次跑偏的改动，之前提交过的成果都还在（A、C）。新手最常见的错恰恰是**死不回滚、在一团乱上硬撑**（D），结果越来越糟。

5. **[基础·情景题]** 你正盯着它做事，突然发现它要去删一个你觉得很重要的文件。这一刻最该做的是？ <!-- quiz: q05 revision: 3 -->
   - A. 先不批准，看清它想做什么，不清楚就问
   - B. 先批准，反正以后可以用Git把它找回来
   - C. 让它先删掉，删完再看diff判断对不对
   - D. 关掉整个工具，从头开始重做这个任务
   > **答案A。** 这同时踩中“不看diff连点同意”（第3条）和急救第①步“先中断”。**许可前先看清、看不懂别放行**（第25、26章）。B、C都假定删了也能找回，但从没提交过的文件Git里没有存档；直接关掉工具（D）又会丢掉弄清情况的机会。

6. **[基础·操作/观察题]** 不必真装工具：回看本章八种常见失误，**对号入座**——你过去用AI（哪怕只是聊天）时，最常犯哪两三条？再把对应的“对策”抄下来，贴在你以后会看到的地方。 <!-- quiz: q06 revision: 3 -->
   > **该观察到：** 多数人会发现自己反复犯同样的一两条（很常见的是“会话不切换”和“轻信幻觉”）。这八条其实只违反三条原则——**没说清、没守两道闸、上下文/数据没管好**；盯住你自己的高频项、从源头堵住，比记全八条更有用。具体怎么回滚，基本命令见第26章“Git最小起步”；工具怎么操作，见第28、29章和附录C。
