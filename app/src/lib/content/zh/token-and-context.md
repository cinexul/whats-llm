很多人用AI时都遇到过这些“怪事”：聊着聊着它就忘了开头说的事；贴一篇长文章进去，它说“太长了”；明明问得差不多，这个月的额度却用得飞快。

这些看起来不相干的现象，背后其实是同一件事——**AI看文字的方式，和我们不一样**。它不是一个字一个字地读，也不是把整段对话“记”在脑子里。搞懂这一章的两个词，**token（令牌）**和**上下文窗口（context window）**，上面那些怪事就全说得通了。这也是整本书里最“值回票价”的一章之一：理解它，你对AI的很多操作会突然“开窍”。

## 一、Token：AI切分文字的“颗粒”

我们读“请帮我写封邮件”，看到的是7个字。模型看到的不是7个字，而是被切成的几块**token**：

```text
输入：  请帮我写封邮件
token： 请 / 帮 / 我 / 写 / 封 / 邮件      （切分只是示意）
```

token是模型表示文本时使用的**单位**，不一定等于一个字或词。**分词器（tokenizer）**按为模型准备的编码与词表切分文本，并不是每次聊天时临时发明一套规则。

- 一个token可能是词、词的一部分、一个字，或一个字符编码的部分。标点、空格与换行也计入token，有时会与相邻文字合在同一个token中。
- **不同模型可能使用不同分词器，也可能共用同一个。** 数量取决于编码与文本，不能假定字数、词数、语言和模型之间有固定比例。

> **为什么模型要这么切？** 因为如果按“字母”切，序列太长、太碎，模型抓不住意义；如果按“整词”切，世界上的词又太多、还层出不穷（新词、拼错的词、外语词）。token是两者之间的折中：**既不太碎，又能拼出任何文字**，包括它没见过的词。你不用记住具体怎么切——只要知道“模型眼里的长度是按token算的，和你数的字数不完全一样”就够了。

> **速算专栏：一段文字大概多少token？**
> 建立一个**量级感**就够用：一段几百字的短文，通常是几百到一千多个token。想要更细的经验——常见英文大约“4个字符 ≈ 1个token”，中文常常“1个字 ≈ 1~2个token”。
> 但这些都是**粗略经验，不是铁律**：到底多少token，取决于用的是**哪个模型的分词器**，还受标点、空格、数字、夹杂的代码影响。过去常说“英文比中文省token”，但在新一些的分词器上这个差距已经小了很多，不能当定律。**要精确，就用对应产品官方的token计数工具（以官方文档为准）。**

## 二、上下文窗口：模型的“工作台”

知道了token，第二个词就好懂了。

**上下文窗口**限制一次模型请求可使用的token。可以把它看成输入上下文加上生成回答所需的空间；具体计数与单独的输入、输出上限依模型而定。系统指令、工具定义与结果，以及推理模型在作答前生成的“思考”token（推理token，第8章）也占用相应预算，要给回答留出余量。

打个比方：上下文窗口就像一张**办公桌**。你要处理一件事，得把相关的资料都摊在桌面上——你说的话、它之前的回答、你贴进来的文档、给它的指示，**全都要占桌面**。桌子有大有小，但再大也有边。

```text
这次对话桌面上摊着的东西，全都算进上下文窗口：
┌─────────────────────────────────────┐
│  你给的指示（"请用口语风格"）         │
│  你贴进来的资料（那篇 5000 字的文章）  │
│  你历次提的问题                       │
│  它历次给的回答                       │
└─────────────────────────────────────┘   ← 加起来不能超过窗口上限
```

> **要点：** 桌面上的东西**不只是你打的字**。你贴进去的长文、它回复的长篇大论，才是占地方的大头。很多人盯着自己那一行短短的问题，纳闷“我没说几句啊”，却忘了刚才贴进来的10页PDF和它洋洋洒洒的2000字回答，早把桌子铺满了。

不同产品、不同模型的桌子大小不一样，而且一直在变大，所以**本书不写具体数字**（写了也很快过时，以官方文档为准）。你只需要建立“桌面有限”这个直觉。

## 三、会话上下文与训练知识是两回事

这是初学者最容易误会的地方，单独拿出来讲。

模型可以利用之前的对话，但**通常聊天不会把每段对话写入训练好的参数**。服务是否保存聊天记录、记忆或日志，是另外的产品与隐私问题。

软件会为下一次回答提供**选定的会话状态**。简单实现会发送全部消息历史；其他产品可能在服务器保存状态、复用缓存计算、选取相关片段或提供摘要。下图只表示完整历史的简单实现，并不要求每轮原封不动重发一切。

```text
第 1 轮：       [你的问题A]                         → 回答a
第 2 轮：    [问题A + 回答a + 你的问题B]             → 回答b
第 3 轮： [问题A + 回答a + 问题B + 回答b + 问题C]    → 回答c
            └────────── 示意：使用完整历史的简单实现 ──────────┘
```

“记得前面的对话”，表示相关信息在当前上下文中，或由产品功能重新提供。接近上限时，产品可能**摘要、裁剪、检索相关片段，或者拒绝超长请求**。细节可能丢失，但“总是自动挤掉最早内容”不是通用规则。

> **误解vs实际：** “昨天说过名字，新对话就一定记得。”只有产品通过历史、保存的记忆、项目资料或个性化设置提供了这条信息，模型才可能用到。新对话仍有系统指令，也可能带入这些上下文，并不一定是空桌面。检查启用的功能，并重新说明关键要求。

对于**在线服务**，提交的资料会发送到该服务处理。上下文裁剪不表示服务已删除保存的副本；保留期限与训练用途是另外的问题（第37章）。本地处理的数据路径不同。

### 那产品里的“项目”和“记忆”功能又是什么？

你可能会立刻反问：可我明明见过一些产品能“记住”我的偏好、记住整个项目啊？截至2026年10月，Claude、ChatGPT等不少产品都提供**项目**和**记忆**一类的功能：项目让你把资料和要求放在一起反复用，记忆则把你的偏好和聊过的要点存下来。写代码的工具也常有项目说明文件，账号里有个性化设置，公司还可能接入内部知识库……这和“模型没有记忆”矛盾吗？

**不矛盾。** 关键是分清两层：

| | 模型本体 | 产品层的“记忆” |
| --- | --- | --- |
| 是什么 | 结合当前上下文工作的已训练参数 | 保存并提供相关信息的产品功能 |
| 记不记得 | 通常推理不会把聊天写入参数 | 可能保存历史、偏好或项目资料 |
| 怎么做到的 | 使用本次请求可用的上下文 | 按相关性提供选定信息，不一定每轮带入所有已存内容 |

也就是说，记住你的偏好通常表示**产品提供了相关的已存信息**，而不是聊天重新训练了模型。这与第2章介绍的训练数据记忆是不同的概念。

> **要点：** 各家的项目、记忆功能作用范围不同。有的产品会从聊天里**自动提取**要记的内容，而且可能默认开启；反过来，也不是每次回答都会用上所有已存信息。不想被记住的内容，可以用临时对话（有的产品叫无痕对话），或者先关掉记忆再聊；隔一阵子去设置里看看存了什么，过时的、不对的删掉。具体会保存、使用、分享哪些内容，以及怎么删除，以官方文档为准（第10、13章）。

## 四、为什么长对话可能跟丢重点？

即使没达到上下文上限，长对话也**可能更难跟进**。长度本身不决定质量：有用的上下文能改善回答，无关或矛盾的材料则可能造成干扰。下面是三种可用“桌面”类比理解的问题：

| 原因 | 桌面比喻 | 具体表现 |
| --- | --- | --- |
| 重点被淹没 | 桌上资料太多，真正重要的那张纸被压在底下 | 你早先定的关键要求，它后来“看不见”了 |
| 矛盾在堆积 | 试错过程中产生的旧方案、错信息还摊在桌上 | 它被自己之前的错误带着走，越绕越偏 |
| 摘要丢细节 | 桌子快满时，旧资料被“压缩成便签”，细节没了 | 早期说过的具体数字、约定，被模糊化 |

> **实际会怎么遇到：** 一个典型场景——你和它来回打磨一篇稿子，前10轮挺好，越往后它越“轴”，开始无视你的新要求、翻炒早就否决过的写法。这不是它“累了”，是桌面被这一长串试错塞满了，**噪音盖过了信号**。

## 五、token还决定了“费用”和“能塞多少”

最后一件实用的事：**token是计量单位**。

- 许多**文本API**按输入与输出token计量，二者费率可能不同，并可能有缓存折扣和工具费用。订阅额度也可能按消息、工具、计算量、所选模型等限制，并不普遍等于可见的token余额。
- **上下文上限**按token衡量，但产品还可能有文件大小、页数或上传限制。文档也可能按需检索片段，而非全文进入上下文。

所以会出现这种事：你觉得“我就问了个小问题”，但因为前面贴了一大段资料、又让它生成了长长的回答，**token蹭蹭涨，额度掉得飞快**。第38章会专门讲怎么“省着用”，这里先记住一句话——

> **要点：** **保留相关资料，并给回答留空间。** 更长的输入可能增加计算、费用与干扰，但有用上下文也能提高准确率，缓存与套餐规则还会改变实际成本。桌面更满不等于一定更差。

## 六、常见误解，集中纠正

| 误解 | 实际 |
| --- | --- |
| token就是一个字 | token是模型的切分单位，可能是一个词、半个词或一个字，和“字数”不完全对应 |
| 它一定记得以前的所有聊天 | 应用选择提供哪些历史或记忆；通常推理不会把聊天写入训练参数 |
| 我这次只打了一行短问题，没花多少 | 前面贴的长文、带入的历史、它回的长答，才是占token的大头 |
| 上下文窗口越大越没烦恼 | 窗口更大能放更多，但仍需考虑相关性、回答余量、检索与实际费用 |
| 忘事一定是故障 | 信息未被带入或被摘要只是可能原因；模型也会忽略仍在上下文中的内容 |

## 小结

- **token**是分词器表示文本的单位。准确数量应使用对应编码或官方计数工具；订阅额度不一定是token余额。
- **上下文窗口**是模型这次能同时摊在“桌面”上的token上限——你说的、它说的、你贴的资料，全都占桌面。
- **会话状态**由应用管理。完整历史、服务端状态、相关片段与摘要都是提供上下文的方法，并不等于重新训练参数。
- 长对话可能因重点被淹没、指令矛盾、摘要遗漏而跟丢信息；有用的上下文也能改善回答。
- 保留**相关上下文**，预留输出空间。查看实际用量和价格，不要只凭长度判断准确率、速度或费用（第13、38章）。

1. **[基础·概念题]** 下面哪一句最准确？ <!-- quiz: q01 revision: 1 -->
   - A. token就是一个汉字或一个字母，数一数字数就能得出token数
   - B. token就是一个完整的句子，模型每次读进一整句再整体理解
   - C. token是模型切分文字的单位，可能是一个词、半个词或一个字
   - D. token是模型用来记住你的单位，记下的token越多越了解你
   > **答案C。** 分词器把文字切成的单位，不一定和字、词一一对应，具体数量取决于编码和文本本身。A是最常见的误解：字数和token数只有大致关系，没有固定比例。B把单位想得太大了，一句话通常会被切成好几个token。D把文字的切分单位和产品的“记忆”功能混在了一起。

2. **[基础·概念题]** “上下文窗口”指的是？ <!-- quiz: q02 revision: 1 -->
   - A. 模型一次请求能处理的token上限，指令、资料和回答都算
   - B. 聊天软件里输入框的大小，框越大一次能打进去的字越多
   - C. 模型能把你记住多少天，超过这个期限后就会自动忘掉
   - D. 模型训练时读过的资料总量，窗口越大它知道的就越多
   > **答案A。** 窗口限制的是一次请求里能用的token：系统指令、带入的历史和资料、工具内容，以及要生成的回答，都要放在里面；具体的输入、输出和推理token规则要看模型说明。B把它理解成了界面上的输入框。C把它当成了记忆期限，其实模型本身不会跨对话记住你。D混淆了窗口和训练数据：窗口大小和模型“知道多少”没有直接关系。

3. **[基础·误区题]** “我昨天告诉过它我的名字，今天它应该还记得”——这个想法错在哪？ <!-- quiz: q03 revision: 1 -->
   - A. 说得对，模型会把每段聊天写进参数，所以会一直记得
   - B. 模型其实记得，只是出于隐私保护故意装作不认识你
   - C. 只要是同一个账号，所有历史对话都会自动带进新对话
   - D. 只有产品把保存的信息带进新对话，模型才可能用上它
   > **答案D。** 通常推理不会把你的名字写进训练参数；但产品可以通过保存的记忆、项目资料或个性化设置，在新对话里重新提供这条信息。A正是要纠正的误解。B把它想成了会“装”的人。C说过头了：产品带入哪些内容各不相同，不会默认把所有历史都塞进来。应查看已启用的记忆和项目功能，并重新说明重要要求。

4. **[进阶·误区题]** “我这次只打了一行短问题，所以这次没占多少token”——哪里不对？ <!-- quiz: q04 revision: 1 -->
   - A. 说得对，token只按你这一次亲手打进去的字来计算
   - B. 前面贴的资料、带入的历史和它的长回答，往往都要算
   - C. 只有它的回答才算token，你的输入再长都不会计入用量
   - D. 没错，因为每一轮对话开始前，窗口都会被自动清空一次
   > **答案B。** 很多人只盯着自己打的那一行，忘了前面贴进来的10页PDF、随每轮带入的历史，以及它回的2000字长答，才是占token的大头。A正是题目里的误解。C说反了一半：输入和输出通常都计入用量，只是费率可能不同。D不对：在同一个对话里，产品通常会把相关历史继续带进来，并不会每轮清空。

5. **[基础·情景题]** 你和AI聊了很久，它开始答非所问、忘记前面说的设定。最该先做什么？ <!-- quiz: q05 revision: 1 -->
   - A. 把同一个问题原样多问几遍，总有一次它会答对的
   - B. 继续在原来的对话里追问，聊得越久它越了解情况
   - C. 开个新对话，把还需要的目标、要求和事实重新交代
   - D. 换一个上下文窗口更大的模型，问题就一定能够解决
   > **答案C。** 长对话里可能有信息遗漏、摘要损失、前后矛盾或重点被淹没。把核对过的目标、要求和必要事实带进新对话，是一种有效的重整；但它不能证明窗口已满，也不保证答案正确。A只是重复，没改变桌面上的内容。B容易让噪音继续堆积。D窗口更大能放更多，但重点被淹没、信息矛盾的问题不会自动消失。

6. **[基础·操作/观察题]** 选一段公开短文和它的译文，用网页版的官方token计数工具（例如OpenAI的[Tokenizer页面](https://platform.openai.com/tokenizer)，粘贴文字就能看到切分结果和token数；它只反映OpenAI模型的切分方式，截至2026年10月仍可使用，以官方页面为准），或者你所用产品、API后台显示的用量，分别记录所用模型、字符数和token数。再加入一小段代码，重复比较。会写代码的话，也可以用[tiktoken](https://github.com/openai/tiktoken)在本地计数。 <!-- quiz: q06 revision: 1 -->
