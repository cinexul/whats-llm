第23章说了编程智能体是什么：会自己读项目、改文件、跑命令的Agent。这一章讲怎么带着它做事。不管用Claude Code还是Codex，顺利的任务几乎都走同一个循环：调查 → 计划 → 动手 → 验收。学会这套顺序，你就清楚什么时候放手让它做，什么时候必须停下来看一眼。

这一章同样不要求你会写代码。安装和具体命令放在第28、29章。

## 一、先回顾：它和网页聊天差在哪

| | 网页/App聊天 | 编程智能体 |
| --- | --- | --- |
| 怎么对待代码 | 给你一段文字，你自己复制去用 | 直接改你项目里的文件 |
| 知道多少 | 只知道你贴进去的内容 | 自己探索整个项目来了解现状 |
| 推进方式 | 你问一句、它答一句 | 朝目标自己连走好几步 |
| 出错的后果 | 顶多答得不对，不采用就好 | 它真的动了你的文件，所以要能回滚 |

最后一行最要紧。因为它真的会动你的东西，“在能反悔的环境里用它”是前提，不是讲究。

第23章那个比喻在这里最好用：它是一个很能干、手很快、但第一天上班的新同事。体力活交给它，又快又多；可它不了解你的规矩，也不知道哪些地方碰不得（第28章讲怎样把规矩写给它），还会自信地犯错（第9章的幻觉）。所以你是带它的人：派活和验收是你的事，最后署名的也是你。

## 二、核心工作流：调查 → 计划 → 动手 → 验收

下图是这个循环。四步里，调查和动手主要由它做；计划和验收是你把守的两道闸门：计划你点头了它才动手，验收你通过了改动才合并。验收没通过，就回到调查或计划，而不是在原地硬改。

为什么一定要有这两道闸门？因为编程智能体会犯错，又能动手。两条同时成立，动手前看计划、动手后验收就省不得；守住这两道闸门，剩下的体力活才可以放心交给它。

![工作循环示意图：调查、计划、动手、验收四步围成一圈，每步下面写着人在这一步做什么；计划和验收两步由人把关；验收没通过时箭头回到调查或计划，通过后提交并开始下一小步](/figures/zh/work-loop.svg)

### ① 调查：它读项目，你扫一眼

先别急着让它改。让它先找到相关的代码、说明现在是怎么实现的，你确认它没找错地方。可以这样说：

> “先别动手，只调查：要给页面加一个搜索框，涉及哪些文件？现在是怎么做的？”

### ② 计划：它出方案，你批准

让它把“打算怎么改”写成计划：动哪些文件、加不加新东西、分几步。你读完、点头了，它才开始动手。这一步只花几十秒，却能挡掉大部分“跑偏了半小时才发现”的返工。截至2026年10月，Claude Code和Codex都有专门的计划模式，输入`/plan`就能进入；没有这类模式的工具，也可以直接说“先别动手，只给我计划”（第27章细讲）。

### ③ 动手：它改文件，你随时可以叫停

批准后它开始改。哪些操作要逐次确认、哪些在授权范围内自动执行，取决于工具和权限设置（第26章）；没有弹窗不等于没有风险。删除、发布、对外发送这类操作，要按事先约定的规则处理。觉得它走歪了，就打断它，把话说清楚再让它继续。

### ④ 验收：你检查，合格才合并

这是你最重要的一步，第25章专门讲。简单说就是三个问题：它改了什么（看diff，让它用大白话解释）？真的做到了、没弄坏别的吗（按事先写好的验收步骤试一遍，加上相关测试）？出了问题代价多大、能不能退回？你不需要读懂每一行代码，但这三个问题答不上来，就先别合并。

## 三、第一次跑起来，该期待什么

1. 先准备好能反悔的环境。它在你本地项目上动手时，项目要用Git管理，先提交一个起点，再切一个新分支让它动手（还没用过Git的话，先看第26章“Git最小起步”）。分支本身不是备份：Git只恢复提交过的版本，撤不回邮件、部署或外部数据的修改。网页或云端入口有各自的隔离和恢复方式，要另外查清（第26章）。
2. 它会先“读上一阵”。浏览项目需要时间，别以为它卡住了。
3. 看清确认框在问什么。有些操作会请你确认，有些在已授权的范围内自动执行。
4. 它会犯错、会跑偏，这很正常。这时别在一团乱里硬纠。最干脆的办法是：回滚到干净状态，开一个新对话，把刚才碰到的问题当作前提重新交代（第13、30章）。
5. 涉及很新的技术，在话里说清版本，或者把最新资料贴给它（第9章的知识截止）。
6. 别把密钥、密码、真实的个人信息贴进对话或写进代码（第37章）。费用方面，订阅套餐的额度和API按量计费是两回事，第38章细讲。

新手最常见的失误，是让它一口气把一个大功能全做完。改动一大，验收起来就很吃力，出了问题也难回滚。更快的做法是拆小：做一小块、验收一小块、提交一次，再做下一块（第27章）。

## 四、Claude Code与Codex：同在哪、不同在哪

| | 相同（稳定） | 不同（会变，见第28、29章） |
| --- | --- | --- |
| 定位 | 都是会在你项目上动手的编程智能体 | 出品方、背后的模型、提供的入口不同 |
| 工作流 | 都适用“调查 → 计划 → 动手 → 验收” | 具体命令、快捷键、界面不同 |
| 安全 | 都该配合权限设置和可回滚的环境 | 默认权限和设置方式不同 |
| 上手 | 都先在Git分支里小步试 | 安装和登录方式不同 |

这套工作流换哪个工具都管用，因为它来自“怎么带一个会犯错、又能动手的助手”，而不是某个产品的按钮。

## 五、常见误解

| 误解 | 实际 |
| --- | --- |
| 它是AI，写的代码应该对，直接合并 | 它会自信地写错；按第25章验收，答不上验收三问就别合并 |
| 让它一次把大功能全做完最省事 | 大改动难验收、难回滚；拆小、小步验收反而最快 |
| 它记得我整个项目和昨天的对话 | 模型本身没有跨对话的记忆；CLAUDE.md这类“项目记忆”是产品每次把保存的文字重新放进上下文（第9、28章） |
| 我不会编程就没法用 | 不用会写每一行；要会派活，再用具体的检查验收 |
| 它跑偏了就追着它一直改 | 回滚、开新对话重来；在乱掉的上下文里硬纠往往更糟 |

## 小结

- Claude Code和Codex都是会在你项目里动手的编程智能体；在终端、编辑器、桌面应用还是网页上用，取决于产品。
- 和网页聊天的根本区别：它直接改文件、自己探索项目、连走好几步，所以要在能回滚的环境里用。
- 核心工作流是调查 → 计划 → 动手 → 验收。你把守两道闸门：批准计划，验收改动；验收没过就回到调查或计划。
- 第一次用：先提交起点、切Git分支，任务拆小，跑偏就回滚重来，密钥绝不外贴。
- 这套工作流与具体工具无关，学一次，换工具也能用。

下一章（第25章）细讲工作流里最该练熟的一步：看diff、跑测试、回滚和验收。

## 小测验

> 共6题，涵盖概念、误区、情景、操作四类。先自己想，再看引用块里的答案解析。

1. **[基础·概念题]** 编程智能体（如Claude Code / Codex）和网页聊天AI最根本的区别是？ <!-- quiz: q01 revision: 2 -->
   - A. 它用的模型更强大，所以回答更准确、也更少出错
   - B. 它能记住你的整个项目，换了对话也不会忘
   - C. 它只回答编程问题，其他领域的问题都不管
   - D. 它能直接读写项目文件、运行命令，不只给文字
   > **答案D。** 聊天AI是“你来回复制粘贴”；编程智能体是“它直接在你的项目里动手”。这正是它高效、也需要“许可机制”看着的原因。A、C把区别当成了模型强弱或话题范围；B混淆了模型和产品：模型本体没有跨对话记忆，所谓“项目记忆”是产品每次把文件重新放进上下文。

2. **[基础·概念题]** “调查 → 计划 → 动手 → 验收”这个循环里，人最关键的工作在哪一步？ <!-- quiz: q02 revision: 2 -->
   - A. 调查：亲自找出相关文件，再交给它去改
   - B. 动手：盯着它的每一处修改，一条条点确认通过
   - C. 批准计划，并在动手后看diff、跑测试
   - D. 写清目标就够了，后面几步都交给它自己
   > **答案C。** 让AI干活，人守两道闸：**动手前批准计划、动手后验收变更**。调查和动手这类体力活交给它（A、B），你只需扫一眼、随时能叫停；D则把两道闸都放掉了。

3. **[基础·误区题]** “它是AI，写的代码应该是对的，直接合并就好”——错在哪？ <!-- quiz: q03 revision: 3 -->
   - A. 它会自信地写错，没验收过的改动不该合并
   - B. 没有错，只要代码能运行起来，就说明它是对的
   - C. 错在没让它自己确认一遍“确实没有问题”
   - D. 错在没有全部重写，它写的代码总要人来改
   > **答案A。** 幻觉（第9章）在写代码时照样发生：编造不存在的函数、用错版本的写法。能运行不等于做对（B）；让它自己打包票也不算验证（C）；全部重写又走到了另一个极端（D）。diff要看、检查要跑，说不清的地方先让它讲清楚。

4. **[进阶·误区题]** “让它一次把整个大功能全做完，最省事”——为什么往往更费事？ <!-- quiz: q04 revision: 2 -->
   - A. 其实不会，大任务一次说清，反而省了来回沟通
   - B. 因为它一次只能改一个文件，大功能要分很多次
   - C. 改动越大越难逐行验收，出了错也难定位和回滚
   - D. 唯一的问题是大任务用的额度多，其他都一模一样
   > **答案C。** 大改动等于大盲区：diff看不完，错误混在一大坨改动里，回滚也不干净。把任务拆小、先看计划、小步验收，反而最快（第27章）。B不对，它能一次改很多文件，问题恰恰在这里；D只看到了额度，没看到验收和回滚的难处。

5. **[基础·情景题]** 你让它改代码，它跑偏了，越改越乱。最佳止损动作是？ <!-- quiz: q05 revision: 3 -->
   - A. 在同一个对话里一句句纠正，直到它改对为止
   - B. 回滚到干净状态，开新对话，说明碰到的问题
   - C. 让它在现有改动上再改一版，把错误覆盖掉
   - D. 删掉整个项目，从头让它重新生成一遍代码
   > **答案B。** 在乱掉的上下文里硬纠（A、C），往往越纠越歪。**回滚 + 重开一个带着教训的干净对话**，几乎总是更快（第13、30章）。提前提交或备份现有工作，才有可恢复的起点（Git的基本用法见第26章）；回滚时只退这次任务的修改，删项目（D）会连好的部分一起丢掉。Git也不能撤销外部操作。

6. **[进阶·操作/观察题]** 不必真装工具：找一段代码改动（或第25章的diff示例），用第25章的验收三问过一遍：它改了什么？真的做到了、没弄坏别的吗？出了问题代价多大、能不能退回？第一问答不上来时，就该回去让它用大白话解释。 <!-- quiz: q06 revision: 3 -->
   > **该观察到：** 验收不神秘，就是这三问，而且不要求你读懂每一行代码：第一问靠它的大白话解释加上你对照diff，第二问靠事先写好的验收步骤和测试，第三问看风险和退路。养成“三问答不上来就不合并”的习惯，比会任何命令都重要。安装和具体命令见第28、29章与附录C。
