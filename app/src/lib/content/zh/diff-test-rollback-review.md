〔本章涉及具体产品的命令、界面、按钮之处，都会随版本更新而变化，一律**以官方文档为准**。本章只讲**共通、稳定**的把关动作——这部分不会过时。〕

如果整个第四部分你只来得及学会一章，那就是这一章。

第23章我们说定了一条铁律：**它会动手、也会犯错，所以“看不懂、没验证的东西，不要放行”。** 可问题来了——**一个不会写代码的人，怎么“验证”它写的代码？**

好消息是：**验收不等于看懂每一行代码。** 你需要的，是四件再朴素不过的事——**看懂改动（diff）、运行相关检查、知道哪些改动能恢复、怎么恢复（回滚）、用三个问题做最终验收**。这四件事，外行都学得会，而且学会之后，你就真正握住了“让AI替你干活”的方向盘。

我们一件一件来。

## 一、看懂diff：一场“找不同”游戏

它改完代码，第一件事不是问它“好了吗”，而是**让它把改动以diff（差异／差分）的形式给你看**。

**diff，就是“改动前后的对比”。** 别被这个词唬住，它的本质特别简单——就像两张几乎一样的图片让你玩“找不同”，diff帮你把“不同的地方”**直接圈出来**，你不用拿原稿一行行比对。

它长这样（这是**通用示意**，具体颜色、符号在不同工具里略有差别，**以官方文档为准**）：

```diff
  function greet(name) {
-   return "你好，" + name;
+   return "你好，" + name + "！欢迎回来";
  }
```

读法只有三条，记住就够用：

- **绿色、前面带`+`的行 ＝ 新加的**（上面那行“加了欢迎语”）。
- **红色、前面带`-`的行 ＝ 删掉的**（上面那行“原来的写法被替换了”）。
- **没颜色、没符号的行 ＝ 没动**，只是放在那里给你看上下文。

就这么简单。一次改动，可能涉及好几个文件、好几处增删，diff会**一处一处列清楚**：“在哪个文件、加了哪几行、删了哪几行。”你的任务不是看懂每行代码的语法，而是回答两个外行也答得上来的问题：

1. **它动的地方，对不对？** 你让它“改首页的标题颜色”，结果diff里它动了“用户登录”那段代码——这就**明显不对**，哪怕你看不懂那段代码，也知道它跑偏了。
2. **它动的范围，是不是大得离谱？** 你只让它改一个小标题，diff却显示它改了十几个文件、几百行——**警铃该响了**。要么它误解了任务，要么它“顺手”动了一堆不该动的地方。

> **要点：** **看diff，看的是“动了什么、动了多大”，不是“每行代码什么意思”。** 这就像你不是厨师，但你能看出“我点的是一份沙拉，端上来的怎么是一锅红烧肉”——**对不对、量对不对，外行完全判断得了。** 这正是diff这个工具最大的价值：它把“它到底改了什么”摊开给你看，让你不必信它一面之词。

## 二、跑测试：检查有没有引入回归问题

看懂了“它改了什么”，下一个要命的问题是：**它在添新功能的时候，会不会把原来好好的功能弄坏了？**

这在编程里太常见了，常见到有个专门的说法叫“按下葫芦浮起瓢”——你让它修A，它把A修好了，却不小心碰坏了B。**而B出问题的地方，可能根本不在你看的那段diff里**，光看diff发现不了。

这时候就轮到**测试**上场了。

**“测试”是一批预先写好的小检查，专门用来自动确认“这些功能还正常不正常”。** 你可以把它想成产品出厂前的**质检流水线**：每个产品过一遍传送带，机器自动检查“该亮的灯亮不亮、该转的轮转不转”，有一项不合格，**红灯立刻亮起**。

对你这个“带他的人”来说，操作朴素到不可思议：

- 改完之后，**让它运行与改动相关的检查**。措辞修改可能只需校对和链接检查；行为修改则要运行相关测试或手动验证。
- 看结果：**全部通过，只说明覆盖到的情况通过了**，不代表所有可能行为都正确。**失败要调查原因**：可能来自本次改动、已有问题或环境。在合并前解决，或明确说明原因与影响。

不会写测试，也可以使用测试结果。要问：**运行了哪些相关检查、哪些通过或失败、还有什么没测到？** 无关检查亮绿灯，不能证明这次修改正确。

> **误解vs实际：** 很多新手以为“它说改好了，那就是好了”。**实际上，“它觉得好了”和“经得起测试”是两回事。** 它可能真心以为自己改对了（它不是骗你，是它“自信地错了”，第9章的幻觉），测试则为覆盖到的情况提供独立证据。所以养成习惯：**改后运行相关检查、调查失败原因，并说清剩余的验证空白。**

一个补充：不是每个项目都有现成的测试。要是没有，至少做**最朴素的人工验证**——把改动影响的那个功能**亲手用一遍**，看它还正常不正常。哪怕只是“点开页面看看有没有崩”，也比什么都不验强。

## 三、回滚：先知道哪些东西能恢复

**回滚，就是把选定的改动恢复到已知的较早状态。** 它能帮助处理错误，但不保证一键抹掉所有后果。

**本地项目中，Git记录的是你主动保存的版本。** 较大修改前，先检查当前状态，通过合适的提交或备份保留已有工作。不要为了建检查点而把密钥提交进去。Git不是自动保存每一次编辑的相机。

**分支**是一条有名字的开发路线，创建它不会新建目录，也不会隔离运行中的进程。需要分开工作文件时，可以使用**单独的检出目录或Git worktree（工作树）**。工作树共享仓库历史，但有自己的工作目录；它仍不能替代沙箱。

Git可以恢复记录过的文件内容，或撤销已提交改动。它不会自动保护未跟踪或被忽略的文件、本地数据库，以及其他未保存的工作。丢弃任何修改前，先分清哪些属于当前任务，并保留无关工作。恢复也可能需要不止一步。

**云端工作区要查看明确提供的恢复能力。** 检查点、丢弃任务或重置工作区，可能只覆盖特定文件，并有保留期限。不要假定各个平台都有同样的撤销功能。

> **要点：** 回滚代码不会自动撤回消息、收回已经分享的数据、退还费用、恢复远端数据库或撤销部署。外部系统需要各自的恢复流程。动手前准备适当的备份和恢复方案；第26章会解释权限与工作区的边界。

## 四、验收三问：最后这一关，看不懂就别合并

看了diff、跑了测试、确认了能回滚——最后，把这一切收拢成一个**你随时能用、不用任何工具就能做**的动作：**验收三问**。

每次它说“做好了”，你就用这三个问题过一遍。**任何一个答不上来，就先别合并。**

1. **“它改了什么？”**——看着diff，你能不能说出“它动了哪几处、大概在干嘛”。说不清，就让它解释，或者它**改太多了**（拆小，见第27章）。
2. **“会不会弄坏别的？”**——哪些相关检查通过了，哪些失败了，还有什么没验证？合并前调查失败，解决问题或清楚说明原因与影响。没有合适测试时，亲手试用受影响的功能。
3. **“我能不能用一句话讲清这段在干嘛？”**——这是最关键的一问。试着对自己（或对一个外行）用**一句大白话**说“这段改动是干什么的”。**如果你说不出来，那就意味着你没看懂——看不懂的东西，绝不放行。**

第三问最容易被偷懒跳过，但它恰恰是**整套把关的灵魂**。说不上来，不丢人，正确做法是**回去问它**：“这段是干嘛的？为什么要这么改？” 让它解释到你能用一句话复述为止。它解释不清、或者越解释越可疑，那这段改动本身可能就有问题。

> **要点：** **“看不懂别合并”——这是这一章、也是整个第四部分的底线。** 它做完不等于做对（第23章）；diff让你看清它改了什么，测试帮你发现回归问题，回滚给你“反悔”的底气，而验收三问，是把这三样拧成一根你随手就能拉的安全绳。**记住：把关在你，不在它。**

## 五、把四件事串成一套动作

别把它们当四个孤立知识点，它们其实是一条顺下来的流水线，对应第24章那道“验收”闸门：

```text
它说"做好了"
     │
     ▼
①看 diff ──→ 它改了什么？动对地方没？范围正常吗？
     │
     ▼
②运行相关检查 ──→ 调查失败，解决或说明原因，并记录未测范围
     │
     ▼
③验收三问 ──→ 改了什么 / 会不会弄坏别的 / 能不能一句话讲清
     │
     ├── 三问都过 ──→ 合并，进入下一小步
     │
     └── 有一问卡住 ──→ 回去问清楚 / 让它改 / 不行就【回滚】重来
```

最后那条“回滚重来”特别重要：当它**越改越乱**，最干脆的不是在烂摊子里硬纠，而是**保留无关工作，把目标改动恢复到已知状态，再交代任务和刚才的问题；需要时新开对话**（第13、30章讲过这个止损思路）。**回滚不是失败，是你手里最好用的一张牌。**

## 六、常见误解，集中纠正

| 误解 | 实际 |
| --- | --- |
| 看diff得看懂每行代码，我不会 | 看diff看的是“动了什么、动多大、对不对地方”，外行就能判断；绿＝加、红＝删 |
| 它说“改好了”，那就是好了 | 用相关测试、手动操作或文档审阅核实结果；合并前调查失败并记录验证空白 |
| 不会写测试，就没法用结果 | 要问检查了什么、哪些通过或失败、还有什么没测到；测试通过也有覆盖范围 |
| 万一改坏了就没有办法 | Git和备份能恢复已记录内容；先确认覆盖范围。分支不是独立目录，外部影响需要单独恢复 |
| 没全看懂，但它语气很肯定，那就合并吧 | **看不懂就别合并**——验收三问第三问答不上来，回去问清楚，问不清就别放行 |
| 它跑偏了，我得在原地一行行纠正它 | 越改越乱时，**回滚 + 开新对话重来**往往最快（第13、30章） |

## 小结

- **diff（差异）＝ 改动前后的对比**，像玩“找不同”：**绿＝加、红＝删**。看的是“动了什么、动多大、对不对地方”，**不用看懂每行代码**。
- **测试验证它覆盖到的行为。** 运行相关检查、调查失败、说明空白；没有合适测试时，亲手验证受影响功能。
- **回滚恢复选定的已记录状态。** 先保存已有工作，需要时使用单独检出目录或工作树。查清云端恢复范围，未记录数据和外部影响另做安排。
- **验收三问**：①它改了什么？②会不会弄坏别的？③我能不能一句话讲清？——**任何一问答不上来，就先别合并。**
- 底线一句话：**“看不懂别合并。”** 把关永远在人这边（第23、39章）；越改越乱时，回滚重来好过原地硬纠（第13、30章）。

第26章继续解释沙箱边界、范围明确的授权、有效的审批节点，以及恢复的限度。

1. **[基础·概念题]** 在一份diff里，“前面带`+`的绿色行”代表什么？ <!-- quiz: q01 revision: 1 -->
   - A. 被删掉的行
   - B. 新加上去的行
   - C. 出错的行
   - D. 注释行
   > **答案B。**diff是“改动前后对比”：**绿＝加（`+`）、红＝删（`-`）**，没颜色的是没动、给你看上下文的。选A把加和删记反了——这是初学者最容易混的一点，记成“加号就是加上”就不会错。

2. **[基础·概念题]** “跑测试”主要是为了确认什么？ <!-- quiz: q02 revision: 1 -->
   - A. 代码写得好不好看
   - B. 这次改动有没有把原来好好的功能弄坏
   - C. AI的态度好不好
   - D. 项目能不能上线赚钱
   > **答案B。** 测试像出厂质检流水线，专门自动检查“原有功能还正不正常”。它能抓到那些**不在你眼前diff里**、光看改动发现不了的“按下葫芦浮起瓢”。要看运行了哪些相关情况，并调查失败原因；测试通过也不覆盖所有可能。

3. **[基础·误区题]** “它说‘改好了’，那肯定就是好了，直接合并”——错在哪？ <!-- quiz: q03 revision: 1 -->
   - A. 没错，它说好就是好
   - B. “它觉得好”和“经得起测试”是两回事；它可能自信地错了，要靠diff和测试来验
   - C. 它从不说“改好了”
   - D. 合并要先交钱
   > **答案B。** 它不是骗你，是会“自信地错”（第9章的幻觉）。相关测试能验证覆盖到的行为，但通过不证明所有情况都正确。盲信它的语气，正是新手最常见的翻车方式。

4. **[进阶·误区题]** “看diff得能看懂每一行代码，我一个外行根本做不到”——这个顾虑哪里多余了？ <!-- quiz: q04 revision: 1 -->
   - A. 不多余，看不懂代码就没法看diff
   - B. 看diff看的是“动了什么、动多大、对不对地方”，就像看出“我点的是沙拉怎么端来红烧肉”，外行完全判断得了
   - C. diff只有程序员能打开
   - D. 外行看diff会把项目弄坏
   > **答案B。** 验收不等于读懂每行语法。“它动对地方没、范围正不正常”，这种判断不需要编程功底。把“看diff”误当成“读懂全部代码”，会让你白白放弃这个最有用的把关工具。

5. **[基础·情景]** 想在本地代码改坏时有办法恢复，事先应该准备什么？ <!-- quiz: q05 revision: 1 -->
   - A. 只拍一张截图
   - B. 用Git或合适的备份保存起点，确认覆盖范围；需要分开工作文件时使用单独检出目录或工作树
   - C. 相信创建分支就备份了整台电脑
   - D. 相信回滚代码也会撤销数据库修改和邮件发送
   > **答案：B。**Git恢复记录过的内容；分支既不是所有文件的备份，也不会创建另一目录。未记录数据另行保护，保留无关工作，为外部影响准备恢复方案。云端检查点也有各自的范围和保留期限。

6. **[进阶·操作/观察题]** 找一份现成的代码改动（或本章的diff示例），不必看懂代码，只练“验收三问”：**它改了什么？会不会弄坏别的？我能不能用一句话讲清这段在干嘛？** 第三问答不上来时，你打算怎么办？ <!-- quiz: q06 revision: 1 -->
   > **该观察到：** 验收三问不神秘，外行就能做。第三问答不上来时，正确动作是**回去问它**“这段是干嘛的、为什么这么改”，让它解释到你能一句话复述为止——而**不是**因为它语气肯定就放行。养成“看不懂就别合并”的肌肉记忆，比会任何命令都值钱。具体工具的命令、界面**以官方文档为准**。
