如果第四部分你只来得及学会一章，就学这一章。

第23章说过：它会动手，也会犯错，做完不等于做对。那么一个不会写代码的人，怎么确认它写的代码对不对？

验收不等于读懂每一行代码。你要做的是几件朴素的事：看清它改了哪里（diff），用具体的检查确认它真的做到了、没弄坏别的，知道改坏了怎么退回，最后用三个问题收尾。这一章一件一件讲，并在第五节把本书对“要不要读懂代码”的立场说清楚。

## 一、看懂diff：一场“找不同”游戏

它改完代码，第一件事不是问它“好了吗”，而是让它把改动以diff的形式给你看。diff（差异）就是改动前后的对比。就像两张几乎一样的图片玩“找不同”，diff把不同的地方直接圈出来，你不用拿原稿一行行比对。

它大致长这样（不同工具的颜色和排版略有差别）：

```diff
  function greet(name) {
-   return "你好，" + name;
+   return "你好，" + name + "！欢迎回来";
  }
```

读法只有三条：

- 前面带`+`、通常显示为绿色的行：新加的。
- 前面带`-`、通常显示为红色的行：删掉的。
- 没有符号的行：没动，放在那里给你看上下文。

上面这处改动的意思是：原来只说“你好，某某”，现在后面多了“！欢迎回来”。一次改动可能涉及好几个文件、好几处增删，diff会按文件一处处列出来。你不用看懂每行的语法，先回答两个外行也答得上来的问题：

1. 动的地方对不对？你让它改首页标题的颜色，diff里它却动了“用户登录”那段代码。哪怕看不懂那段代码，你也知道它跑偏了。
2. 范围是不是大得离谱？你只要改一个小标题，diff却显示改了十几个文件、几百行。要么它误解了任务，要么它“顺手”动了不该动的地方。

这就像你不是厨师，也能看出“我点的是沙拉，端上来的怎么是红烧肉”。

看不懂的部分，让它讲给你听。可以这样问：

> “逐个文件用大白话告诉我：你改了什么、为什么改。再单独列出有风险的改动：会不会删除或覆盖数据、改权限或登录、联网发送内容、碰到密码或密钥、产生费用？你不确定的地方也标出来。”

把它的解释和diff对照着看。它说只改了标题，diff里却出现了登录相关的文件，就要追问。

## 二、跑测试和验收检查：确认做到了，也没弄坏别的

看清了它改了什么，接下来要问：它真的做到了吗？有没有在改A的时候碰坏了B？后一种情况在编程里太常见，叫回归（regression）：原来好好的功能，被新改动弄坏了。B出问题的地方可能根本不在diff里，光看diff发现不了。

测试（test）是一批预先写好的小检查，自动确认“这些功能还正常不正常”，像出厂前的质检流水线，有一项不合格就亮红灯。你不会写测试，也能用它的结果。改完让它运行与这次改动相关的测试，然后问三件事：跑了哪些检查？哪些通过、哪些失败？还有什么没测到？

读结果时注意两点。全部通过，只说明测到的情况没问题，不代表所有情况都对。有失败，要先查清原因：可能是这次改动造成的，也可能是原本就有的问题或环境问题。合并前解决它，或者明确写下原因和影响。

测试之外，你自己的验收检查同样重要，对不写代码的人来说更是主要手段。动手前就写下“怎样算做成了”，写成能照着操作的步骤：

> 打开首页，在搜索框输入“发票”，应该列出标题里带“发票”的文章；什么都不输就点搜索，不应该报错；把窗口缩到手机宽度，搜索框不会挡住标题。

改完照着亲手做一遍。项目没有现成测试时，这几步就是你的测试。措辞类的修改，校对文字、点一遍链接就够；行为类的修改，一定要实际用一遍。它说“我已经验证过了”不作数，你亲眼看到的结果才算。

## 三、回滚：先知道哪些能恢复

回滚，就是把选定的改动恢复到之前某个已知的状态。本地项目里，这件事通常靠Git。它保存的是你主动提交（commit）过的版本，不会自动记录每一次编辑，所以较大的修改前，先提交或备份一个起点。还没用过Git的话，安装和几条基本命令见第26章“Git最小起步”。

回滚有边界。Git不保护从没提交过的文件和本地数据库，也撤不回已经发出的邮件、公开发布的内容、扣掉的费用或远端数据库的修改。云端工作区的检查点也各有覆盖范围和保留期限。这些边界在第26章细讲；验收时用得上的规矩只有一条：说不清怎么撤销的操作，先别批准。

## 四、验收三问

看了diff、跑了检查、确认了退路，最后用三个问题收尾。每次它说“做好了”，就过一遍；有一个答不上来，就先别合并。

1. 它改了什么？让它用大白话逐个文件讲清楚，你对照diff确认地方和范围都对，并能用一句话复述“这次改动是做什么的”。
2. 真的做到了、没弄坏别的吗？照着事先写好的验收步骤亲手试过，相关检查通过了，失败的查清了原因，没测到的心里有数。
3. 出了问题代价多大、能不能退回？碰到钱、个人数据、密码或密钥、删除文件、对外发布的，有没有经过第二道审查？退路准备好了吗？

第一问答不上来时，回去问它：“这段是做什么用的？为什么要这样改？”让它解释到你能复述为止。它解释不清，或者越解释越可疑，这段改动本身可能就有问题。

## 五、要不要读懂代码：本书的立场

不会编程的人，不需要读懂每一行代码，也能对AI做的改动负起责任。前提是做到四件事：

1. 用具体的验收检查确认行为，而不是相信它说“完成了”（第二节）。
2. 让它用大白话解释diff，并主动点出有风险的地方（第一节）。
3. 凡是涉及钱、个人数据、密码或密钥、删除文件、对外发布的改动，找第二道审查：另开一个新会话，让智能体在不带之前对话的情况下专门审这份diff；或者请一个懂行的人看。同一个会话带着刚才的思路，容易替自己的方案辩护。
4. 退不回的不运行（第三节、第26章）。

> **要点：** 读懂每一行不是门槛。说不清它改了什么、没按验收步骤试过、高风险改动没人复查、出了事退不回，这四种情况出现任何一种，都不要合并。

后面的项目章节都按这个标准验收。比如做个人网站时（第31章），刷新浏览器看效果就是你的验收检查；一旦网站要公开上线，或者开始收集访客的信息，就进入了需要第二道审查的范围。

## 六、把几件事串成一套动作

这些动作对应第24章工作循环里的“验收”一步：

```text
它说"做好了"
     │
     ▼
①看diff，让它用大白话解释 ──→ 地方对吗？范围正常吗？有风险吗？
     │
     ▼
②按验收步骤试 + 跑相关检查 ──→ 失败查清原因，没测到的记下来
     │
     ▼
③验收三问 ──→ 改了什么 / 做到没、坏没坏 / 代价和退路
     │
     ├── 都过了 ──→ 合并、提交，进入下一小步
     │
     └── 卡住了 ──→ 问清楚 / 让它改 / 不行就回滚重来
```

越改越乱时，与其在一团乱里硬纠，不如保留无关的工作，把这次的改动恢复到上一个好状态，重新交代任务和刚才遇到的问题，需要时开一个新对话（第13、30章）。

## 七、常见误解

| 误解 | 实际 |
| --- | --- |
| 看diff就要看懂每行代码，我不会 | 先看动了哪里、动了多大；看不懂的让它用大白话讲，你对照diff核实 |
| 它说“改好了”，那就是好了 | 按事先写好的验收步骤亲手试，再看相关检查的结果 |
| 测试全过，就证明全对 | 只说明测到的情况没问题；还要问什么没测到 |
| 不会写测试，就没法验收 | 把“怎样算做成了”写成操作步骤，亲手照着做，就是你的测试 |
| 让同一个会话再检查一遍就够了 | 高风险改动要换新会话或请人审；同一个会话容易替自己辩护 |
| 改坏了，回滚就能全部恢复 | Git只恢复提交过的内容；邮件、发布、费用、远端数据撤不回（第26章） |

## 小结

- diff是改动前后的对比：`+`是加，`-`是删。先看动了哪里、动了多大；看不懂的让它用大白话解释，并点出风险。
- 测试验证它覆盖到的行为；事先写好的验收步骤，是不写代码的人最主要的检查手段。
- 回滚只能恢复记录过的状态；说不清怎么撤销的操作先别批准（第26章）。
- 验收三问：改了什么？做到没、坏没坏？代价多大、能不能退回？
- 本书的立场：不必读懂每一行，但要用具体检查确认行为，让它解释diff和风险，高风险改动找第二道审查，退不回的不运行。

第26章讲怎样让它动手又不失控：权限设置和可以回滚的环境。

## 小测验

> 共6题，涵盖概念、误区、情景、操作四类。先自己想，再看引用块里的答案解析。

1. **[基础·概念题]** 在一份diff里，“前面带`+`的绿色行”代表什么？ <!-- quiz: q01 revision: 2 -->
   - A. 被删掉的行，原来有、改完以后就没有了
   - B. 工具标出来、提醒你重点检查的出错行
   - C. 新加上去的行，改之前没有、改之后才有
   - D. 没有变动的行，只是放在那里给你看上下文
   > **答案C。** diff是“改动前后对比”：绿＝加（`+`）、红＝删（`-`），没颜色、没符号的是没动、给你看上下文的（D）。选A把加和删记反了，这是初学者最容易混的一点，记成“加号就是加上”就不会错。B把颜色当成了报错提示，diff本身不判断对错。

2. **[基础·概念题]** “跑测试”主要是为了确认什么？ <!-- quiz: q02 revision: 2 -->
   - A. 这次改动有没有弄坏原来正常的功能
   - B. 新写的代码是否规范、读起来顺不顺
   - C. AI有没有完全按照你批准的计划去改
   - D. 改完之后，所有可能的情况都一定正确
   > **答案A。** 测试像出厂质检流水线，专门自动检查“原有功能还正不正常”，能抓到那些不在你眼前diff里的“按下葫芦浮起瓢”。代码写得规不规范（B）、是否照计划改（C），要靠看diff和验收三问；测试通过也只说明覆盖到的情况没问题，不代表所有情况都对（D）。

3. **[基础·误区题]** “它说‘改好了’，那肯定就是好了，直接合并”——错在哪？ <!-- quiz: q03 revision: 2 -->
   - A. 没有错，它能检查自己的代码，它说好就一定好
   - B. 错在没抽查：随便点开一两处看看就够了
   - C. 错在没跑全部测试，测试全过就证明全对
   - D. 它可能自信地错了，要用diff和检查来验
   > **答案D。** 它不是骗你，是会“自信地错”（第9章的幻觉）。它自己的判断不能代替验证（A）；随手抽查一两处挡不住藏在别处的问题（B）；相关测试能验证覆盖到的行为，但通过也不证明所有情况都正确（C）。

4. **[进阶·误区题]** “看diff得能看懂每一行代码，我一个外行根本做不到”——这个顾虑哪里多余了？ <!-- quiz: q04 revision: 2 -->
   - A. 不多余，看不懂代码的话，就根本没办法看懂diff
   - B. 看diff主要看改了哪里、改了多少、地方对不对
   - C. 不用看diff，只要测试跑过了就能代替它
   - D. 只需数一数改了几个文件，具体内容不必看
   > **答案B。** 验收不等于读懂每行语法。“它动对地方没、范围正不正常”，就像看出“我点的是沙拉怎么端来红烧肉”，外行完全判断得了。测试抓不到“改错了地方”这类问题，所以不能代替看diff（C）；只数文件个数又太粗，看不出它动的是不是你要的那块（D）。

5. **[基础·情景]** 想在本地代码改坏时有办法恢复，事先应该准备什么？ <!-- quiz: q05 revision: 2 -->
   - A. 用Git提交或合适的备份存好起点，查清覆盖范围
   - B. 新建一个分支就够了，它会自动备份整个项目的文件夹
   - C. 截一张屏，改坏了就照着截图一处处手动改回去
   - D. 不必准备，回滚代码时数据库和邮件也会跟着恢复
   > **答案A。** Git恢复的是记录过的内容（基本命令见第26章“Git最小起步”）；分支既不是所有文件的备份，也不会另建一个目录（B）。截图记不下所有改动（C）；数据库、邮件这些外部影响需要各自的恢复方案（D）。需要分开工作文件时，可以用单独检出目录或工作树；云端检查点也有各自的范围和保留期限。

6. **[进阶·操作/观察题]** 找一份现成的代码改动（或本章的diff示例），不必看懂代码，练一遍“验收三问”：它改了什么？真的做到了、没弄坏别的吗？出了问题代价多大、能不能退回？第一问答不上来时，你打算怎么办？ <!-- quiz: q06 revision: 3 -->
   > **该观察到：** 第一问答不上来时，回去让它逐个文件用大白话解释、点出有风险的地方，直到你能用一句话复述；不能因为它语气肯定就放行。第二问靠事先写好的验收步骤和相关检查来回答；第三问看改动有没有碰到钱、个人数据、密钥、删除或发布，以及退路在哪里。三问都答得上来，再合并。
