Claude Code是Anthropic的编程智能体，可以探索仓库、修改文件、运行工具，并协助Git工作流。你可以通过终端、支持的编辑器或其他产品入口使用它。本章以终端为例，完成一次具体的入门练习。

安装与命令示例核查于**2026-10-22**。请记录实际安装版本：老教程可能仍在介绍已经变化的安装方式或界面。

## 一、安装并打开一个小项目

官方仓库推荐原生安装器。macOS或Linux的命令是：

```bash
curl -fsSL https://claude.ai/install.sh | bash
```

这条命令会下载并执行安装脚本，请确认使用官方地址，并遵循组织的安装规定。已有Homebrew的读者，也可以选`brew install --cask claude-code`。Windows用户可以使用官方仓库列出的方式：

```powershell
winget install Anthropic.ClaudeCode
```

选一种方式即可。**当前官方README已把npm安装标为弃用**；旧教程中的`npm install -g @anthropic-ai/claude-code`不再是首选起点。

然后确认命令可用，进入已有练习项目：

```bash
claude --version
claude --help
cd /path/to/your/project
git status
git switch -c practice/claude-first-task
claude
```

把路径换成真实目录。先保证工作区干净，或另行保存已有工作。按登录流程操作，再用`/status`查看会话和当前账号。符合条件的订阅登录与API配置是不同使用路径；装好CLI不会自动使API调用免费。

## 二、先调查，再完成一个修改

一个有用的初次请求是：

```text
阅读项目指引和 README。说明项目做什么、入口在哪里、
现有检查怎样运行。先不要修改，建议一处很小的文档改进。
```

看回答有没有引用真实文件和命令，再授权修改：

```text
完成刚才的文档改进，控制改动范围。
查看 diff 并做相关检查。报告修改的文件、实际运行的命令
以及还没解决的问题。不要推送或部署。
```

自己读一遍`git diff`。如果改的是功能，还要运行相应测试并实际尝试修改后的行为。对于陌生仓库，有文件路径支持的简明解释，比对项目“应该如何运作”的自信猜测更有用。

## 三、项目指引、记忆和技能不是一回事

`CLAUDE.md`保存项目约定、常用命令和限制。`/init`可以辅助起草，但生成后仍要检查。一个小例子：

```markdown
# 项目指引
- 改变行为前，先读 README 和现有实现。
- 使用仓库文档规定的包管理器和测试命令。
- 除非任务要求，不要手工修改生成文件。
- 示例使用虚构数据。
- 说明验证了什么，以及仍有哪些不确定性。
```

实际核对后，再把泛泛要求换成具体命令。不要把完整手册或密钥塞进来。

| 机制 | 保存什么 | 应怎样对待 |
| --- | --- | --- |
| `CLAUDE.md`与项目规则 | 在此项目工作的明确要求 | 像维护其他项目文档一样审查和更新 |
| 自动记忆（启用时） | 产品从以往工作中保留的笔记 | 查看并纠正，旧观察可能已经失效 |
| Skills | 可复用流程，以及可选脚本或参考文件 | 核对来源，任务匹配时使用 |
| 当前对话 | 此次任务的要求、证据和进度 | 换会话时交接关键状态 |

用`/memory`查看当前版本的记忆界面。持久化笔记和指引加载是产品能力，不意味着模型权重“学会了”你的项目。记忆里保存的说法，也不会因此自动变成事实。

## 四、按用途认识几个命令

| 会话内命令 | 用途 |
| --- | --- |
| `/help` | 查看可用命令 |
| `/status` | 查看会话和账号配置 |
| `/plan` | 进入任务规划流程 |
| `/permissions` | 查看或调整你有权管理的权限规则 |
| `/memory` | 查看项目指引和记忆控制 |
| `/usage` | 查看可用的用量与限制信息 |
| `/diff` | 在支持的界面查看改动 |

终端、编辑器和云端会话提供的命令可能不同。范围不清楚时，计划有帮助；但计划模式不能替代执行环境的权限控制。一旦你明确授权了一个有边界的修改，通常可以让智能体继续完成常规实现和检查，不必逐步重新批准。

## 五、看清执行与计费边界

遇到权限请求，读清楚具体行动：**什么命令、哪些文件或服务、产生什么后果？** 一次许可可能覆盖重复操作，不能假定以后每次都会再次弹窗。Shell命令、hooks、带脚本的skills和外部工具都能产生真实影响；Git分支无法撤回外部消息或付款。

产品支持且任务授权时，可以用子智能体分担调查或实现。明确各自范围，以及谁负责整合。不同对话不一定使用不同目录，并行修改可能互相覆盖。委派任务不会扩大原任务的权限。

结合`/status`和账号用量页面，区分：

- **订阅使用：** 按套餐规则消耗包含的额度。
- **API或其他服务商使用：** 按对应账号的账单和限制处理。
- **可选积分、付费模式或连接服务：** 启用后可能增加费用。

不能默认消费者订阅替API密钥买单，也不能断言长会话一定产生单独的token账单。用量异常时，先看当前凭据、模型／模式、任务长度、重复工具输出和后台工作，再考虑换套餐。

1. **[基础·概念题]** 哪条安装建议符合核查到的官方README？ <!-- quiz: q01 revision: 1 -->
   - A. npm是唯一入门方式
   - B. 所有使用入口都不需要安装
   - C. 选择列出的原生安装器或包管理器方式，npm安装已弃用
   - D. 同时安装所有发行方式
   > **答案C。** 官方推荐原生安装器，也列出Homebrew、WinGet等方式。选一种，并检查安装版本。

2. **[基础·概念题]** 什么适合写进`CLAUDE.md`？ <!-- quiz: q02 revision: 1 -->
   - A. 核实过的项目约定和常用命令
   - B. API密钥
   - C. 所有历史会话的完整日志
   - D. 以后不再受权限检查约束的假设
   > **答案A。** 项目指引应简洁、准确、有用，不应存放密钥或无限授权。

3. **[进阶·误区题]** 自动记忆保存了一个过时的测试命令，应怎样处理？ <!-- quiz: q03 revision: 1 -->
   - A. 相信记忆，忽略当前仓库
   - B. 立刻重新训练基础模型
   - C. 删除项目
   - D. 核实当前命令，并纠正保留的笔记
   > **答案D。** 记忆是存储的上下文，会过时。它不是绝对可靠的事实来源，也不是模型权重变化。

4. **[基础·情景题]** 开始长任务前，什么检查有助于避免费用意外？ <!-- quiz: q04 revision: 1 -->
   - A. 只检查安装是否成功
   - B. 检查当前账号、额度和已启用的付费附加项
   - C. 假定订阅包含每一次API调用
   - D. 让模型猜账单
   > **答案B。** 订阅额度、API计费和可选附加项需要分开确认。实际账号和用量页面提供相关证据。

5. **[进阶·情景题]** 两个子智能体准备修改仓库，什么措施有用？ <!-- quiz: q05 revision: 1 -->
   - A. 假定不同对话天然隔离文件
   - B. 让它们无协调地重写同一批文件
   - C. 分配不同文件责任或隔离工作树，并指定整合者
   - D. 给它们不受限制的外部服务凭据
   > **答案C。** 没有明确隔离时，并行工作者可能共享文件。范围、权限和整合仍需协调。

6. **[基础·操作题]** 写五条项目指引，其中区分一个核实过的命令、一项约定和一条数据处理限制；再与已有记忆对照。 <!-- quiz: q06 revision: 1 -->
   > **该观察到：** 项目指引表达应遵循的规则；记忆可能保存有用观察。但仓库变化时，两者都需要复查。
