附录C列的是工具里有哪些命令和开关；这份附录讲怎么把它们和你自己的规则、检查串起来，让编程智能体的工作可以信赖。业界把这一整套东西叫做harness。

## 一、Harness是什么意思

harness原意是套在马身上的挽具：马的力气没变，有了挽具，它才能拉着车往你要的方向走。用在AI上，截至2026年常见的说法是“智能体 = 模型 + harness”：harness指智能体里模型之外的一切，包括给模型的指令、它能调用的工具、反复调用模型直到任务完成的循环、决定每一步让模型看到什么的上下文管理，以及权限和检查。例如，Anthropic把Claude Agent SDK称为通用的智能体harness，并说明它提供的正是驱动Claude Code的那套工具、智能体循环和上下文管理。

对使用者来说，harness分两层。内层是工具自带的：Claude Code、Codex这类编程智能体已经内置了循环、读写文件和运行命令的工具、上下文压缩和许可机制，你一般改不了。外层是你自己搭的：项目规则文件、动手前看计划、自动测试和检查、人的验收。Thoughtworks的Birgitta Böckeler把外层的东西分成两类：事前引导，在它动手前告诉它怎么做，比如规则文件；事后检查，在它动手后发现问题、让它自己改，比如测试和代码检查。

下面是本书整理的一份工作清单，帮你搭这层外层。它综合了上述资料和本书第24至27章的做法，不是哪家厂商的官方方法。用Claude Code还是Codex，道理都一样。

## 二、你能搭的外层：四个部件

| 部件 | 属于哪类 | 作用 | 例子 |
| --- | --- | --- | --- |
| 项目规则文件 | 事前引导 | 每次开工都被放进上下文，告诉它本项目怎么做事 | `CLAUDE.md`、`AGENTS.md`（第28章、附录C） |
| 计划关口 | 事前引导 | 动手前先确认改哪些文件、复用什么 | 计划模式（第27章） |
| 自动检查 | 事后检查 | 每次改完都跑，出错就让它自己修 | 测试、代码检查、构建 |
| 人的验收 | 事后检查 | 确认行为符合要求，高风险改动再加一道复核 | 本附录第六节的清单（第25章） |

有一点要分清：规则文件只是放进上下文的文字，模型多半会照做，但不保证。真正要拦住的事，比如读取`.env`或删除目录，要靠工具的权限规则或沙箱来强制（第26章）。

## 三、五步工作流

把外层落到具体对话里，是下面五步。每一步给一句“对AI说的话”的范例，都是大白话提示词，不是产品命令。

| 步骤 | 这一步要它做什么 | 提示词范例 |
| --- | --- | --- |
| ① 调查 | 先摸清现状，别动手 | “动手前，先调查这个项目：整体结构、和这次需求类似的现有做法、可以复用的公共模块（网络请求、错误处理、日志、表单等）、命名和代码风格。带上文件路径列给我，先别写代码。” |
| ② 写规则 | 把调查结果固化成规则 | “把上面的调查结果整理成一份给AI看的项目规则：哪些机制必须复用、哪些事禁止做。” |
| ③ 计划关口 | 出方案，等你批准 | “任务是〈……〉。动手前先给计划：要改或加哪些文件、复用哪些现成机制、要不要加新依赖（要的话说明理由）。我批准前不要写代码。” |
| ④ 动手 | 顺着现有的来 | “批准。严格按现有的目录结构、命名和风格，复用刚才找到的公共模块来实现，不要自己引入新的抽象。” |
| ⑤ 验收 | 自检，再由你把关 | “对照刚才参考的现有写法自检：有没有自造轮子、有没有破坏整体设计、有没有绕开公共模块。然后用大白话告诉我你改了什么、哪里有风险。”之后按第六节的清单验收。 |

整套流程里最省返工的是第③步：动手前先看它要做什么。不少工具有计划模式帮你守住这一步（第27章、附录C）。

## 四、项目规则文件：可复制的雏形

第②步产出的规则，最好落成项目里的一个文件，让工具每次开工自动读取：Claude Code用`CLAUDE.md`（没有它时也会读`AGENTS.md`），Codex用`AGENTS.md`（附录C）。它看起来像“记住了项目规矩”，其实是产品每次开工都把它重新放进上下文，模型本身并不会记住（第13章）。所以写进文件的它才“记得”，规则越具体越稳。

下面是一份雏形，把`<...>`换成你项目的真实情况：

```markdown
# 项目规则 / AI协作规则

## 最重要的原则
- 顺着现有的实现方式和设计走，不要带入自己的流派。
- 引入任何新机制（库、抽象、分层）前，先查有没有同类的现成做法；有就复用，没有就先说明理由和替代方案，等我批准。
- 不做破坏整体架构（分层、依赖方向、命名规则）的改动。

## 工作流程
1. 先调查相关的现有实现和公共模块，列出参考位置（路径）。
2. 给出实现计划（改或加哪些文件、复用什么、要不要新依赖及理由），我批准后再写代码。
3. 改完运行现有的检查、格式化和测试：<例：npm run lint && npm test>，并报告结果。

## 技术栈与版本
- <例：TypeScript 5 / React 18 / Vite>

## 目录结构与职责
- <例：components/界面　hooks/逻辑　services/接口通信　utils/公共函数>
- 依赖方向：<例：界面 → hooks → services，单向，禁止反向或跨层>

## 必须复用的公共机制
- 网络请求：<例：services/apiClient>（不要到处直接写fetch）
- 错误处理：<例：AppError / errorHandler>
- 日志：<例：logger>（不要直接用console.log）

## 禁止事项
- 擅自新增第三方依赖
- 读取或打印.env等密钥文件
- 跨层依赖（如界面层直接访问数据库）
```

## 五、让它起作用的几条诀窍

| 诀窍 | 怎么做 |
| --- | --- |
| 规则写具体 | “写干净点”没用；要写明复用的模块名、文件路径和禁止事项 |
| 调查、计划、动手分开 | 别想一句话搞定全部；调查和计划批准各单独走一轮 |
| 小步走 | 一次改一大块最容易跑偏；拆小，每一步都验收 |
| 规则持续补 | 发现它跑偏，就把对应的规则补进文件，团队共享 |
| 让检查自动跑 | 把测试和代码检查的命令写进规则文件，要求它每次改完都跑并报告结果 |
| 别过度抽象 | “复用”过头会催生没必要的封装；贴着现有代码的颗粒度走 |

## 六、上线前检查清单

把这两张清单放在手边：交给AI之前过第一张，采用它的产出之前过第二张。

### 交给AI之前

- 要给的内容里有没有机密代码、生产数据、个人信息？有就先脱敏，或者干脆不给（第37章）。
- 有没有混进API密钥、密码、连接串？这些一律不给（第37章）。
- 用的服务和套餐，是不是公司或这个场景允许的？
- 有没有讲清前提：语言、框架、版本？
- 有没有给够上下文：相关代码、日志、期望的行为？

### 采用它的产出之前

不会写代码的人，不必逐行读懂每一处改动，但下面这些要做到：

- 用具体的验收检查确认行为：打开哪个页面、点哪里、应该看到什么；相关测试是否通过，原来的功能有没有坏（第25章）。
- 让智能体用大白话解释这次的diff：改了哪些文件、各自为什么改，并指出有风险的部分。改动范围和你的要求对不上，就先别采用。
- 凡是涉及钱、个人数据、密钥、删除文件或对外发布的改动，请第二个人复核：懂行的同事，或者至少另开一轮独立的审查。
- 回滚不了的操作不要运行：先确认改动已经提交到Git、数据有备份（第26章）。发出去的邮件、改过的线上数据，Git救不回来。
- 新加的依赖库来源可信吗，许可证允许你这样用吗（第39章）？
- 它提到的函数名、API和配置项真的存在吗？拿官方文档或实际运行结果核对（第9章）。
- 重要的事实、数字和引文，有没有自己复核（第39章）？

## 七、团队要立规矩时

一个人用靠习惯，一群人用要靠写下来的规矩。数据、授权、凭证和恢复这四条的写法见第40章；编程团队在此之外再补两件事：

1. 定审批流：AI生成的代码，从审查、合并到部署，谁来批准，按什么标准。
2. 建共享资产：把项目规则文件、常用提示词模板（附录B）整理出来团队共用，并定期复审，因为工具和模型都在变。

## 小结

- harness指智能体里模型之外的一切：指令、工具、循环、上下文管理、权限和检查。编程工具自带内层，你搭的是外层。
- 外层由事前引导（规则文件、计划关口）和事后检查（自动检查、人的验收）组成；真正要拦住的事，靠权限和沙箱强制，不能只写在规则里。
- 五步工作流里，动手前看计划最省返工。
- 采用产出前不必逐行读代码，但要用具体检查确认行为，让它解释diff和风险，高风险改动请第二个人复核，回滚不了的操作不运行。
