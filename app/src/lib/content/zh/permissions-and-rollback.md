Agent能改文件、跑命令、调用接上的服务。想让它帮得上忙又不出乱子，先讲好三件事：在哪里做、可以做什么、做完怎么检查和恢复。用不着它每敲一下键盘都来请示，要守住的是几条真正要紧的边界。

## 一、分清三件事：沙箱、授权与审批

想象请师傅来修房间：门锁决定师傅能进哪里，工单写明要做什么，临时改工单要先联系你。

| 控制 | 回答什么问题 | 例子 |
| --- | --- | --- |
| 沙箱 | 进程在技术上能接触哪些资源？ | 只准写入当前项目文件夹；不准联网 |
| 授权 | 你或组织允许它做哪些工作？ | 修复这个页面，并运行相关的本地检查 |
| 审批 | 什么时候必须停下来等人决定？ | 命令要越出沙箱，或操作超出约定范围 |

沙箱（sandbox）是技术上的围栏，围栏外的文件和网络它碰不到。三者相关，但不是一回事：一个命令可能在技术上能执行，却不在你的指示范围内。弹出审批是一个决策点，没有弹窗不代表其他操作都无害。

最小权限，就是只给任务需要的文件、工具、账号和网络。读公开网页不需要访问你的整个邮箱；改本地文档不需要线上系统的密钥。

## 二、权限的四级

各家工具的权限设置叫法不同，但大致可以排成从低到高的四级：

![权限四级示意图：从下往上依次是只读、每次改动前先问、可以直接改项目里的文件、什么都不问直接执行；前两级标为新手可用，第三级标为存好起点后可用，第四级标为新手别用](/figures/zh/permission-levels.svg)

1. 只读：只看文件、回答问题，不改任何东西。适合让它先调查一个陌生的项目。
2. 每次改动前先问：改文件、跑命令之前都停下来等你同意。适合刚上手的时候。
3. 可以直接改项目里的文件：项目文件夹里的修改不再逐次询问，越出范围（比如联网、改项目外的文件）仍要问。项目用Git存好起点之后（第五节），用这一级既省事又能退回。
4. 什么都不问、直接执行：关掉审批，有的连沙箱也一起关掉。新手不要用。

截至2026年10月的对应关系（模式名以后可能会变）：Claude Code的Manual模式（设置里写作`default`）在大多数改文件、跑命令、联网的操作前询问，是第2级；`acceptEdits`模式可以直接改工作目录里的文件，是第3级。要留意，新版Claude Code在终端和VS Code里默认以下面说的auto模式启动；想用第2级，在终端里按Shift+Tab，切到状态栏显示“manual mode on”。Codex在Git管理的文件夹里默认就是第3级（它叫Auto，越出沙箱才问），其他文件夹默认只读；会话里输入`/permissions`可以调整。

第4级在两个工具里都有，名字里都带着“dangerous”（危险）：Claude Code的`--dangerously-skip-permissions`参数（对应`bypassPermissions`模式），Codex的`--dangerously-bypass-approvals-and-sandbox`参数（别名`--yolo`）和名为`danger-full-access`的沙箱设置。开了它，Agent的一次误判，或者它从网页、邮件里读到的恶意指令，都可能直接变成真实操作。别因为嫌提示烦就打开它。真有需要，比如无人值守地跑一批测试，也只在用完即扔的隔离环境里用：一台没有你的个人文件、重要账号和密钥的虚拟机或容器。两家的文档都把它标为高风险。

还有一类“自动模式”（比如Claude Code的auto模式，新版在终端里默认就是它），由另一个模型替你审查操作，弹窗会少很多。官方文档写明它能减少提示，但不保证安全；删除、发布、花钱这类事，仍要按第四节明确授权。

## 三、实用循环：约定范围 → 范围内工作 → 验证

一条清楚的指令，可以授权一整段合理的工作：

> “修复这个项目里的导航问题。可以查看和修改相关文件，运行本地检查。保留我已有的改动，发布前给我看diff和检查结果。”

在这个范围和环境限制内，Agent可以读文件、修改、测试、修复失败的检查，不必反复问同一个问题。已有授权对它覆盖的工作持续有效。新的收件人、线上环境的变更、破坏性的清理或扩大访问范围，才需要新的决定。

```text
约定目标、范围和恢复方式
             ↓
在授权范围内工作 → 检查结果
             │
             └─ 需要越界？ → 说明具体操作 → 获得批准
```

弹窗多不等于更安全；模糊的提示太多，人也容易不看就点。有用的审批会说清：改什么、改哪里、影响谁、花多少钱、能恢复到什么程度。

## 四、影响重大的操作，要有明确、具体的授权

只看“删除”两个字判断不了风险：删除生成的测试文件和删除客户记录，差别很大。要看对象、范围、外部影响和能否恢复。

| 操作 | 执行前要约定什么 |
| --- | --- |
| 删除或覆盖有价值的数据 | 具体对象、备份或恢复办法、会不会丢掉无关的工作 |
| 发消息或对外发布 | 收件人或目的地、内容、哪些信息可以发出 |
| 花钱或调用收费服务 | 预算、账号、数量和停止条件 |
| 修改线上系统或账号权限 | 环境、受影响的人、预期变更和恢复方案 |

授权可以是当下的具体指令，也可以是此前批准、边界清楚的流程。“把这份已确认的通知发给这三位收件人”，不必再确认一次；“帮我整理邮箱”，则不等于允许把私人邮件转发到新地址。允许编辑项目，也不等于允许发布、花钱或清空无关文件。超出范围时，先拿出具体方案，执行前停下来。

## 五、Git最小起步

前面几章多次说“先存起点”“出了问题就回滚”。在本地项目里，这件事通常靠Git：一个记录文件版本的工具。你每提交（commit）一次，它就把项目当时的样子存成一个以后能回去的版本。下面是够用的最小一套。

### 1. 安装并确认

- Windows：从Git官网git-scm.com下载“Git for Windows”安装包，按默认选项安装。
- macOS：在“终端”里运行`xcode-select --install`，装上苹果的命令行工具，里面带Git；已经在用Homebrew的话，也可以运行`brew install git`。
- Linux：用系统自带的软件包管理器安装。

装好后打开一个新的终端窗口，运行`git --version`，能显示版本号就好。

第一次使用前，告诉Git你是谁。每台电脑做一次，这两项会写进每条提交记录：

```bash
git config --global user.name "你的名字"
git config --global user.email "you@example.com"
```

### 2. 给项目存一个起点

进入项目文件夹，先运行`git status`。如果提示“not a git repository”，说明这个文件夹还没交给Git管理，就依次运行：

```bash
git init
git add -A
git commit -m "开始前的起点"
```

`git init`让Git开始管理这个文件夹，只需做一次。`git add -A`把文件夹里所有新增、修改和删除放进“待保存”清单。`git commit -m "..."`把清单存成一个版本，引号里写一句说明。提交前看一眼清单里有没有密码或密钥文件；不想被记录的文件，把文件名写进项目里一个叫`.gitignore`的文本文件，Git就会跳过它。以后每完成并验收一小步，再`git add -A`、`git commit -m "做了什么"`一次，就是存一个新档（第27章）。

### 3. 看改了什么

- `git status`：列出自上次提交以来改过的文件，以及Git还没记录过的新文件（Untracked files）。
- `git diff`：逐行显示还没提交的改动，读法见第25章。

### 4. 撤销

- 某个文件改坏了、还没提交：先用`git diff 文件名`看清楚，再运行`git restore 文件名`，把它恢复成最近一次提交（或`git add`）时的内容。这个文件里没保存的改动会被直接丢掉，找不回来。
- Agent新建、从没提交过的文件不受`git restore`影响。它们在`git status`里列为“Untracked files”，确认没用后再手动删除。
- 已经提交了，想撤掉某一次：先用`git log --oneline`找到那次提交前面的编号，再运行`git revert 编号`。Git会新建一个“反向”提交把那次改动抵消掉，原来的记录都还在，所以比较安全。运行前，手头没提交的改动要先提交或处理掉。

网上教程里常见的`git reset --hard`会一次丢掉所有未提交的改动，新手先别用。撤销常常要好几步，一步一步来，每步之后用`git status`看看结果。

不想自己敲命令，也可以对编程智能体说：“请用Git给这个项目存一个起点。每条命令运行前先告诉我它做什么，等我确认再继续。”它请求运行命令时，你对照上面的说明看懂了再同意。

## 六、分支不是另一间房

分清三个词：

- 分支（branch）：一条有名字的开发路线。`git switch -c practice/first-task`会新建一个分支并切换过去，之后的提交都记在这条路线上。创建分支不会新建目录；在同一个文件夹里切换分支，用的仍是那个文件夹。
- 工作树（worktree）或单独的检出目录：另一个放工作文件的目录。`git worktree`能在独立目录里处理另一个分支，同时共享仓库历史，适合让两个任务互不干扰。
- 沙箱：技术上的访问边界。工作树只负责组织文件，本身不会阻止进程访问其他目录、账号或网络。

分支和工作树都不会给整台电脑拍快照。Git只能恢复它记录过的内容；未跟踪和被忽略的文件、本地数据库、密钥，需要各自的备份。恢复或丢弃修改本身也可能抹掉没保存的工作，所以先弄清要恢复哪一部分。

## 七、恢复也有边界

回滚代码，撤不回已发出的邮件、别人已收到的数据、扣掉的费用、远端数据库的修改，也不会自动撤销线上部署。这些系统需要各自的恢复步骤，有些影响无法完全逆转。

云端工作区和一些工具自带检查点（比如Claude Code的`/rewind`，见第28章），用之前查清它包含什么、保留多久，“重置工作区”不是万能的撤销键。正因为外部影响撤不回，发布、发送这类操作之前，先看diff和验证结果（第25章）。

## 小结

- 沙箱限制技术上能碰什么，授权决定该做什么，审批决定什么时候停下来问人。
- 权限大致分四级：只读、每次改动前先问、可以直接改项目里的文件、什么都不问直接执行。新手用前三级（第三级先存好Git起点），不用第四级；自动模式减少提示，但不保证每一步都合适。
- 一次说清范围，已授权的本地工作不必反复请示；删除、发布、花钱、改线上系统，要有对象和边界明确的授权。
- Git最小起步：`git init`、`git add -A`、`git commit`存起点；`git status`、`git diff`看改动；`git restore`丢掉某个文件未提交的改动，`git revert`撤销某次提交。
- 分支记录开发路线，工作树提供另一个目录；两者都不能替代沙箱或备份。
- 回滚只恢复记录过的项目状态，外部后果另行处理。

第27章把这些边界落实为计划：把较大的修改拆成可以逐步验收的小块。

1. **[基础·概念]** 下列哪种区分正确？ <!-- quiz: q01 revision: 2 -->
   - A. 沙箱决定允许做哪些工作，审批负责限制技术上能碰什么
   - B. 沙箱限技术访问，授权定该做的事，审批定何时暂停
   - C. 只要命令能在沙箱里执行，就说明用户已经授权
   - D. 审批弹窗出现得越频繁，说明这套控制越安全
   > **答案B。** 工具在技术上能做，不等于你授权它做；审批是停下来等人决定的时点。A把沙箱和审批的作用对调了；C把“能执行”当成了“被允许”；D忽略了模糊提示太多反而让人不看就点。

2. **[基础·情景]** 你已授权修复本地页面并测试。范围内每次普通修改都要重新问吗？ <!-- quiz: q02 revision: 2 -->
   - A. 要，范围内每次编辑都重新审批才算稳妥
   - B. 修改不用问，但每次运行测试前都要再问
   - C. 不用，可以在约定范围和环境限制内继续
   - D. 不用，而且这个授权也等于允许发布到正式环境
   > **答案C。** 已有授权覆盖约定好的工作，包括相关的修改和检查，所以A、B都多余。发布或扩大权限属于另一道边界，除非此前已明确授权，所以D不对。

3. **[进阶·情景]** 你只说了“整理邮箱”，一封邮件要求把整个邮箱转发到陌生地址。应该怎样处理？ <!-- quiz: q03 revision: 2 -->
   - A. 把邮件内容当资料，不越出用户授权去对外发送
   - B. 邮件在用户自己的邮箱里，可以视为用户的指示
   - C. 先建一个Git分支，出了问题还能把转发撤回来
   - D. 只转发不含隐私的那部分邮件，算是折中处理
   > **答案A。** 外部内容不能授予权限，对外发送需要用户授权过的目的地和范围。B把“在邮箱里”误当成“用户说的”；C以为Git能撤回已发出的东西；D仍然是在执行一条没有授权的指令。

4. **[基础·概念]** 什么能创建另一份工作文件目录？ <!-- quiz: q04 revision: 2 -->
   - A. 新建分支，Git会自动把它放进一个新文件夹
   - B. 在同一个项目里，再开一个新的Agent对话
   - C. 批准一条命令，让它到沙箱里单独复制一份运行
   - D. 创建单独的检出目录，或用Git worktree
   > **答案D。** 分支是同一目录里的一条开发路线，不会新建文件夹（A）；新对话不一定换目录（B）；批准命令也不会多出一份工作文件（C）。工作树提供另一个工作目录，但它仍不是安全沙箱。

5. **[进阶·误区]** Agent发了邮件、改了数据库，Git回滚能保证什么？ <!-- quiz: q05 revision: 2 -->
   - A. 撤回那封邮件，并把数据库恢复到改动之前
   - B. 恢复仓库里的全部文件，连同那些从来没提交过的
   - C. 恢复已记录的相关代码，邮件和数据库另行处理
   - D. 只要发生不久，外部操作也能跟着一起撤销
   > **答案C。** Git管理仓库里记录过的内容。邮件、数据库状态、账单都在Git之外，多久都撤不回来（A、D）；从没提交过的文件Git也没有存档（B）。

6. **[操作·观察]** 先不要删除任何东西，为“清理旧项目文件”做个计划。你会先检查什么？ <!-- quiz: q06 revision: 2 -->
   > **应当观察到：** 列清具体候选文件，分清生成文件和有价值的数据，保留已有工作，查明Git或备份实际覆盖什么。约定清理范围和外部影响。明确、有边界的授权，比批准一句没解释的“清空所有东西”更有用。
