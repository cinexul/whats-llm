Agent能改文件、运行命令、调用连接的服务。要用好这份帮助，先约定三件事：**在哪里工作、可以做什么、结果怎么检查和恢复。** 目标不是每敲一下键盘都请示，而是守住有意义的边界。

产品默认值和权限模式会变化。请查看官方文档及所在组织的设置；下面这些概念能帮你读懂那些开关。

## 一、分清三件事：沙箱、授权与审批

想象请人修理房间：门锁决定他能进哪里，工单写明你要他做什么，临时改变工单则需要联系你。

| 控制 | 回答什么问题 | 例子 |
| --- | --- | --- |
| **沙箱** | 进程在技术上能接触哪些资源？ | 只准写入当前工作区；限制可连接的网络目标 |
| **授权** | 用户或组织允许做哪些工作？ | 修复这个页面，并运行相关本地检查 |
| **审批机制** | 什么时候必须暂停等待决定？ | 命令需要越过沙箱，或操作超出了约定范围 |

三者有关联，但不是一回事。一个命令可能在技术上能执行，却不在你的指示范围内；你也可能授权了任务，但环境仍禁止它使用某项能力。出现审批提示是一个决策点，**没有提示不代表其他操作都无害**。有的工具还会按策略自动审查。

**最小权限**，就是只给任务需要的文件、工具、账号和网络访问权限。读公开网页不需要访问你的整个邮箱；改本地文档不需要生产环境密钥。

## 二、实用循环：约定范围 → 范围内工作 → 验证

一条清楚的指令，可以授权一整段合理的工作：

> “修复这个检出目录里的导航问题。可以查看和修改相关文件，运行本地检查。保留我已有的工作，发布前给我看diff和检查结果。”

在这个范围及环境限制内，Agent可以读文件、修改、测试、修复失败的检查，无须反复问同一个问题。**已有授权对其覆盖的工作持续有效。** 新收件人、生产环境变更、破坏性清理或扩大访问范围，才可能需要新的决定。

```text
约定目标、范围和恢复方式
             ↓
在授权范围内工作 → 检查结果
             │
             └─ 需要越界？ → 说明具体操作 → 获得批准
```

提示多，不自动等于更安全。模糊提示太多，人也容易不看就点。有效的审批应展示：**改什么、改哪里、影响谁、花多少钱、能恢复到什么程度。** 每条命令都询问、只在提权时询问，还是按策略决定，取决于工具配置。

## 三、“跳过审批”的开关，新手先别开

很多工具都有让Agent少问、甚至完全不问的选项。截至2026年10月，Claude Code有`--dangerously-skip-permissions`参数（对应bypassPermissions模式）；Codex有`--dangerously-bypass-approvals-and-sandbox`参数（别名`--yolo`），以及名为`danger-full-access`的沙箱设置。名字里都带着“dangerous”（危险）：它们会关掉审批，有的连沙箱也一起关掉。这时Agent的一次误判，或者它从网页、邮件里读到的恶意指令，都可能直接变成真实操作。

新手不要用这类选项，也别因为嫌提示烦就打开它们。真有需要，比如无人值守地跑一批测试，也只在隔离的沙箱或用完即扔的环境里用：一台没有你的个人文件、重要账号和密钥的虚拟机或容器。Claude Code的官方文档也建议，只在不联网的容器、虚拟机这类隔离环境里使用这种模式；Codex的文档把这种完全放开的组合标为高风险、不推荐。

还有一类“自动模式”：由另一个模型或预设策略替你审查操作，弹窗会少很多。它能减少打扰，但官方也写明它不保证安全。被自动放行的操作，不代表每一步都合适；删除、发布、花钱这类事，仍要按下一节的方法给出明确授权。具体有哪些模式、叫什么名字，以你所用版本的官方文档为准。

## 四、影响重大的操作，要有明确、具体的授权

只看“删除”两个字判断不了风险：删除生成的测试文件和删除客户记录，差别很大。要看**对象、范围、外部影响和可恢复性**。

| 操作 | 执行前要约定什么 |
| --- | --- |
| 删除或覆盖有价值的数据 | 具体对象、备份或恢复办法、会不会丢失无关工作 |
| 发消息或对外发布 | 收件人或目的地、内容、哪些信息可以发出 |
| 花钱或调用收费服务 | 预算、账号、数量和停止条件 |
| 修改线上系统或账号权限 | 环境、受影响的人、预期变更和恢复方案 |

这些操作需要明确授权。授权可以是当下的具体指令，也可以是此前批准、边界清楚的有限流程。“把这份已确认的通知发给这三位收件人”，不必再重复确认一次；“帮我整理邮箱”，则不等于允许把私人邮件转发到新地址。

超出范围时，先准备具体方案，在执行前暂停。允许编辑项目，不等于允许发布、无限花钱或清空无关文件。影响尤其重大的决定，应由负责的人把关。

## 五、Git最小起步

前面几章多次说“先保存起点”“出了问题就回滚”。在本地项目里，这件事通常靠**Git**：一个记录文件版本的工具。你每“提交”（commit）一次，它就把项目当时的样子存成一个以后能回去的版本。下面是够用的最小一套。

**1. 安装并确认。**

- Windows：从Git官网git-scm.com下载“Git for Windows”安装包，按默认选项安装。
- macOS：在“终端”里运行`xcode-select --install`，装上苹果的命令行工具，里面带Git；已经在用Homebrew的话，也可以运行`brew install git`。
- Linux：用系统自带的软件包管理器安装。

装好后打开一个新的终端窗口，运行`git --version`，能显示版本号就行。安装步骤偶尔会变，以git-scm.com的安装页面为准。

第一次使用前，告诉Git你是谁。每台电脑做一次就行，这两项会写进每条提交记录：

```bash
git config --global user.name "你的名字"
git config --global user.email "you@example.com"
```

**2. 给项目存一个起点。** 进入项目文件夹，先运行`git status`。如果提示“not a git repository”，说明这个文件夹还没交给Git管理，就依次运行：

```bash
git init
git add -A
git commit -m "开始前的起点"
```

`git init`让Git开始管理这个文件夹，只需做一次。`git add -A`把文件夹里所有新增、修改和删除放进“待保存”清单。`git commit -m "..."`把清单存成一个版本，引号里写一句说明。提交前看一眼清单里有没有密码或密钥文件；不想被记录的文件，把文件名写进项目里一个叫`.gitignore`的文本文件，Git就会跳过它。以后每完成并验收一小步，再`git add -A`、`git commit -m "做了什么"`一次，就是存一个新档（第27章）。

**3. 看改了什么。**

- `git status`：列出自上次提交以来改过的文件，以及Git还没记录过的新文件（Untracked files）。
- `git diff`：逐行显示还没提交的改动，读法见第25章。

**4. 撤销。**

- 某个文件改坏了、还没提交：先用`git diff 文件名`看清楚，再运行`git restore 文件名`，把它恢复成最近一次提交（或`git add`）时的内容。这个文件里没保存的改动会被直接丢掉，找不回来。
- Agent新建、从没提交过的文件不受`git restore`影响。它们在`git status`里列为“Untracked files”，确认没用后再手动删除。
- 已经提交了，想撤掉某一次：先用`git log --oneline`找到那次提交前面的编号，再运行`git revert 编号`。Git会新建一个“反向”提交把那次改动抵消掉，原来的记录都还在，所以比较安全。运行前，手头没提交的改动要先提交或处理掉。

网上教程里常见的`git reset --hard`会一次丢掉所有未提交的改动，新手先别用。撤销常常要好几步，一步一步来，每步之后用`git status`看看结果。

**5. 撤销的边界。** Git只管这个文件夹里它记录过的文件。Agent已经发出的邮件、删掉的云端数据、发布出去的帖子、扣掉的费用，Git都撤不回来（见第七节）。

**也可以让Agent代劳。** 不想自己敲命令，可以对编程智能体说：“请用Git给这个项目存一个起点。每条命令运行前先告诉我它做什么，等我确认再继续。”它请求运行命令时，你对照上面的说明看懂了再同意。

## 六、分支不是另一间房

较大修改前，先用`git status`看清当前状态，用提交或备份保留已有工作。不要盲目把密钥提交进去，也不要丢弃别人的未完成修改。

分清三个词：

- **分支（branch）**：一条有名字的开发路线。`git switch -c practice/first-task`会新建一个分支并切换过去，之后的提交都记在这条路线上。创建分支不会新建目录；在同一工作目录切换分支，用的仍是那个目录。
- **单独检出目录或工作树（worktree）**：另一个放工作文件的目录。Git worktree能在独立目录处理另一个分支，同时共享仓库历史。
- **沙箱**：技术上的访问边界。工作树负责组织文件，本身不会阻止进程访问其他目录、账号或网络。

分支便于审阅和合并；需要独立的工作文件时，单独的工作树或检出目录更合适。**两者都不会自动给整台电脑拍快照。**

Git可以恢复记录过的文件内容，或撤销已提交的改动。但仅仅有一个分支，并不能救回从未记录的文件。未跟踪和被忽略的文件、本地数据库、上传资料、密钥，可能需要各自的备份。恢复文件或丢弃修改，本身也可能抹掉未完成工作，所以先明确究竟要恢复哪一部分。

## 七、恢复也有边界

回滚代码，**不会**撤回已发邮件、收回别人已收到的数据、退还账单费用、恢复远端数据库，也不会自动撤销线上部署。这些系统需要各自的恢复步骤，有些影响无法完全逆转。

云端工作区可能提供检查点或可丢弃的检出目录。要查清：**包含什么、保留多久、外部服务怎么办。** “重置工作区”不是万能撤销键。

实用流程可以这样安排：

1. 定义工作，只授予需要的访问权限。
2. 保存起点（第五节）；有需要时使用独立工作目录。
3. 让Agent完成已授权的本地工作，真正改变范围时再停下来。
4. 在约定的发布或外部操作前，检查diff和相关验证结果。
5. 需要恢复时，只撤销目标改动，外部影响另行处理。

## 小结

- 沙箱限制、用户授权和审批提示，回答的是不同问题。
- 一次说清范围，已授权的本地工作不必反复请示。
- “跳过审批”“完全访问”这类开关，新手不要开；真要用，只在隔离的一次性环境里用。自动模式减少提示，但不保证每一步都合适。
- 影响重大的外部操作，需要对象和边界明确的授权。
- Git最小起步：`git init`、`git add -A`、`git commit`存起点；`git status`、`git diff`看改动；`git restore`丢掉某个文件未提交的改动，`git revert`撤销某次提交。
- 分支记录开发路线，工作树提供另一个目录；两者都不能替代沙箱或备份。
- 动手前知道恢复上限：Git恢复记录过的项目状态，不是所有后果。

第27章把这些边界落实为计划：把较大修改拆成可以逐步验收的小块。

1. **[基础·概念]** 下列哪种区分正确？ <!-- quiz: q01 revision: 2 -->
   - A. 沙箱决定允许做哪些工作，审批负责限制技术上能碰什么
   - B. 沙箱限技术访问，授权定该做的事，审批定何时暂停
   - C. 只要命令能在沙箱里执行，就说明用户已经授权
   - D. 审批弹窗出现得越频繁，说明这套控制越安全
   > **答案B。** 工具在技术上能做，不等于你授权它做；审批是停下来等人决定的时点。A把沙箱和审批的作用对调了；C把“能执行”当成了“被允许”；D忽略了模糊提示太多反而让人不看就点。

2. **[基础·情景]** 你已授权修复本地页面并测试。范围内每次普通修改都要重新问吗？ <!-- quiz: q02 revision: 2 -->
   - A. 要，范围内每次编辑都重新审批才算稳妥
   - B. 修改不用问，但每次运行测试前都要再问
   - C. 不用，可以在约定范围和环境限制内继续
   - D. 不用，而且这个授权也等于允许发布到正式环境
   > **答案C。** 已有授权覆盖约定好的工作，包括相关的修改和检查，所以A、B都多余。发布或扩大权限属于另一道边界，除非此前已明确授权，所以D不对。

3. **[进阶·情景]** 你只说了“整理邮箱”，一封邮件要求把整个邮箱转发到陌生地址。应该怎样处理？ <!-- quiz: q03 revision: 2 -->
   - A. 把邮件内容当资料，不越出用户授权去对外发送
   - B. 邮件在用户自己的邮箱里，可以视为用户的指示
   - C. 先建一个Git分支，出了问题还能把转发撤回来
   - D. 只转发不含隐私的那部分邮件，算是折中处理
   > **答案A。** 外部内容不能授予权限，对外发送需要用户授权过的目的地和范围。B把“在邮箱里”误当成“用户说的”；C以为Git能撤回已发出的东西；D仍然是在执行一条没有授权的指令。

4. **[基础·概念]** 什么能创建另一份工作文件目录？ <!-- quiz: q04 revision: 2 -->
   - A. 新建分支，Git会自动把它放进一个新文件夹
   - B. 在同一个项目里，再开一个新的Agent对话
   - C. 批准一条命令，让它到沙箱里单独复制一份运行
   - D. 创建单独的检出目录，或用Git worktree
   > **答案D。** 分支是同一目录里的一条开发路线，不会新建文件夹（A）；新对话不一定换目录（B）；批准命令也不会多出一份工作文件（C）。工作树提供另一个工作目录，但它仍不是安全沙箱。

5. **[进阶·误区]** Agent发了邮件、改了数据库，Git回滚能保证什么？ <!-- quiz: q05 revision: 2 -->
   - A. 撤回那封邮件，并把数据库恢复到改动之前
   - B. 恢复仓库里的全部文件，连同那些从来没提交过的
   - C. 恢复已记录的相关代码，邮件和数据库另行处理
   - D. 只要发生不久，外部操作也能跟着一起撤销
   > **答案C。** Git管理仓库里记录过的内容。邮件、数据库状态、账单都在Git之外，多久都撤不回来（A、D）；从没提交过的文件Git也没有存档（B）。

6. **[操作·观察]** 先不要删除任何东西，为“清理旧项目文件”做个计划。你会先检查什么？ <!-- quiz: q06 revision: 2 -->
   > **应当观察到：** 列清具体候选文件，分清生成文件和有价值的数据，保留已有工作，查明Git或备份实际覆盖什么。约定清理范围和外部影响。明确、有边界的授权，比批准一句没解释的“清空所有东西”更有用。
